# 最小有效 Prompt

> [!important] 一句话核心
> 从能够表达任务契约的最简单直接指令开始，只为已经观察到的失败增加复杂度。

## 为什么要保持最小

长 prompt 不天然更可靠。每增加一条规则、一个示例或一个阶段，都可能引入：

- 新的指令冲突。
- 更多上下文成本和延迟。
- 示例对行为的意外偏置。
- 更难定位的失败原因。
- 更高的模型迁移和维护成本。

最小 prompt 的目的不是追求最短字符数，而是让每一部分都能追溯到 [[01-task-contract|任务契约]] 或真实失败。

## 最小 Baseline

一个通用 baseline 只需要五部分：

```text
<task>
{{模型要完成的具体动作}}
</task>

<input>
{{待处理数据}}
</input>

<constraints>
{{必须遵守的任务边界和未知值行为}}
</constraints>

<output>
{{输出语义和可验收要求}}
</output>

<success>
{{怎样判断结果合格}}
</success>
```

标签不是必须使用 XML。Markdown 标题、清晰分隔符或 API 消息角色也可以；关键是结构一致、边界明确。

## 最小干预阶梯

按以下顺序处理，在足以解决问题的位置停止：

1. 把类型、枚举、解析和确定性规则交给 schema 或代码。
2. 删除含糊、重复和不可检查的措辞。
3. 明确任务、输入边界和禁止越界的范围。
4. 明确输出语义、长度和未知值行为。
5. 调整稳定规则、材料、任务和最终问题的顺序。
6. 加入最少且具有区分力的示例。
7. 只有单步确实不可靠时才拆解、路由或 chaining。
8. 最后才考虑模型专属提示或 sampling parameters。

这个顺序体现了一个原则：==先移走不应由 prompt 承担的责任，再改 prompt==。

## 根据失败增加内容

| 观察到的失败 | 首个改动假设 | 不应默认添加 |
|---|---|---|
| 任务理解错误 | 改写目标和动作动词 | 角色背景故事 |
| 漏掉输入范围 | 增加边界和分隔 | 更多同义指令 |
| 不知道材料不足 | 定义证据与未知值策略 | “绝对不要幻觉” |
| 格式可变 | 使用 schema；补充字段语义 | 复杂 JSON 示例堆叠 |
| 分类边界不稳定 | 加入少量边界示例 | 大量容易样例 |
| 输出过长 | 指明必须保留和优先省略的内容 | 只写“简洁” |
| 复合任务漏步骤 | 拆成有输入输出契约的阶段 | 要求展示完整内部推理 |
| 工具选择错误 | 明确 tool routing 和参数来源 | 无限制重试 |

## Few-shot 的正确位置

Few-shot 适合直接指令难以稳定表达的判断边界、格式或风格。示例应当：

- 覆盖真实变化和关键边界，而不是重复容易样例。
- 使用一致的标签、字段和输出结构。
- 与当前约束保持一致。
- 包含任务真正关心的区分，而不是额外装饰。
- 从能够表达规则的最少数量开始，再通过 eval 决定是否增加。

> [!warning] 示例是行为规格，不是背景材料
> 一个错误、矛盾或多余的示例会比抽象指令更强地影响输出。没有样例库和验证证据时，不要引入动态示例选择系统。

## 复杂推理如何表达

现代推理模型通常具有内部推理能力，不应把“展示完整思维过程”当成通用技巧。更可靠的做法是要求可检查的外部产物：

- 列出假设、依据和不确定项。
- 将复杂任务拆成有明确输入输出的阶段。
- 对计算使用代码工具。
- 对事实结论给出来源引用。
- 对最终结果执行独立规则校验。

需要判断 CoT、Least-to-Most、Self-Consistency、ToT、Step-Back 或工具增强是否适用时，先阅读 [[04-reasoning-strategies|推理增强策略]]；需要把策略实现为可恢复的多步系统时，详见 [[13-decomposition-and-agent-workflows|任务拆解与 Agent 工作流]]。

## Prompt 中的正向与禁止规则

优先描述期望行为：

```text
弱：不要啰嗦，不要重复，不要写无关内容。

强：输出最多三项；每项包含结论和一条依据；
优先保留会改变决策的信息，省略背景复述。
```

禁止规则只用于真实失败、安全边界或硬约束。大量否定句会增加冲突，却不一定告诉模型应该怎样做。

## 一轮最小迭代

1. 用 [[01-task-contract|任务契约]] 写 baseline。
2. 在代表性输入上运行并保存原始输出。
3. 把失败归类为具体、可观察的问题。
4. 提出一个可证伪的改动假设。
5. 只修改一个主要变量。
6. 在相同条件下重新运行。
7. 改善则保留，否则回滚。

详见 [[14-evaluation-and-iteration|Prompt 评估与迭代]]。

## 删除检查

完成初稿后，对每一段提问：

- 它对应哪一项任务契约或哪个失败样例？
- 删除后，哪个可观察指标会变差？
- 这件事是否应该由 schema、代码、tool 或模型选择解决？
- 是否与其他规则重复或冲突？
- 是否包含会快速过期的模型专属建议？

无法回答的内容通常应该删除。

## 常见误区

- **一次加入所有技巧**：无法判断究竟哪项改动有效。
- **固定示例数量**：示例数量应由边界覆盖、上下文预算和 eval 决定。
- **把角色当成能力升级**：虚构资历不能弥补规则和证据缺失。
- **只改措辞不保留 baseline**：无法证明质量发生变化。
- **要求模型反复自检**：确定性校验应交给程序，事实校验需要独立证据。
