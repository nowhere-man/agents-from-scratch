# 工具、状态与授权边界

> [!important] 一句话核心
> Agent prompt 不只是告诉模型“使用工具”，而是定义工具路由、参数来源、状态恢复、副作用授权和失败停止条件。

## Tool Calling 的真实职责

工具用于模型本身不能可靠完成的工作：

- 获取实时或私有数据。
- 精确计算和代码执行。
- 查询结构化系统。
- 写入外部状态或发送消息。
- 调用领域服务。

模型负责选择工具和解释结果；程序负责暴露能力、验证参数、执行动作和返回真实状态。

## 好的工具定义

每个工具只需要清楚说明：

- **用途**：它解决什么问题。
- **必填输入**：字段语义和允许范围。
- **输出**：成功与失败的可检查结构。
- **副作用**：是否读取、写入、发送、购买或删除。
- **主要失败**：超时、权限不足、资源不存在等。

工具描述应简洁且可区分。暴露大量作用重叠的工具，会增加错误选择和参数混淆。

## Tool Routing

为每个工具定义四类规则：

| 路由问题 | 示例 |
|---|---|
| 何时必须调用 | 用户问实时余额时必须查询账户服务 |
| 何时可以调用 | 静态解释通常不需要查询 |
| 何时禁止调用 | 未授权时禁止执行退款 |
| 参数不足怎么办 | 从可信状态推导、请求补充或停止 |

独立读取可以并行；存在数据依赖或副作用的调用必须按顺序执行。不要为了速度并行化相互依赖的动作。

## 授权按影响分层

可以采用简单的风险模型：

| 风险 | 典型动作 | 默认处理 |
|---|---|---|
| 低 | 读取、分析、本地无副作用验证 | 在任务范围内执行 |
| 中 | 修改草稿、更新配置、可逆外部写入 | 明确范围并记录结果 |
| 高 | 发送、购买、删除、生产发布、权限变化 | 执行前获得明确授权 |

授权只覆盖用户已经说明的对象、范围和动作。例如“更新这份草稿”不等于“发布到生产”，也不等于“发送给所有客户”。

> [!warning] Schema 通过不等于获得授权
> 模型生成了合法的 `refund(amount=500)` 参数，只说明数据形状有效；程序仍需验证账户、金额、策略和用户授权。

## 状态模型

Agent 运行状态分为：

- **稳定规则**：长期职责、安全和固定工具边界。
- **任务状态**：目标、当前步骤、决定、未完成事项。
- **证据状态**：tool 结果、来源、版本和不确定项。
- **授权状态**：谁在何时授权了什么对象和动作。

状态应存储在可信位置并带任务 ID、版本和时间。不要把模型自然语言总结当作唯一真相，也不要默认旧授权永久有效。

```yaml
task_id: refund-review-1842
step: awaiting_approval
facts:
  order_id: A-1024
  eligible_amount: 120.00
authorization:
  status: not_granted
  scope: null
pending:
  - request_explicit_refund_approval
```

## 恢复流程

跨窗口、压缩或中断后：

1. 从可信存储读取稳定规则和最近状态。
2. 验证任务 ID、版本和来源。
3. 重建已完成与未完成事项。
4. 重新确认授权边界和高风险动作。
5. 只加载继续当前步骤所需证据。
6. 不重复已经成功完成的副作用。

详见 [[10-context-and-instruction-architecture|上下文与指令架构]]。

## 失败与重试

Tool 失败应结构化返回：

```json
{
  "status": "retryable_error",
  "code": "UPSTREAM_TIMEOUT",
  "message": "查询服务超时",
  "retry_after_ms": 1000
}
```

重试策略至少定义：

- 哪些错误可恢复。
- 最大尝试次数或时间预算。
- 是否需要更换参数或工具。
- 何时降级、人工接管或停止。
- 如何避免重复副作用。

不可恢复错误和权限拒绝不应通过无限重试绕过。

## Tool 结果也是输入

使用 tool 结果前检查：

- 调用是否真正成功。
- 返回对象是否属于当前任务。
- 来源、时间和版本是否正确。
- 字段是否完整。
- 结果是否包含不可信文本。
- 是否需要第二个来源或业务校验。

模型不能在 tool 返回成功之前声称动作已完成。涉及不可逆结果时，执行后还应核对最终状态。

## Prompt 应明确什么

Agent prompt 保留模型需要作出的语义判断：

- 工具选择标准。
- 参数缺失时的行为。
- 哪些结果需要进一步确认。
- 哪些动作必须请求授权。
- 达到什么条件应停止。

确定性权限检查、参数验证、幂等性和重试计数应由程序实现。

## 常见误区

- **工具越多越强**：重叠能力会降低路由可靠性。
- **让模型自行判断所有权限**：高风险授权必须由系统验证。
- **把历史消息当长期状态**：难以保证版本和恢复一致性。
- **失败时反复调用同一参数**：没有新的假设，只会放大成本和副作用风险。
- **看到返回文本就声称成功**：应检查状态码、字段和真实外部状态。
- **旧授权自动延续**：授权必须绑定对象、动作和有效范围。

## 检查表

- [ ] 只暴露当前任务可能需要的工具。
- [ ] 每个工具用途、输入、输出、副作用和失败明确。
- [ ] 必须、可选和禁止调用条件明确。
- [ ] 参数来源可追溯，不从不可信文本直接执行。
- [ ] 高风险动作在执行前验证授权。
- [ ] 状态包含任务、证据和授权版本。
- [ ] 重试有限制，并避免重复副作用。
- [ ] Tool 成功后才声明完成。
