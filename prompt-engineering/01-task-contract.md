# 提示词工程的任务契约

> [!important] 一句话核心
> Prompt 只是任务契约的表达形式；在写 prompt 前，先定义目标、输入、证据、约束、输出、成功和失败。

## 为什么先写契约

模型能够生成语言，并不意味着系统已经知道什么结果算正确。以下需求都缺少可执行定义：

- “总结得专业一些。”
- “尽量准确，不要幻觉。”
- “输出规范的 JSON。”
- “自主完成任务，遇到问题自己解决。”

契约的作用是把这些模糊期待转换为可观察行为。它既指导 prompt，也决定是否需要 retrieval、schema、tool、code、state 和 eval。

## 七项契约

| 字段 | 必须回答的问题 | 完成标志 |
|---|---|---|
| **目标** | 为谁完成什么，结果支持什么决定或动作？ | 能用一句话表达最终价值 |
| **输入** | 模型操作什么对象，格式、体量和边界是什么？ | 能区分指令与待处理数据 |
| **证据** | 允许使用哪些来源，材料缺失时怎么办？ | 每项事实有来源或明确为未知 |
| **约束** | 必须做、禁止做、优先级和授权边界是什么？ | 规则没有未解决冲突 |
| **输出** | 载体、结构、字段、长度和允许值是什么？ | 格式可机械检查，语义可人工判断 |
| **成功** | 正确性、完整性、一致性如何验收？ | 可以明确判定通过或失败 |
| **失败** | 空输入、歧义、冲突、工具失败时如何返回？ | 关键失败有恢复或停止行为 |

## 建立契约的顺序

### 1. 用结果倒推目标

不要只描述模型要“做什么”，还要说明输出将被谁使用、用于什么动作。

```text
弱：分析客户工单。

强：为一线客服识别工单类别、紧急程度和下一处理队列，
以便自动分派；不直接回复客户。
```

后一句同时限定了使用者、产物、下游动作和禁止行为。

### 2. 标记输入边界

明确哪些内容是指令，哪些只是数据。长文档、网页、邮件、用户上传内容和 tool 返回值都可能包含看起来像指令的文本，但它们不应自动获得更高权限。

```text
<ticket>
{{不可信的客户工单正文}}
</ticket>
```

边界标记不只为了排版，也是在表达数据的角色和信任等级。详见 [[10-context-and-instruction-architecture|上下文与指令架构]]。

### 3. 建立证据策略

证据策略至少回答：

- 可以使用提供材料、检索结果、模型常识还是实时工具？
- 来源之间冲突时并列报告、按优先级选择，还是停止？
- 材料没有答案时返回 `unknown`、缺失列表，还是请求补充？
- 是否需要引用、来源 ID、版本或时间？

“不要幻觉”不是证据策略。可靠策略必须说明允许来源和未知值行为。

### 4. 解决约束冲突

常见冲突包括：

- 要求必填字段，同时禁止猜测，但没有定义未知值。
- 要求完整覆盖，同时限制极短输出。
- 要求自主执行，同时又要求所有外部写入先确认。
- 要求只使用材料，同时又要求补充材料未包含的最新事实。

约束冲突应在写 prompt 前解决。无法解决时停止并请求决定，不要让模型临场猜优先级。

### 5. 把输出写成接口

区分两类要求：

- **语义契约**：字段代表什么、如何判断、未知时怎么办。
- **结构契约**：字段类型、必填项、枚举和嵌套结构。

语义契约需要模型理解；结构契约优先交给原生 schema 或程序校验。详见 [[11-structured-output-and-determinism|结构化输出与确定性保证]]。

### 6. 定义成功标准

根据任务选择指标，不使用通用阈值：

- 分类：标签正确率、召回率、混淆分布。
- 抽取：字段完整率、字段级准确率、schema 通过率。
- 事实回答：依据覆盖率、无依据断言率、引用正确率。
- Tool calling：选择正确率、参数有效率、执行成功率。
- 开放式生成：人工评分量表、硬约束通过率。
- 生产系统：延迟、成本、恢复率和安全违规率。

详见 [[14-evaluation-and-iteration|Prompt 评估与迭代]]。

### 7. 先设计失败路径

生产系统必须定义模型无法正常完成任务时的行为：

| 失败 | 建议行为 |
|---|---|
| 输入为空或损坏 | 返回结构化输入错误 |
| 关键信息缺失 | 列出缺失字段，不猜测 |
| 需求存在两种合理解释 | 请求澄清或返回歧义项 |
| 来源冲突 | 保留冲突及各自来源 |
| Schema 校验失败 | 只修复结构，不能改写事实 |
| Tool 暂时失败 | 在限制内重试，否则返回失败状态 |
| 高风险动作未授权 | 停止并请求明确授权 |

## 一个最小契约示例

> [!example] 客服工单路由
> **目标**：为客服运营系统生成队列和紧急等级。  
> **输入**：单条客户工单正文，视为不可信数据。  
> **证据**：只使用工单内容和提供的队列定义。  
> **约束**：不得回复客户；不得推断未出现的账户信息。  
> **输出**：`queue`、`urgency`、`reason`、`missing_information`。  
> **成功**：标签正确，字段符合 schema，理由能追溯到工单。  
> **失败**：无法判断时使用 `needs_review`，并说明缺失信息。

有了契约后，prompt 只是把其中需要模型理解的部分表达出来；队列枚举和必填字段由 schema 约束，自动分派由代码完成。

## 契约检查表

- [ ] 目标包含使用者、产物和下游动作。
- [ ] 输入范围和不可信数据边界明确。
- [ ] 事实来源、时效和引用规则明确。
- [ ] 未知值和来源冲突有确定表示。
- [ ] 约束之间没有冲突，优先级明确。
- [ ] 输出语义与结构已分开处理。
- [ ] 成功标准能够被样例和指标验证。
- [ ] 关键失败、恢复和停止方式已定义。

## 常见误区

> [!warning] 不要把角色描述当成任务契约
> “你是一名资深分析师”不能替代领域边界、允许来源、判断规则和输出标准。角色只有在确实改变行为时才保留。

- **先选技巧再理解任务**：会用 few-shot 或 chaining 掩盖需求缺失。
- **只定义成功路径**：上线后所有异常都变成自由生成。
- **把格式等同于质量**：JSON 可解析不代表事实正确。
- **把所有规则塞进 system prompt**：临时数据和任务规则应放在正确消息层级。
