# Prompt 评估与迭代

> [!important] 一句话核心
> Prompt 优化是受控实验：固定条件、保留 baseline、按失败提出假设、每轮只改变一个主要变量。

## 为什么 Eval 是提示词工程的一部分

模型输出具有随机性，也会随模型版本、工具、上下文和运行参数变化。仅凭一个演示样例无法判断 prompt 是否稳定，更无法判断改动是否改善整体表现。

Eval 连接了两端：

- [[01-task-contract|任务契约]] 定义什么叫成功。
- Eval 用样例、评分和运行记录检查是否成功。

没有 eval，prompt 只能“看起来更好”。

## 建立测试集

测试集应来自真实任务分布和已知失败，包括：

- 常见正常输入。
- 关键边界和罕见但高风险输入。
- 空值、歧义、冲突和材料不足。
- Tool、schema 和权限失败。
- 对抗或不可信内容，只在任务存在相应边界时加入。

不要追求固定样例数量。覆盖程度由任务风险、输入多样性、成本和上线范围决定。

每个样例保存：

```yaml
id: ticket-042
input_ref: fixture/ticket-042.json
expected:
  queue: billing
  must_not_reply: true
rubric:
  - 标签符合人工基准
  - evidence 引用输入原文
  - schema 通过
```

## 指标设计

根据任务选择指标：

| 任务 | 主要指标 |
|---|---|
| 分类 | 正确率、召回率、混淆分布 |
| 抽取 | 字段完整率、字段级准确率 |
| Structured Outputs | 解析率、schema 通过率 |
| 事实回答 | 依据覆盖、无依据断言、引用正确率 |
| Tool calling | 工具选择、参数有效、执行成功 |
| 开放式生成 | 人工 rubric、硬约束通过率 |
| Agent 工作流 | 完成率、恢复率、步骤/工具成本 |
| 生产运行 | 延迟、token、费用、安全违规率 |

结构正确、事实正确和业务有用是不同指标，不能用一个总分掩盖。

## 固定运行条件

比较版本时固定：

- 模型和版本。
- Prompt、tool 定义和 schema。
- Sampling 与 reasoning 参数。
- Retrieval 数据与排序。
- 测试集和评分方式。
- 超时、重试和预算。

保存原始输出和运行元数据，确保结果可复现。若同时更换模型、prompt 和参数，就无法把变化归因到某一项。

## 单变量迭代

```text
目标失败：模型把取消咨询误分到退款队列
改动假设：现有定义没有区分“咨询取消”和“已扣款退款”
唯一改动：在队列语义中补充这条边界
测试集：常见工单 + 取消/退款边界集
Baseline：保存原结果
结果：记录新指标及其他标签的副作用
结论：保留 / 回滚 / 证据不足
```

每轮步骤：

1. 从失败样例提出可证伪假设。
2. 改变一个主要变量。
3. 在相同条件运行完整相关测试集。
4. 比较目标指标和副作用。
5. 改善则保留，否则回滚。

## 处理随机性

当一致性重要且输出具有随机性时，对相同样例重复运行，报告通过率或结果分布，而不是只挑最好输出。重复次数同样由风险和成本决定，不设置通用数字。

如果评分本身由模型完成：

- 使用清晰 rubric 和示例。
- 固定评审模型和版本。
- 对关键样例进行人工校准。
- 避免让评审只偏好更长或更像参考答案的文本。
- 记录评审不一致和无法判断项。

## 离线与在线评估

### 离线

适合快速迭代、回归测试和高风险发布前验证。优势是可复现，局限是测试集可能偏离真实流量。

### 在线

适合观察真实用户行为、延迟、成本和工具成功率。需要小流量、功能开关、监控、隐私保护和快速回滚。

在线指标不应替代离线语义质量检查；两者回答不同问题。

## 失败分类

评估结果应回到 [[03-choose-the-right-lever|失败分层]]：

- 指令理解错误 → Prompt。
- 材料缺失 → Retrieval。
- 字段或解析失败 → Schema。
- 计算错误 → Code。
- 工具或授权错误 → Runtime。
- 单步流程不可靠 → Workflow。
- 成本或能力不匹配 → Model / Architecture。

这防止团队把所有失败都变成 prompt patch。

## 发布门槛

不要使用脱离业务的通用准确率门槛。发布标准应写成：

- 目标指标达到当前业务要求。
- 高风险类别没有不可接受退化。
- Schema、tool 和权限路径通过。
- 延迟与成本在预算内。
- 已有回滚版本和触发条件。

详见 [[15-production-lifecycle|Prompt 的生产生命周期]]。

## 常见误区

- **只测平均分**：掩盖高风险边界失败。
- **用训练样例做全部 eval**：容易对 prompt 过拟合。
- **同时改多个变量**：无法归因。
- **开放式任务用字符串完全匹配**：评分不反映真实质量。
- **没有原始输出**：只保存汇总数字，无法诊断。
- **没有实际运行却填写数字**：把计划当成了结果。

## 检查表

- [ ] 成功标准来自任务契约。
- [ ] 测试集覆盖真实分布和关键失败。
- [ ] 输入、期望属性和评分方式可复现。
- [ ] Baseline、模型和运行参数固定。
- [ ] 每轮只有一个主要变量。
- [ ] 目标改善和副作用同时报告。
- [ ] 随机性通过重复运行或分布处理。
- [ ] 发布门槛、回滚条件与监控一致。
