# Context Window Management：容量够用不等于信息可用

> [!abstract] 本篇学习终点
> 为 SSO 排障任务分配一份完整的 token 预算，解释为什么模型声明的最大窗口不是任务的有效窗口，并能在超预算时选择过滤、压缩、检索、拆分或外部状态，而不是静默截断。

## 当所有材料都有效，新的问题出现了

经过 [[context-engineering/02-context-lifecycle|Context Lifecycle]] 验证后，系统拥有：

- 3,000 token 的稳定规则和工具定义；
- 1,000 token 的当前用户请求；
- 8,000 token 的对话历史；
- 5,000 token 的 planning state 与历史决定；
- 18,000 token 的日志、运行手册和代码证据；
- 预计 4,000 token 的下一轮 tool result；
- 预计 4,000 token 的分析和结构化输出。

假设目标模型的一次调用最多处理 32,000 token，上述分区合计已经超过容量，因此不能无差别进入同一请求。即使换成更大窗口，重复日志、旧状态和位置效应仍可能让关键 audience 差异难以被利用。

窗口管理的目标不是“刚好塞进上限”，而是：==给当前决策、后续工具观察和最终输出分配足够空间，同时让不可丢失的信息保持可见、可恢复。==

## 先把一次调用的预算算完整

可以用下面的概念式检查预算是否闭合：

$$
W \ge P + U + H + S + E + T + O + R
$$

在 SSO 任务里：

- $W$：目标模型允许的总窗口；
- $P$：稳定规则、工具定义和输出契约；
- $U$：当前用户输入；
- $H$：本轮需要的对话历史；
- $S$：当前任务与 planning state，即外部保存的目标、进度、决定和未完成项；
- $E$：日志、文档、memory 和 workspace 证据；
- $T$：后续 tool result 的预留；
- $O$：模型输出预算；
- $R$：应对估算误差、标签膨胀和截断的安全余量。

这条公式不用于计算模型质量，而用于防止漏算。系统常见错误是只统计文档正文，却忘了工具 schema、消息标签、图片表示、输出和下一次 tool loop 都会占用窗口。

本篇用于预算的 Token，是模型 tokenizer（把输入拆成 token 的组件）产生的离散单位，不是 SSO 身份凭证。相同字符数在不同语言、代码和 JSON（一种键值结构化文本格式）中可能对应不同 token 数。下面的数字只是规划用的近似值，真正发送前仍要用目标模型的计数方式复核。

有些 API 还会单独限制最大输出长度，因此 $O$ 不仅要让总式成立，还不能超过目标模型或接口的输出上限。

### 一份可执行的示例预算

仍以 32,000 token 为例，可以先给各分区设上限：

| 分区 | 预算 | 当前任务中的内容 |
|---|---:|---|
| $P$ | 3,000 | 安全规则、只读权限、工具定义、输出 schema |
| $U$ | 1,000 | 用户当前请求和最新修正 |
| $H$ | 2,000 | 与当前步骤直接相关的最近消息 |
| $S$ | 2,000 | 目标、约束、决定、completed 与 pending |
| $E$ | 12,000 | 运行手册章节、日志 span、相关代码与 diff |
| $T$ | 4,000 | 日志或测试工具可能返回的新观察 |
| $O$ | 4,000 | 诊断、补丁说明和证据引用 |
| $R$ | 4,000 | token 估算误差、序列化和继续执行余量 |

这不是通用比例。不同任务的重点不同：长文总结可能提高 $E$，结构化分类可能降低 $O$，多工具循环则需要提高 $T$。真正重要的是每个分区都有 owner、上限和超预算策略。

## 最大窗口为什么不是有效窗口

API 接受 32,000 token，只能证明请求没有因长度被拒绝。模型能否稳定使用其中的信息，还受到：

- 关键证据在输入中的位置；
- 无关和重复材料的干扰；
- 多个远距离事实的组合难度；
- 任务类型、模型版本和输出长度；
- 工具 schema、图像、音频等非正文内容；
- 证据是否有清楚标题、来源和当前动作连接。

Lost in the Middle 研究观察到，某些长上下文任务中，位于中间的相关信息更难被利用。这个结论不能简化成“模型只看开头和结尾”，也不能当成所有模型的永久规律。正确用法是：在目标模型、真实长度和真实任务上改变证据位置，测量答案和引用是否稳定。

因此：

> [!warning] 能放进去，不代表能被可靠使用
> Context Window 是容量上限；有效窗口是模型在当前任务、材料排列和输出预算下能够稳定利用的范围。

## 先判断什么绝不能丢

超预算时，系统需要按信息职责而不是按消息年龄处理。下面的 P0 / P1 / P2 是本系列用于说明优先级的工程约定，不是某家模型 API 的固定字段；实现可以换名字，但必须保留同样的“不变量、可压缩材料、当前可淘汰材料”区别。

### P0：丢失后任务会改变或越界

SSO 任务中的 P0 包括：

- 目标：修复 SSO 登录失败；
- 禁止事项：不修改生产环境；
- 成功标准：根因有证据、补丁最小、测试通过；
- 当前步骤和必要对象 ID；
- 可信授权状态；
- 关键否定信息：数据库异常已排除；
- 当前仍未确认的缺口：身份服务配置版本未知。

P0 应原样或以无歧义结构保留。若 P0 本身超过窗口，应停止、拆分任务或改变架构，而不是裁掉其中一部分。

### P1：可以压缩，但语义不应改变

- 已完成步骤的详细过程；
- 较早对话；
- 重复证据；
- 大型 tool payload；
- 多个相似代码片段。

P1 可以变成结构化摘要、精确 span 或外部 artifact reference，但必须保留来源、否定、决定和未完成事项。

### P2：对当前步骤没有足够价值

- 与 SSO 无关的文件；
- 被 v4 替代的运行手册 v1；
- 重复寒暄；
- 已失效的旧 workspace snapshot；
- 不能提供独特信息的重复示例。

P2 可以从当前请求淘汰。淘汰只表示“本轮不注入”，不等于删除原始记录。

## 超预算时按什么顺序处理

直接删除最旧消息是一个方便但危险的默认值。更稳健的顺序是：

1. **硬过滤**：移除无权、过期、任务不匹配和失败伪结果；
2. **去重**：合并相同版本和相同来源的重复内容；
3. **按需检索**：只取当前子问题需要的章节或代码；
4. **缩小 evidence span**：保留结论所需上下文和原始引用；
5. **结构化压缩**：把事件历史变成当前状态；
6. **拆分任务**：让不同阶段只携带自己的 context slice；
7. **改用外部状态**：把大 payload 和可恢复进度保存在窗口之外。

这个顺序不是固定算法，但它先移除确定无价值的内容，再处理有损压缩，能降低误删 P0 的概率。

## 压缩后必须保持什么不变

压缩不是“把字数变少”，而是保留继续任务所需的不变量。

对 SSO 任务，一份最小恢复状态至少包含：

```yaml
recovery_state:
  task_id: sso-login-fix-42
  objective: 修复 SSO 用户登录失败
  constraints:
    - 不修改生产环境
  success_criteria:
    - 根因有证据
    - 最小补丁
    - 相关测试通过
  completed:
    - reproduce_failure
    - rule_out_database
  current_step: compare_token_audience
  decisions:
    - id: decision-focus-mobile
      reason: 失败只出现在 mobile SSO
      evidence_refs:
        - log-sso-mobile-20260722
  unknowns:
    - identity_service_config_version
  authorization:
    production_write: false
  next_action:
    tool: inspect_token_fixture
```

压缩前后，以下内容不能被悄悄改变：

- 当前目标与成功标准；
- 用户明确约束和禁止事项；
- 已做决定及其证据；
- 已完成、进行中和待完成状态；
- 冲突、未知项和否定结论；
- 授权范围和副作用状态；
- 下一步所需对象 ID、版本和 artifact reference。

自由文本摘要适合人阅读；可靠恢复更适合固定字段。两者可以并存，但不能用“我们已经讨论过登录问题”代替可执行 State。

## 长材料应该怎样排列

当材料必须较长时，可以从下面的 baseline（用于后续实验比较的起始方案）开始：

1. 稳定规则、权限和来源策略；
2. 当前任务状态、目标和成功标准；
3. 带来源 ID 的主要证据；
4. 必要的 tool 与 workspace observation；
5. 当前动作和局部问题；
6. 输出契约与停止条件。

这不是所有模型的固定最优顺序。它背后的因果关系是：

- 先建立不能被数据改写的边界；
- 再告诉模型现在正在完成哪一步；
- 证据出现时已有阅读目的；
- 最终动作靠近需要执行的位置；
- 输出格式不与事实材料混在一起。

对特别长的运行手册，可以在前部给出目录和 source ID，在相关章节附近标出证据 span，并在当前动作中明确要求比较哪些字段。真正的顺序仍需用 [[context-engineering/04-context-selection|实际选出的材料]] 做位置和长度 eval。

## Prompt Cache 解决的是重复计算

Prompt Cache 或 Prefix Cache 复用相同或兼容前缀的处理结果，常用于降低重复 prefill 的延迟或成本。

它也不等于模型推理内部的 KV（Key-Value）cache。KV cache 保存当前生成序列中已经为已读 token 计算过的中间值，避免生成下一个 token 时重复计算；供应商暴露的 Prompt Cache 则可能跨请求复用稳定前缀。两者都只优化计算，不会替系统判断事实是否仍有效。

SSO Agent 可以把以下稳定内容放在前缀：

- 稳定安全规则；
- 工具定义；
- 不变的输出字段语义；
- 多轮共享且版本固定的文档。

把以下动态内容放在后部：

- 当前用户请求；
- 时间和 branch；
- planning state；
- 最新 tool result；
- 本轮证据和动作。

为了提高命中率，序列化、顺序、模型和相关配置要稳定；为了保证正确性，来源、权限和版本变化必须使旧前缀失效。

Prompt Cache 不判断两次任务“意思是否相近”。根据语义相似度复用历史检索或答案的是 Semantic Cache，见 [[context-engineering/12-retrieval-engineering|Retrieval Engineering]]。两者的 key、风险和验证方式不同。

TTL（time to live）是缓存条目允许保持有效的时间；prefill 是模型处理输入、准备生成前缀的阶段。缓存命中通常只改善重复输入的处理成本或延迟，不会证明内容仍然新鲜或答案正确。

缓存还必须绑定 tenant、权限和敏感性范围；为了命中率跨用户复用含私有数据的前缀，会把性能优化变成数据泄漏。

## 什么时候应该拆分，而不是继续压缩

如果一次请求同时要求：

- 阅读整个认证子系统；
- 分析线上日志；
- 修改代码；
- 运行多组测试；
- 编写最终报告；

把所有信息压成一个 packet 可能丢失阶段边界。可以改成：

```text
阶段 1：确认失败范围与证据
→ 保存 diagnosis artifact
阶段 2：定位相关代码与最小修改点
→ 保存 patch candidate
阶段 3：运行验证并核对成功标准
→ 保存 test evidence
阶段 4：组装最终交付
```

每个阶段只加载自己的必要材料，通过稳定 artifact 和 planning state 连接。拆分会增加接口、调用和状态成本，因此应在单次调用无法可靠满足成功标准时使用，而不是为了形式上的复杂架构。

## 评估窗口管理是否真的有效

至少同时观察：

- 输入、输出和 tool result token 分布；
- 截断率、预算超限率和安全余量使用；
- P0 约束保留率；
- 关键证据召回与引用覆盖；
- 不同位置和不同长度下的任务准确率；
- 压缩前后的决定、否定和未知项保留率；
- TTFT（time to first token，即首个输出 token 出现前的延迟）、端到端延迟与成本；
- Prompt Cache 命中率、失效正确率和质量；
- 中断后的恢复成功率。

只降低 token 但漏掉“不能改生产”，不是优化；只扩大窗口却让关键日志被噪声淹没，也不是优化。

## 用三个问题检查本篇

1. 为什么预算公式必须包含输出、tool result 和安全余量？
2. “数据库异常已排除”虽然来自较早步骤，为什么不能按“最旧消息”直接删除？
3. 什么情况下应该拆分阶段，而不是继续压缩同一个 context packet？
