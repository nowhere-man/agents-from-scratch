# 基础模型怎样成为助手模型

> [!abstract] 本章只回答一个问题
> 已经会续写文本的 Base Model，怎样经过不同训练信号，逐渐变成会理解指令、选择更合适回答并遵循交互协议的 Assistant Model？

## 前置知识

[[05-how-a-base-model-is-created|上一章]]已经说明：预训练用海量文本的下一个 Token 误差更新权重，最终得到 Base Model。后训练仍然会更新这套权重，但它要解决的问题变了。

先把“后训练”这个名字说清楚：**后训练（Post-training）不是停止训练后做一些 Prompt 配置，而是在预训练完成的 Base Model 上继续训练。** 它仍会进行前向计算、计算 Loss、反向传播和参数更新；“后”只表示它发生在大规模预训练之后。

相比预训练，后训练主要换了三样东西：

| 对比 | 预训练 | 后训练 |
|---|---|---|
| 起点 | 近似随机初始化的模型 | 已有语言和知识能力的 Base Model |
| 数据 | 大规模自然文本、代码等 Token 序列 | 指令回答、偏好比较、可验证任务、安全和工具轨迹等定向数据 |
| 优化信号 | 真实下一个 Token 的预测误差 | 理想回答的模仿 Loss、回答间偏好、验证器 Reward 等 |

两者最终修改的对象通常仍是 Transformer 的参数。不同点不在于“训练参数”变成了“训练行为”，而在于训练数据和 Loss 开始专门奖励某些行为；大量参数更新后，模型面对相同 Context 时产生的 Logits 和概率分布随之改变。

但“更新模型参数”还要再区分两个问题：

1. **训练目标是什么**：SFT、DPO、Reasoning Post-training 等决定哪种输出应该获得更低 Loss 或更高 Reward；
2. **用什么方式承载这次更新**：可以更新原模型的全部参数，也可以冻结原参数，只训练一小组附加参数。

因此，后训练前后通常不需要增加一个独立的“助手层”“安全层”或“推理模块”。变化主要体现在训练后的有效权重中：Base Model 本来就能生成许多候选，后训练让直接回答、遵循指令、展开有效推理、使用工具协议或适当拒绝等候选更容易被生成。

本章始终使用同一个请求观察模型行为怎样变化：

> 用户：请用一句话解释彩虹为什么出现。

## 1. Base Model 已经会语言，为什么还需要后训练

预训练数据里既有问答，也有小说、网页、试卷、论坛和代码。当 Base Model 看到这句请求时，它只需要生成“在类似文本后面可能出现什么”。因此可能出现多种续写：

~~~text
候选 A：彩虹是阳光在水滴中折射、反射并色散形成的。
候选 B：请用一句话解释雷电为什么出现。
候选 C：以下是关于天气现象的十道练习题……
~~~

这些续写在某些训练文本中都可能合理，但只有候选 A 符合“用户正在请求助手回答”的交互目标。

所以 Base Model 缺少的不是基础语法能力，而是稳定的行为方向：谁在发出任务、模型应该扮演什么角色、怎样直接作答、什么时候澄清或拒绝、需要工具时用什么协议表达。

后训练的作用可以概括为：==在模型已经能生成的众多可能后续中，持续提高符合人类交互目标的行为概率。==

~~~mermaid
flowchart LR
    A[Base Model<br/>会续写] --> B[SFT<br/>模仿理想回答]
    B --> C[偏好优化<br/>区分更好与更差]
    C --> D[Reasoning Post-training<br/>提高成功推理轨迹概率]
    D --> E[安全及协议训练<br/>学习边界和接口]
    E --> F[评测与发布]
    F --> G[Assistant Model]
~~~

这是一张作用关系图，不是所有模型都必须严格执行的唯一流水线。各阶段可能交错和重复，但它们提供的训练信号不同。

## 2. SFT：先让模型看懂“助手应该怎样回应”

**SFT** 是 Supervised Fine-Tuning，即监督微调。训练数据不再是任意网页，而是经过组织的“输入与理想输出”示范：

~~~text
System：你是一个回答简洁、准确的助手。
User：请用一句话解释彩虹为什么出现。
Assistant：彩虹是阳光在水滴中发生折射、反射和色散后形成的彩色光带。
~~~

模型仍然执行下一个 Token 预测，只是通常重点对 Assistant 回答部分计算 Loss。它会逐 Token 学习：在前面出现这种角色、指令和上下文时，理想回答中的 Token 应该获得更高概率。

大量示范共同教会模型：

- 区分不同消息角色；
- 把用户文本当成要完成的任务，而不是任意续写素材；
- 直接回答、解释、改写、总结或澄清；
- 遵循长度、语气和格式要求；
- 在示范覆盖的场景中拒绝或使用工具调用格式。

### 这些示范必须更新全部参数吗

现在已经知道 SFT 用什么数据、计算什么 Loss，接下来才适合回答“反向传播具体更新哪些数值”。

一种做法是 **全参数微调（Full Fine-tuning）**：保留 Base Model 作为初始化起点，反向传播后允许原模型中的大量参数一起更新。它提供较大的调整空间，但训练时还要为大量参数保存梯度和优化器状态，显存、计算和 Checkpoint 成本都较高。

如果只想让模型适应一种任务、领域或回答风格，是否必须改动全部大矩阵？**LoRA（Low-Rank Adaptation，低秩适配）**给出的答案是：先冻结原权重，只学习一个较小的调整量。

假设 Transformer 中原本有一个权重矩阵 $W$。全参数微调直接修改 $W$；LoRA 保持 $W$ 不变，把微调后的计算写成：

$$
W'=W+\Delta W
$$

其中不直接训练一个与 $W$ 同样大的 $\Delta W$，而是把它表示成两个较小矩阵的乘积：

$$
\Delta W=BA
$$

假设 $W$ 的形状是 $d_{out}\times d_{in}$，则可以令：

- $A$ 的形状为 $r\times d_{in}$；
- $B$ 的形状为 $d_{out}\times r$；
- $r$ 是远小于 $d_{in}$ 和 $d_{out}$ 的 **Rank（秩）**。

原本直接训练 $\Delta W$ 需要 $d_{out}d_{in}$ 个参数；拆成 $A$、$B$ 后只需训练：

$$
r(d_{in}+d_{out})
$$

例如，若 $W$ 是 $4096\times4096$，直接更新该矩阵涉及约 1680 万个参数；取 $r=16$ 时，$A$ 和 $B$ 合计约 13 万个参数。这里的“低秩”表示：不让调整量在所有可能方向上任意变化，而是用较少中间方向组合出这次任务需要的权重改动。

一次使用 LoRA 的 SFT 仍沿用前面的训练主线：

~~~text
输入指令与理想回答
→ 使用 W + BA 完成前向计算
→ 对理想回答计算 SFT Loss
→ 反向传播经过完整模型
→ 冻结的 W 不更新，只更新 A 和 B
→ 下一次前向计算中的有效权重发生变化
~~~

因此 LoRA 并没有省掉训练闭环，也不是一个新的行为目标。它主要减少需要训练、保存以及维护优化器状态的参数；前向计算仍要使用 Base Model，反向传播所需的激活值也不会全部消失。

训练完成后，较小的 LoRA 参数可以单独保存并在使用时挂载到同一个 Base Model，也可以把 $BA$ 合并进原权重，得到用于推理的 $W'$。这使同一个 Base Model 可以配合不同 LoRA 适配不同任务，而不必为每个任务都保存一份完整模型。

> [!important] LoRA 与 SFT 不在同一层
> SFT 回答“用理想示范奖励什么行为”；LoRA 回答“为了学到这种行为，哪些参数参与更新”。同一次 SFT 可以采用全参数微调，也可以采用 LoRA。

同理，LoRA 也可用于 DPO、安全训练或其他后训练 Loss。它不会自动带来指令遵循、偏好对齐或推理能力，最终学到什么仍由训练数据、Loss、可训练模块和容量共同决定。对于需要深度改变模型能力的大规模后训练，全参数训练通常拥有更大的调整空间；LoRA 是否足够，要用目标任务评测，而不能只凭参数更少下结论。

SFT 之后，候选 A 会更容易出现。但 SFT 的信号本质上是“模仿这个示范”，它仍有两个限制。

第一，同一个请求可能有许多措辞不同但都正确的回答，不可能为每种输入写出唯一标准文本。第二，示范只明确告诉模型“这个回答可取”，没有直接比较其他回答差在哪里。

这就引出了下一类训练信号。

## 3. 偏好数据：不要求唯一答案，而是比较哪个更好

对同一个彩虹问题，可以让模型生成两个回答：

~~~text
回答 A：彩虹是阳光在水滴中折射、反射并色散形成的。

回答 B：彩虹是一种非常美丽而神奇的自然现象，它有很多颜色，
       通常在雨后出现，给人们带来希望和快乐。
~~~

两者都通顺，但用户要求“一句话解释为什么”。回答 A 更直接地给出原因；回答 B 较空泛，没有解释关键机制。标注者、规则或评估器可以记录：在这个输入下，A 优于 B。

这类数据通常写成：

$$
(x,y^+,y^-)
$$

- $x$ 是同一个请求和上下文；
- $y^+$ 是更偏好的回答；
- $y^-$ 是较差的回答。

偏好数据把“更清楚、更相关、更真实、更安全或更符合格式”等相对判断变成训练信号。它不要求所有好回答逐字相同。

## 4. 偏好信号怎样更新模型

偏好数据可以通过不同方法作用于模型。初学者首先要看懂它们共同改变了什么，而不是先背算法缩写。

### Reward Model 与 RLHF

一种经典流程是先训练 **Reward Model**。它读取请求和回答，输出一个分数，学习让 $y^+$ 的分数高于 $y^-$。然后使用强化学习继续更新 Assistant Model，使高奖励回答更容易生成，同时限制模型不要偏离原有能力过远。

这类方法常被称为 **RLHF**，即基于人类反馈的强化学习（Reinforcement Learning from Human Feedback）。完整因果链是：

~~~text
人类比较回答
→ Reward Model 学习近似这种偏好
→ Assistant Model 生成候选并获得评分
→ 强化学习提高高分行为的概率
~~~

Reward Model 不是事实验证器。它只是在训练数据覆盖范围内近似“什么看起来更符合偏好”。如果评分标准偏爱冗长、自信或特定格式，模型也可能学会迎合这些表面特征。

### DPO 等直接偏好优化

RLHF 先把人类偏好训练成 Reward Model，再让 Assistant Model 通过强化学习追求更高奖励。DPO（Direct Preference Optimization，直接偏好优化）则问：既然训练数据已经明确告诉我们“同一个输入下，$y^+$ 优于 $y^-$”，能否直接用这组比较更新 Assistant Model，而不再单独训练 Reward Model？

答案是可以。DPO 仍然使用上一节的三元组：

$$
(x,y^+,y^-)
$$

先理解“模型给一整段回答多大概率”。自回归模型生成回答时，每个 Token 都有一个条件概率，因此整段回答的概率是各 Token 条件概率的乘积：

$$
\pi_\theta(y\mid x)
=\prod_{i=1}^{T}p_\theta(y_i\mid x,y_{<i})
$$

- $x$ 是彩虹问题；
- $y_i$ 是回答中的第 $i$ 个 Token；
- $y_{<i}$ 是此前已经生成的回答 Token；
- $\pi_\theta(y\mid x)$ 表示当前 Assistant Model 在看到 $x$ 后生成整段回答 $y$ 的倾向。

这个概率通常极小，因为许多小于 1 的数连乘会越来越小，所以实际计算使用对数概率。对数会把连乘变成求和，但含义不变：模型在逐 Token 生成时，整体上有多倾向于走出这段回答。

回到彩虹例子，DPO 比较的是：

~~~text
同一个问题 x
├─ 好回答 y+：直接解释折射、反射和色散
└─ 差回答 y-：语言流畅，但没有解释原因
~~~

如果当前模型对 $y^+$ 和 $y^-$ 的倾向差不多，说明它还没有充分学会这项偏好。DPO 的训练目标会推动参数发生两方面变化：

1. 让当前模型相对更倾向于生成 $y^+$；
2. 让当前模型相对不那么倾向于生成 $y^-$。

这里强调的是 **相对差距**，不是要求模型以后逐字背出 $y^+$，也不是把 $y^-$ 的概率强制变成零。经过大量不同请求和回答对后，模型会更常生成与 preferred answers 共有的行为模式，例如更直接、更相关或更符合安全要求。

### 为什么还要有一个 Reference Model

如果只要求不断拉高 $y^+$、压低 $y^-$，模型可能为了适应有限的偏好数据而变化过猛，损伤原本通过 SFT 获得的语言和指令能力。因此 DPO 通常保留一份训练开始前冻结的模型，称为 **Reference Model（参考模型）**。

它与正在更新的模型分工不同：

- **当前模型 $\pi_\theta$**：训练过程中持续更新；
- **参考模型 $\pi_{ref}$**：参数冻结，用来表示后训练开始前的行为基线。

DPO 关注的不是“当前模型给好回答的概率是否绝对很大”，而是当前模型相对于参考模型，对好回答和差回答的倾向分别改变了多少。可以用下面的差值理解：

$$
s(x,y)=\log\frac{\pi_\theta(y\mid x)}{\pi_{ref}(y\mid x)}
$$

- $s(x,y)>0$：当前模型比参考模型更倾向于回答 $y$；
- $s(x,y)<0$：当前模型比参考模型更不倾向于回答 $y$；
- 比较 $s(x,y^+)$ 与 $s(x,y^-)$，就能判断训练是否把行为更多地推向了偏好回答。

DPO 的核心目标可以写成：

$$
\mathcal{L}_{DPO}
=-\log\sigma\left(\beta\left[s(x,y^+)-s(x,y^-)\right]\right)
$$

不需要计算这个公式，只要按顺序读出它的意义：

1. 分别计算当前模型相对参考模型，对 $y^+$ 和 $y^-$ 的倾向变化；
2. 用两者之差检查是否更偏向 $y^+$；
3. 如果差距方向不对或不够大，Loss 就较大；
4. 反向传播根据这个 Loss 更新当前模型，使下一次更偏向 $y^+$；
5. $\sigma$ 把比较结果压到 0 到 1，可理解为模型对“$y^+$ 应胜过 $y^-$”这一偏好的拟合程度；
6. $\beta$ 控制偏好推动与保留参考模型原有行为之间的尺度，具体效果还取决于实现和数据。

所以一次 DPO 更新的完整链路是：

~~~text
输入同一个问题以及好、差两段回答
→ 当前模型计算两段回答的逐 Token 对数概率
→ 参考模型也计算两段回答的对数概率，但不更新
→ 比较当前模型相对基线是否更偏向好回答
→ 得到 DPO Loss
→ 反向传播只更新当前模型参数
~~~

### DPO 省掉了什么，又没有省掉什么

DPO 省掉了显式训练 Reward Model 和运行在线强化学习的那段管线。它把成对偏好直接转成 Assistant Model 的训练 Loss，因此工程流程通常更直接、稳定。

但它没有省掉偏好数据本身，也没有自动判断哪个回答真的更好。若 chosen / rejected 标注带有偏差，模型仍会学习这种偏差；若样本只偏爱冗长、自信或固定措辞，模型可能学到表面捷径。它还主要从给定的回答对中学习，训练效果受候选质量和覆盖范围限制。

> [!important] DPO 到底做了什么
> DPO 不给模型增加新的“偏好模块”。它把“同一输入下，回答 A 比回答 B 好”转换成一个可反向传播的 Loss，直接调整原有 Transformer 参数，使未来生成更容易走向与 A 相似的行为模式。

RLHF 与 DPO 的工程过程不同，但对本章主线而言，结果都是：在同一个请求下，把概率质量从较差行为移向较好行为，同时尽量保留模型原有能力。

## 5. Reasoning Post-training：强化能够得到正确结果的推理行为

SFT 和偏好优化首先解决“像不像一个合适的助手”。现代模型还常进行专门的 **Reasoning Post-training（推理后训练）**，提高模型在数学、代码、逻辑等结果可检查的复杂任务上，通过多步计算得到正确结果的概率；规划任务也可以参与，但只有具备可靠的任务结果或环境反馈时，才能提供同样明确的可验证奖励。

> [!note] 它不是新的网络模块
> Reasoning Training 通常仍然更新原有 Transformer 权重。变化的是训练任务、反馈信号和生成过程，不是给模型外接一个固定的“推理器”。不同模型的实际训练配方并不完全相同。

### 为什么预训练和普通 SFT 还不够

Base Model 在预训练中读过教材、证明、程序和解题过程，因此已经具有一定推理能力；Reasoning SFT 也可以让它模仿高质量步骤。但只模仿示范仍有局限：

- 一道题可能有多条有效解题路径，不存在唯一标准文字；
- 示范中的每个 Token 都被同样模仿，不代表这条路径一定稳健；
- 模型可能学会“写得像推理”，却在关键计算处得出错误结果；
- 对困难问题，训练数据未必能预先提供覆盖所有路径的理想答案。

因此推理后训练常让模型自己生成多条候选轨迹，再根据结果反馈强化成功轨迹。

### 什么是推理轨迹

假设任务是：

> 一个商品原价 100 元，先涨价 20%，再降价 20%，最终价格是多少？

模型可能生成不同的完整输出：

~~~text
轨迹 A：100 × 1.2 = 120，120 × 0.8 = 96，所以答案是 96 元。
轨迹 B：上涨和下降都是 20%，二者抵消，所以答案是 100 元。
轨迹 C：100 + 20 - 24 = 96，所以答案是 96 元。
~~~

从开始分析到最终答案的一整段生成序列，可以称为一条 **推理轨迹（reasoning trajectory）**。这里的“轨迹”是模型生成出来、可用于训练和验证的 Token 序列，不是把神经网络内部所有 Hidden State 翻译成文字。

轨迹 A 和 C 的表达不同，但都得到正确结果；轨迹 B 看似流畅，却犯了百分比基数变化的错误。普通单一示范只能要求模型模仿某一种写法，而结果验证可以同时承认多条有效路径。

### 可验证奖励怎样提供训练信号

数学答案、代码测试、逻辑题和某些工具任务具有可自动检查的结果：

- 数学题可以检查最终数值；
- 代码可以编译并运行测试；
- 形式化问题可以检查约束是否满足；
- 某些工具任务可以检查外部状态是否真正达到目标。

负责检查结果的程序称为 **Verifier（验证器）**。验证器对候选轨迹给出 Reward，例如正确为 1、错误为 0，或提供更细的分数。这类由可检查结果产生的反馈常称为 **可验证奖励**，对应的强化学习常被称为 **RLVR（Reinforcement Learning with Verifiable Rewards，基于可验证奖励的强化学习）**。

一次典型流程是：

~~~text
给模型一道题
→ 模型采样多条推理轨迹和最终答案
→ Verifier 检查每条轨迹的结果
→ 正确轨迹获得较高 Reward，错误轨迹获得较低 Reward
→ 强化学习根据 Reward 计算训练 Loss
→ 反向传播更新模型参数
→ 以后遇到类似问题时，成功行为更容易被生成
~~~

需要注意，Reward 不会直接告诉模型“第二步的乘法应该怎么改”。它首先只评价这次完整生成是否成功。强化学习算法再根据高、低 Reward 调整生成这条 Token 轨迹的概率。

### 为什么同一道题要生成多条候选

对于同一个问题，模型可以采样一组不同轨迹。组内有成功也有失败时，比较信号尤其清楚：哪些生成行为比同组其他尝试更有可能得到正确结果。

某些方法会根据同组 Reward 计算相对优势。例如，若 8 条轨迹中 3 条通过验证，那么通过的轨迹相对组内平均表现更好，训练会提高它们的概率；失败轨迹则被相对压低。GRPO 等算法属于实现这种强化学习更新的具体方法，但算法名称不是本章重点。

这里与 DPO 的区别是：

| 对比 | DPO | 推理强化训练 / RLVR |
|---|---|---|
| 训练比较从哪里来 | 数据已给出 $y^+$ 和 $y^-$ | 模型现场生成候选，由 Verifier 打分 |
| 主要信号 | 哪个回答更受偏好 | 哪条轨迹得到可验证的正确结果 |
| 是否常需探索新轨迹 | 通常使用固定回答对 | 通常需要采样多条候选进行探索 |
| 适合的问题 | 帮助性、风格、安全等相对偏好 | 数学、代码等结果可检查的复杂任务 |

两者都通过 Loss、反向传播和参数更新改变模型的输出分布，只是“好坏信号”从不同地方获得。

### 推理后训练究竟让什么发生了变化

假设后训练前，模型面对复杂数学题时：

~~~text
直接猜答案：概率较高
展开两步但中途放弃：概率较高
正确分解、计算并检查：概率较低
~~~

经过大量可验证任务的更新后，原有权重发生变化。同样的题目进入模型时，每一步产生的 Logits 也会变化，于是更可能生成：

- 把复杂问题分成中间步骤；
- 使用更多 Token 继续计算，而不是过早结束；
- 尝试能被验证的解题策略；
- 在发现冲突时修正或重新尝试；
- 最终到达可验证的正确答案。

所以所谓“推理能力被强化”，不是模型学会了一套由工程师硬编码的固定解题流程，而是==能产生成功推理轨迹的 Token 选择在相关 Context 下获得了更高概率==。


## 6. 只看最终结果，还是也看中间过程

如果只判断最终答案是否正确，叫作 **结果监督**。它容易获得，但无法指出中间哪一步开始偏离。

如果对解题步骤、工具选择或关键决策也提供反馈，叫作 **过程监督**。它能给出更细的训练信号，但需要定义什么过程才算好，标注成本也更高。

模型写出的自然语言步骤是一段可供检查的输出，不是对神经网络内部全部隐藏计算的逐字读取。过程监督改变的是可观察的推理行为和轨迹概率。

## 7. 安全训练把风险处理也变成要学习的行为

Assistant Model 不应对所有指令机械服从，而要根据安全训练学会：

- 识别不同风险类型；
- 对允许的请求正常帮助；
- 对不允许的部分拒绝；
- 在合适时提供安全替代方案；
- 对证据不足或高风险情况表达不确定并要求确认。

这些行为同样可通过 SFT 示范、偏好比较、规则反馈和对抗样本训练。它们会提高合适处理方式的概率，但仍是概率性行为。

> [!warning] 安全训练不是权限系统
> 模型可能遇到训练未覆盖的攻击、冲突指令或含糊边界。真正的身份验证、数据隔离、访问控制和高风险动作授权，必须由模型外部的确定性系统执行。

## 8. Tool Calling 与 Structured Output 是协议能力

如果用户问“北京现在会下雨吗”，模型参数中的旧知识不足以提供实时天气。后训练可以教模型在这种情境下生成约定格式：

~~~json
{
  "name": "get_weather",
  "arguments": {"city": "北京"}
}
~~~

训练示范让模型学习三件事：什么时候可能需要工具、该选择哪个工具、参数应该以什么结构生成。工具真正执行、返回实时结果，再由外部程序交回模型。

同样，Structured Output 训练或受约束解码能让输出更稳定地符合 JSON Schema。它解决的是输出协议和可解析性，不会自动验证字段事实、业务规则和用户权限。

因此这里发生的变化仍然是：模型更会生成某种协议中的正确候选；它没有因为见过工具格式就获得网络连接和执行权。

## 9. 把各阶段重新串起来

回到最初的彩虹请求，可以按行为变化串起全章：

| 阶段 | 主要修正的问题 | 不能单独保证什么 |
|---|---|---|
| Base Model | 已学会语言和知识模式 | 不保证把文本当作用户指令 |
| SFT | 学习角色、任务和理想回答格式 | 不覆盖所有输入，也不比较所有候选 |
| 偏好优化 | 更常选择相关、清楚、安全的候选 | 偏好标准可能有偏差，不等于事实证明 |
| Reasoning Post-training | 提高产生成功推理轨迹和正确结果的概率 | 只覆盖训练任务与 Verifier 检查到的目标 |
| 安全训练 | 学习风险识别、拒绝和替代行为 | 不替代外部权限与隔离 |
| 协议训练 | 学习 Tool Call 和结构化输出 | 不负责真实执行和业务正确性 |

这张表用于回顾已经走过的变化。真正的主线始终是：每一类新训练信号都在修正上一阶段仍然无法稳定区分的行为。

## 10. 什么时候才算得到可发布的 Assistant Model

训练结束并不自动等于可以部署。还要在未参与训练的任务上评测：

- 基础语言、知识、代码和推理能力是否退化；
- 是否正确理解指令和消息角色；
- 输出格式与工具选择是否可靠；
- 遇到未知事实时是否编造；
- 正常请求是否被误拒，危险请求是否漏拒；
- 多语言、长 Context 和输入改写后是否稳定；
- 延迟和成本是否满足使用要求。

最终的 Assistant Model 仍是自回归生成模型。后训练重塑了它的输出分布，使直接回答、澄清、拒绝、按格式输出和提出工具调用更常出现，却没有把概率行为变成硬保证。

从参数层看，Base Model 与后训练模型的核心区别可以准确表述为：架构和 Token 生成机制通常没有根本改变，但后训练后的权重已经不同。同一请求经过这些新权重后，会产生不同的 Hidden State、Logits 和 Token 概率，因此助手行为和推理行为的分布发生变化。

| 同一个输入下的表现 | Base Model 更可能 | 后训练模型更可能 |
|---|---|---|
| 用户提出问题 | 延续任意文本模式 | 识别任务并直接作答 |
| 多个通顺回答 | 不稳定地选择其一 | 偏向更有帮助、更符合偏好的回答 |
| 复杂可验证问题 | 猜测、短答或生成不稳定步骤 | 展开并延续更可能成功的推理轨迹 |
| 实时事实需求 | 根据参数知识继续生成 | 按训练协议提出 Tool Call |
| 风险请求 | 行为取决于普通文本模式 | 更可能遵循训练过的安全边界 |

这些都是概率变化，不是确定性开关。后训练也可能造成能力退化、过度拒绝、迎合偏好或在未覆盖任务上泛化失败，所以发布前必须分别评测基础能力、推理、工具和安全行为。

下一章会固定这套训练完成的权重，跟踪它在收到一次真实请求后，怎样从输入 Context 开始逐 Token 生成回答。
