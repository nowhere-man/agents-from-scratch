# 模型能力、边界与 Agent

> [!abstract] 本章只回答一个问题
> 单次模型调用能生成有用但不确定的候选；当任务还需要实时事实、真实动作和长期状态时，怎样把模型放进一个可控制、可验证的 Agent 系统？

## 前置知识

前面已经建立三件事：模型根据权重和本次 Context 逐 Token 生成；后训练提高符合人类期望的行为概率；API 可以让模型生成 Tool Call，但真正执行发生在外部。

本章不再列一张“模型会什么”的固定清单，而是跟踪一个任务逐步增加系统能力：

> 用户：如果北京明天下雨，把我上午的户外跑步改到周六，并通知同行人。

这个请求同时包含语言理解、实时天气、日历状态、修改操作和发送通知。它能清楚暴露模型负责什么，以及为什么单次回答不够。

## 1. 模型首先能做的是理解并提出候选

只看用户句子，Assistant Model 通常能识别出：

- 条件是“北京明天下雨”；
- 待处理事件是“上午的户外跑步”；
- 目标时间是“周六”；
- 后续动作是“通知同行人”。

这种能力来自多个阶段共同作用：预训练学习语言、世界模式和任务格式；Transformer 在当前 Context 中组合远近信息；后训练塑造指令遵循和工具协议；推理时配置影响模型如何生成候选。

模型可以先提出计划：

~~~text
1. 查询北京明天的天气。
2. 若下雨，查找上午的户外跑步日程。
3. 检查周六是否冲突。
4. 修改日程。
5. 通知同行人。
~~~

这份计划很有用，因为任务需要理解自然语言和动态选择步骤。但它仍然只是一段模型输出：它不能证明明天会下雨、日程存在、周六无冲突，也不能证明消息已经发出。

> [!important] 本章最关键的边界
> 模型输出首先是一个候选判断、候选计划或候选 Tool Call。它可以很合理，但事实、权限、执行成功和最终状态必须由对应的外部证据证明。

## 2. 为什么模型不能独自回答这个任务

### 参数知识不是实时数据库

训练权重可能包含“北京有雨季”等一般模式，却没有可靠的明日天气记录。权重中的知识没有稳定记录 ID、来源时间和精确更新接口，因此需要天气 API 提供实时证据。

### Context 不是外部世界

即使 Context Window 很长，模型也只能使用被放进来的内容。日历事件、参与人和当前时间如果没有经工具查询进入 Context，模型无法凭长窗口看到它们。

### 生成 Tool Call 不是完成动作

模型可以生成：

~~~json
{
  "name": "move_calendar_event",
  "arguments": {
    "event": "上午的户外跑步",
    "new_date": "周六"
  }
}
~~~

这仍是一份候选请求。参数可能指向错误日程，“周六”可能存在时区歧义，用户可能没有修改权限，调用也可能因网络失败而没有执行。

因此任务必须把模型与可信数据、工具和控制程序组合起来。

## 3. 从单次模型调用到 Agent

**Agent** 不是一种新的神奇模型，而是一个让模型能够反复“观察当前状态、提出下一步、经验证后执行、读取真实结果”的系统。

~~~mermaid
flowchart LR
    A[目标与真实状态] --> B[构造当前 Context]
    B --> C[模型提出下一步]
    C --> D[程序校验权限和参数]
    D --> E[工具执行]
    E --> F[返回真实结果并更新状态]
    F --> G{任务完成或达到限制？}
    G -->|否| B
    G -->|是| H[返回可验证结果]
~~~

在跑步任务中，第一轮模型可能选择 get_weather。外部程序执行后返回：

~~~json
{
  "city": "北京",
  "date": "2026-07-21",
  "condition": "rain",
  "source": "weather-service",
  "observed_at": "2026-07-20T10:00:00+08:00"
}
~~~

这条结果进入下一轮 Context 后，模型才有证据判断条件成立，并提出查询日历的下一步。这个“模型输出候选、外部世界反馈真实观察、再继续判断”的循环就是 Agent Loop 的核心。

## 4. 每一轮到底有哪些不同对象

Agent 容易混乱，是因为自然语言对话看起来把一切混在一起。实际上至少要区分六个对象：

| 对象 | 在跑步任务中是什么 | 负责什么 |
|---|---|---|
| Parameters | Assistant Model 的权重 | 提供语言、推理和工具协议能力 |
| Prompt / Instructions | 本轮目标、规则和输出要求 | 告诉模型当前要做什么 |
| Context | 当前可见的天气、日历结果和必要历史 | 为这一轮决策提供条件 |
| Memory | 应用保存并按需检索的用户偏好或历史 | 让未来调用重新获得相关信息 |
| State | 任务是否已查天气、待确认、已修改等真实进度 | 作为恢复和判断完成的事实来源 |
| Tool | 天气、日历、通知接口 | 查询或改变外部世界 |

其中 **State** 最容易被误当成聊天文字。可靠系统不应只保存“我已经修改日程”这句话，而应保存机器可检查的事实：

~~~json
{
  "task_id": "task-123",
  "status": "awaiting_confirmation",
  "weather_result_id": "weather-456",
  "event_id": "event-789",
  "proposed_new_start": "2026-07-25T09:00:00+08:00"
}
~~~

模型可以帮助总结 State，但外部存储才是任务进度的真实来源。下一轮需要哪些 State 和 Memory，由应用筛选后重新放入 Context。

## 5. 工具给模型补上三类缺失能力

沿当前任务看，工具的作用可以分成三类。

### 提供模型权重之外的事实

天气 API 和日历查询提供最新、私有且可标识来源的数据。模型负责理解结果与用户条件的关系，数据源负责证明事实。

### 提供精确计算和规则判断

时间换算、冲突检测、参与人去重可以交给确定性代码。模型适合解释“周六上午”的语义，程序适合计算准确时间范围和检查重叠。

### 改变外部世界

日历写入和发送通知具有副作用。模型只能提出调用；外部服务执行后返回事件 ID、状态码和时间戳，才能证明动作发生。

一个工具应有清楚名称、单一职责、明确类型和机器可判定的返回值。例如查询日历与修改日历应分开，避免模型为了读取信息被迫获得写权限。

## 6. Tool Call 到真实执行之间为什么必须有门控

假设模型找到了正确事件，并提出改到周六。程序不能立刻照做，至少还要检查：

1. event_id 是否来自刚才的可信查询，而不是模型编造；
2. “周六”已按用户时区解析成具体时间；
3. 用户是否拥有该事件的修改权限；
4. 周六是否存在冲突；
5. 修改和通知是否需要用户明确确认；
6. 写入是否携带幂等键，避免重试造成重复事件或通知。

这几步分别对应语法、语义、权限、风险和一致性验证。JSON Schema 只能完成其中最外层的字段形状检查。

高影响动作的可靠流程是：

~~~text
模型提出候选
→ 程序生成具体变更预览
→ 校验资源、权限、冲突和策略
→ 必要时获得绑定具体参数的确认
→ 工具执行
→ 回读真实结果
→ 更新 State 和审计记录
~~~

模型说“已经改好了”不能代替工具返回的 event_id 和真实日历回读。

## 7. 为什么模型会给出流畅但错误的候选

### 生成目标不包含自动事实验证

模型每一步都在当前条件下选择高概率后续 Token。训练提高了相关和真实回答的概率，却没有内置一个“这句话已经被现实证明”的变量。缺少天气证据时，它仍可能生成符合常见天气叙述的答案，这就是许多幻觉的根源。

### Context 中有信息，不等于一定正确使用

模型可能因材料过长、位置不显著、信息冲突或需要组合多条记录而漏掉关键日程。把整个日历和所有聊天历史塞进 Context，只说明信息可见，不保证它被可靠定位。

### 多步任务会累积错误

如果第一步把日期解析错，后面的冲突检测、修改和通知都可能围绕错误日期继续生成得很流畅。更长的解释提供了更多计算空间，也增加了更多可能出错的位置。

### 同一个模型的自检不等于独立证明

让模型“再检查一次”可能发现明显错误，但两次判断共享相同权重、Context 和盲点。关键事实应由天气源、日历回读、代码约束或人工审核独立验证。

所以模型的自然语言自信不能直接用作执行阈值。可靠性来自证据覆盖、工具结果、验证器和实测成功率。

## 8. Agent Runtime 必须掌握循环控制权

模型可以建议下一步和判断任务是否可能完成，但不能成为唯一的循环控制器。外部 **Agent Runtime** 至少要控制：

- 最大步骤、Token、费用和总时间；
- 每个工具的超时、重试和熔断；
- 重复调用与循环检测；
- 允许使用的工具和每个工具的权限；
- 中途取消、失败和人工接管；
- Checkpoint、State 持久化和恢复；
- 什么外部证据才算任务完成。

例如，模型连续三次查询同一天气并不会自动带来新证据。Runtime 应识别重复观察并停止或改变策略。模型提出“任务完成”后，Runtime 仍需检查日历变更和通知是否都有成功回执。

系统还需要明确失败状态，而不是逼模型每次给出肯定答案：

| 状态 | 含义 | 合适后续 |
|---|---|---|
| insufficient_evidence | 现有证据不足以判断 | 补充查询或交给人工 |
| not_found | 在查询范围内未找到日程 | 调整条件或询问用户 |
| conflicting_evidence | 数据源之间冲突 | 保留冲突并升级处理 |
| permission_denied | 用户无权执行 | 停止，不能让模型绕过 |
| requires_confirmation | 具体副作用等待确认 | 持久化并暂停 |
| tool_failure | 外部依赖失败 | 按可重试策略处理 |
| success | 外部结果证明目标已完成 | 保存结果并结束 |

允许正式失败，是防止模型在证据不足时编造“完成”的重要设计。

## 9. 并不是所有任务都需要 Agent

回到跑步任务，它有条件分支、非结构化表达和多个外部反馈，受控 Agent Loop 有价值。但如果业务步骤完全固定：

~~~text
校验表单 → 查询订单 → 按规则计算 → 写数据库 → 返回结果
~~~

普通工作流通常更可靠、便宜和容易测试。模型可以只在“从用户文本抽取结构化意图”这个节点参与，其他步骤由固定代码执行。

可以按复杂度逐级增加系统开放性：

1. 单次模型调用：输入明确，结果容易检查；
2. 模型加一个工具：只缺某类外部事实或计算；
3. 固定工作流：步骤已知，个别节点需要语义判断；
4. 受控 Agent Loop：路径无法预先确定，但每步都有反馈和边界。

不是循环越多、工具越多就越“智能”。每增加一层，都会增加延迟、状态、错误累积和调试成本。

## 10. 风险决定模型能自主到哪一步

“修改日历”和“通知同行人”都产生外部影响。自主程度应由动作风险决定，而不是由模型看起来多聪明决定：

| 风险 | 例子 | 合适策略 |
|---|---|---|
| 低风险、可撤销 | 生成日程修改草稿 | 可自动完成并记录 |
| 中风险、有副作用 | 修改共享日历 | 规则校验，必要时确认 |
| 高风险、不可逆 | 付款、删除、发布、权限变更 | 强权限、独立验证和人工批准 |

确认应绑定具体事件、时间和接收人，不能把用户先前一句泛化的“你帮我处理”当作未来所有动作的授权。

## 11. Agent 应该怎样评测

只看最终回复“已经为你改好”远远不够。要同时检查结果和完整轨迹：

- 是否在需要实时天气时调用了正确工具；
- 日期、地点、event_id 和接收人参数是否正确；
- 是否使用了真实工具结果，而不是自行补全；
- 是否出现重复查询、无限循环或无效步骤；
- 修改前是否满足权限、冲突和确认规则；
- 工具失败后 State 是否保持一致且可恢复；
- 最终日历和通知系统是否真正达到目标；
- 延迟、Token、调用次数和费用是否可接受。

评测要覆盖正常案例、边界输入、工具故障、权限拒绝、恶意外部文本和恢复流程。模型、Prompt、工具 Schema、Runtime 或数据源任一变化，都可能改变端到端表现。

## 12. 用完整任务收束分工

现在可以把最初请求完整执行一遍：

~~~text
用户目标
→ 模型理解条件和提出查天气
→ 天气工具返回带来源的真实结果
→ 模型判断条件成立并提出查日历
→ 日历工具返回 event_id 和冲突信息
→ 模型提出具体修改及通知计划
→ 程序校验权限、时间、参与人和风险
→ 用户确认具体变更
→ 工具执行并返回成功回执
→ Runtime 更新 State 并验证最终日历
→ 模型依据真实结果向用户总结
~~~

其中模型负责语言理解、在不确定路径中提出候选和结合观察选择下一步；确定性系统负责真实事实、权限、执行、状态、一致性、预算和最终验证。

这个边界不是限制模型价值，而是让模型最擅长的语义判断与外部系统最擅长的确定性保证各自承担正确职责。
