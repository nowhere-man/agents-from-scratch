# OpenAI API 参数究竟改变什么

> [!abstract] 本章只回答一个问题
> 调整一个 API 参数时，它究竟改变了请求生命周期中的哪一步，为什么会影响结果，又有哪些问题不是它能解决的？

## 前置知识

[[20-openai-api-request-anatomy|上一章]]已经把一次请求拆成应用、API 服务、模型 Context、模型推理和 Response。现在继续使用同一个调用，但把注意力放在参数的作用位置：

~~~python
response = client.responses.create(
    model="<model-id>",
    instructions="回答要准确、简洁。",
    input="请用一句话解释彩虹为什么出现。",
    max_output_tokens=100,
)
~~~

接口字段会随 API 和模型演进。本文使用通用概念和常见字段名解释机制；实际支持范围、取值和默认行为应查阅当前模型的官方 Reference。

## 1. 先纠正一个容易混淆的说法

API 调用时填写的配置常被口头称为“模型参数”，但它们与训练得到的数十亿个参数不是同一回事：

- **模型参数 / 权重**：预训练和后训练更新，普通 API 调用期间固定；
- **API 参数**：本次请求提交的输入和运行配置，不会把新知识写入权重。

同一个 API 参数表里，字段作用的层次也不同：

~~~mermaid
flowchart LR
    A[构造 Context] --> B[选择模型与推理投入]
    B --> C[从 Logits 选择 Token]
    C --> D[控制输出预算和停止]
    D --> E[约束工具与输出协议]
    E --> F[传输、保存和观测]
~~~

例如，input 改变模型看到了什么，Temperature 改变怎样选择 Token，stream 只改变生成结果怎样传输。把它们统称为“调模型随机性”会掩盖真正原因。

下面沿这条生命周期逐层判断。

## 2. 第一层：输入字段先决定模型有机会依据什么回答

假设模型把彩虹解释错了。在调整采样前，首先应检查 input、instructions、历史消息、工具定义和提供的材料，因为它们共同构造本次 Context。

### input 与 instructions 改变任务条件

下面两次调用不是“同一个问题使用不同语气”，而是给模型提供了不同条件：

~~~text
请求一：解释彩虹为什么出现。

请求二：只依据下面的教材段落，用一句话解释彩虹为什么出现；
       不足以回答时返回 insufficient_evidence。
~~~

第二个请求增加了证据范围、输出长度和失败方式。它不会更新权重，但会改变本次条件概率。

如果必要事实根本不在权重、输入或工具结果中，降低 Temperature 也只能让模型更稳定地选择自己当前最偏好的答案，不能创造证据。

### 历史和工具定义也占用 Context

多轮历史能补充指代和任务状态，但无关历史会增加噪声。工具描述能开放外部查询路径，但工具过多、名称相似或描述含糊，会让选择更困难。

所以“输入更多”不是单调变好。输入字段改变的是模型可见的信息和任务解释空间，质量取决于相关性、边界、冲突和长度。

## 3. 第二层：model 和推理投入改变由谁算、投入多少计算

### model 改变整套能力分布

换 model 可能改变权重、架构、训练方法、Context 范围、工具能力、速度和价格。它的影响远大于普通采样参数，因此不能假设同一 Prompt 在不同模型上只会出现风格差异。

模型选择应依据真实任务评测，而不是只看参数量、名称或单个排行榜。

### reasoning effort 一类配置改变运行时计算预算

某些推理模型允许用 reasoning effort 一类配置指定较低或较高的推理投入。它不是临时提高模型参数量，也不是让每个 Transformer Block 多运行一次，而是影响模型在提交最终答案前，可以把多少生成预算用于内部推理过程。

先看普通回答与推理模型回答的概念差别。普通自回归模型可以直接从输入开始生成用户可见文本：


```text
输入 Context
→ 生成最终回答 Token
```

推理模型则可能先生成一段服务管理的 **Reasoning Token（推理 Token）**，再以这段中间过程为条件生成最终回答：

~~~text
输入 Context
→ 生成内部推理 Token
→ 推理 Token 成为后续计算的中间条件
→ 生成用户可见的最终回答 Token
~~~

Reasoning Token 仍由模型逐 Token 产生。它不是 Transformer 层内的 Hidden State，也不是模型在一次前向计算中突然得到的完整答案。两者的区别是：

| 对象              | 位于哪里                    | 主要作用                   |
| --------------- | ----------------------- | ---------------------- |
| Hidden State    | 每个 Transformer 层的数值计算内部 | 表示当前 Token 在该层的上下文状态   |
| Reasoning Token | 多轮自回归生成的中间序列            | 为后续 Token 提供可继续计算的中间条件 |
| 最终回答 Token      | 返回给用户的输出序列              | 表达最终结论和解释              |

服务通常不会直接返回原始 Reasoning Token；某些接口可能提供单独的推理摘要。摘要是模型或服务生成的可见概括，不等于原始内部推理序列。具体可见性、保留方式和计费规则要以当前接口为准。

#### 较高 effort 到底给模型增加了什么机会

以这个问题为例：

> 一个商品原价 100 元，先涨价 20%，再降价 20%，最终价格是多少？

较低推理投入时，模型可能很快选择一条短路径：

~~~text
20% 上涨和 20% 下降相互抵消
→ 回答 100 元
~~~

较高推理投入允许模型在提交答案前生成更多中间 Token，因而有更多机会展开：

~~~text
先计算涨价后的基数：100 × 1.2 = 120
→ 再按新基数降价：120 × 0.8 = 96
→ 检查两次百分比使用的基数不同
→ 回答 96 元
~~~

它可能带来几类具体变化：

1. **分解问题**：先生成子问题，再逐个处理；
2. **保存中间结果**：让前一步生成的数字、假设或约束成为后续 Context；
3. **尝试与修正**：在预算允许时识别矛盾、改换路径或重新计算；
4. **检查答案**：在输出最终结论前做一致性或边界检查；
5. **延迟结束**：降低模型过早生成最终答案或结束 Token 的倾向。

之所以这些额外 Token 可能提高成功率，是因为自回归模型每生成一个中间 Token，就把复杂的“一步得到答案”转换成多个较小的条件预测。前面产生的中间结果会参与后续 Attention，使模型不必只依靠单次前向计算的最后一个 Hidden State 完成全部多步计算。

但 reasoning effort 一般是高层预算或策略提示，不是精确的“思考步数”。设置为较高档位，不代表每个请求必然多生成固定数量的推理 Token，也不保证模型一定使用某种指定算法。具体能使用多少、何时停止以及不同档位名称，都由模型和服务实现决定。

#### 它怎样影响延迟、Token 和费用

更多内部推理 Token 意味着更多次自回归 Decode：

~~~text
推理 Token 更多
→ Decode 循环更多
→ 需要读取和追加更多 KV Cache
→ 首个最终答案 Token 通常更晚出现
→ 计算量和输出侧 Token 用量通常更高
~~~

因此较高 effort 的常见代价是：

- **延迟增加**：用户可见答案开始前，模型先完成更多内部生成；
- **Token 消耗增加**：推理 Token 通常也占用某种输出或 Context 预算；
- **费用增加**：若接口对推理 Token 计费，更多推理会提高费用；
- **可见答案空间受挤压**：总输出预算固定时，内部推理使用更多预算，可能留给最终回答的空间更少。

最后一点尤其容易忽略。假设某接口把推理 Token 和最终回答 Token 都纳入同一个输出上限，概念上可以理解为：

$$
\text{总输出预算}
=\text{推理 Token}+\text{最终回答 Token}
$$

如果总预算为 1,000 Token，内部推理使用了 800 Token，最终可见回答就只剩约 200 Token 的空间。实际预算口径、Token 是否保留以及计费方式因模型和接口而异，不能把这个示意公式当成所有 API 的固定合同。

#### 它与 max_output_tokens 有什么区别

两者都会涉及 Token，但控制的问题不同：

- **reasoning effort**：控制模型倾向于在最终回答前投入多少内部推理；
- **max_output_tokens**：给整个输出阶段设置不能超过的硬上限。

可以把它们理解为“预算分配倾向”和“总预算上限”：

~~~text
reasoning effort 较高 + 总输出预算足够
→ 有空间进行较多中间计算并给出完整答案

reasoning effort 较高 + 总输出预算过小
→ 推理可能占用大量预算，最终答案可能简短或被截断
~~~

所以提高 reasoning effort 时，还要检查输出预算是否足够，并读取 Response 中的完成状态和 Token 用量，而不是只看最终文本是否语法完整。

#### 什么问题更可能从较高 effort 中受益

| 问题 | 增加推理投入为什么可能有帮助 |
|---|---|
| 多步数学与逻辑 | 可以保存中间结果并逐步检查 |
| 复杂代码分析 | 可以追踪多个条件、依赖和失败路径 |
| 约束较多的规划 | 可以逐项检查约束是否冲突 |
| 简单分类或格式转换 | 通常没有足够复杂度需要长轨迹 |
| 输入缺少关键事实 | 不能通过多想创造可靠证据 |
| 工具参数违反业务规则 | 仍需外部权限和业务校验 |
| JSON 语法不稳定 | 应优先使用正式格式约束 |

更多推理也可能沿错误前提走得更远、生成不必要的步骤或增加超时。因此它提高的是复杂任务成功的机会，不是正确性保证。实际应用应在目标任务上比较正确率、延迟、Token 和费用，再选择合适档位，而不是一律设置最高 effort。

## 4. 第三层：Temperature 与 Top-p 只在选 Token 时生效

经过一次前向计算，模型已经为词表产生 Logits。此时采样参数才开始作用。

### Temperature 改变概率分布的尖锐程度

$$
p_i=\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)}
$$

- $z_i$ 是 Token $i$ 的原始 Logit；
- $T$ 是 Temperature；
- 较低 $T$ 让高 Logit 候选占据更大优势；
- 较高 $T$ 让候选概率更接近，增加选到其他候选的机会。

假设原始候选已经是：

| Token | 原始倾向 |
|---|---:|
| 彩 | 高 |
| 阳 | 中 |
| 云 | 低 |

降低 Temperature 会让“彩”更集中，提高 Temperature 会让“阳”“云”等候选更有机会。它不会重新阅读资料，也不会验证哪个 Token 对应真实世界。

所以 Temperature 不是“创造力”“准确率”或“智商”的直接旋钮。开放式构思可能受益于多样性；事实抽取和稳定分类通常希望减少无必要变化，但低 Temperature 仍可能稳定地产生同一个错误。

### Top-p 改变哪些候选能进入抽样

Top-p 先将 Token 按概率从高到低排序，再保留累计概率达到阈值的最小集合。例如：

| Token | 概率 | 累计概率 |
|---|---:|---:|
| 彩 | 0.55 | 0.55 |
| 阳 | 0.25 | 0.80 |
| 当 | 0.10 | 0.90 |
| 其他 | 0.10 | 1.00 |

若 top_p 为 0.8，当前步只需在“彩”和“阳”的集合中采样。下一步的概率分布不同，候选集合大小也会变化。

Temperature 修改候选间的相对概率，Top-p 截断参与采样的尾部。两者都会影响输出多样性。排查问题时通常先改变一个，避免无法判断变化来自哪里；有些模型也不允许任意设置这些字段。

### Top-k：只保留概率最高的固定数量候选

Top-k 与 Top-p 都在采样前缩小候选集合，但规则不同。假设某一步的概率为：

| Token | 概率 | 排名 |
|---|---:|---:|
| 彩 | 0.45 | 1 |
| 阳 | 0.25 | 2 |
| 当 | 0.15 | 3 |
| 云 | 0.08 | 4 |
| 其他 | 0.07 | 5 以后 |

若 $k=3$，Top-k 只留下“彩、阳、当”，将其他 Token 排除，再对保留候选重新归一化并采样。

它和 Top-p 的差别是：

- **Top-k** 固定保留 $k$ 个候选，不管第 $k$ 名的概率有多低；
- **Top-p** 固定保留多少累计概率，候选数量随当前分布变化。

当分布很集中时，Top-p 可能只留下少量 Token；当分布较平时，它可能留下更多 Token。Top-k 的集合大小始终固定，因此不能随模型当前不确定程度自动伸缩。

> [!warning] Top-k 不一定是 OpenAI API 的公开字段
> Top-k 是常见的解码概念，许多本地推理框架和其他模型 API 会提供它，但 OpenAI 的特定接口或模型未必暴露 top_k。没有出现在当前官方 Reference 中时，不能自行把它放进请求；OpenAI API 常见的是 Temperature 和 Top-p。

### Presence Penalty：降低已经出现过的 Token 再次出现的倾向

生成过程中，模型可能反复使用同一个词或围绕同一内容打转。Presence Penalty 会检查候选 Token 是否已在当前生成文本中出现，并对出现过的 Token Logit 施加惩罚。可以用简化形式理解：

$$
z'_i=z_i-\lambda\,\mathbf{1}(i\text{ 已出现})
$$

- $z_i$ 是 Token $i$ 原来的 Logit；
- $\lambda$ 是 Presence Penalty；
- $\mathbf{1}$ 只有“出现过”和“没出现过”两种状态；
- 出现过时，调整后的 $z'_i$ 会降低，再经 Softmax 后被重复选中的概率通常也会下降。

它关心的是“是否出现过”，不是出现了几次。与它相关的 Frequency Penalty 通常还会根据出现次数增加惩罚，两者不要混为一谈。

较高 Presence Penalty 可能推动模型转向新词或新话题，但它不是语义级的“去重器”：

- 惩罚作用在 Token 上，同义词仍可能重复同一意思；
- 常用虚词和任务必要术语也可能受到影响；
- 值过高会让表达生硬，甚至刻意回避必须重复的名称；
- 它不能修复模型因任务不清而产生的内容循环。

### Logit Bias：在 Softmax 前直接调整指定 Token 的分数

Logit Bias 允许应用按 Token ID 给指定候选的 Logit 加上偏置：

$$
z'_i=z_i+b_i
$$

- $b_i>0$ 会提高 Token $i$ 的相对倾向；
- $b_i<0$ 会降低它的相对倾向；
- 很大的负值常被用于近似禁止某个 Token，很大的正值可能近似强迫它出现。

这个参数比自然语言指令更接近解码层，因为它直接作用于每一步的词表分数。但也正因为它操作的是 **Token ID**，使用时很容易误判：

1. 一个词可能被切成多个 Token，禁止其中一个不一定禁止所有写法；
2. 前导空格、大小写和不同语言形式可能对应不同 Token ID；
3. Token ID 依赖具体模型的 Tokenizer，换模型后映射可能变化；
4. 强偏置可能让模型绕道表达、破坏语法，或陷入重复生成。

因此 Logit Bias 适合少量、明确的词表级控制，不应代替安全策略、业务规则或正式的结构化输出约束。该字段同样取决于具体接口和模型支持。

### Logprobs 与 Top Logprobs：观察分布，而不是改变分布

前面的参数都可能影响 Token 怎样被选中；**Logprobs** 主要用于把模型选词时的概率信息返回给调用方。

若某 Token 的概率为 $p$，它的 Logprob 是：

$$
\log p
$$

因为 $0<p\leq1$，Logprob 通常不大于 0：越接近 0，代表概率越高。例如：

| 概率 $p$ | Logprob $\log p$ | 直观含义 |
|---:|---:|---|
| 0.80 | 约 -0.22 | 当前分布中很有优势 |
| 0.20 | 约 -1.61 | 倾向较弱 |
| 0.01 | 约 -4.61 | 很低概率 |

不同接口的字段形式可能不同。常见语义是：

- **logprobs**：要求返回实际选中 Token 的 Logprob；
- **top_logprobs**：同时返回该位置概率最高的若干候选及其 Logprob。

例如模型最终选择“彩”时，Top Logprobs 可能显示：

~~~text
实际选择：彩，logprob = -0.60
其他高分候选：
阳，logprob = -1.20
当，logprob = -1.90
~~~

它们适合用于调试分类边界、观察候选竞争、计算一段输出的联合对数概率，或发现模型在哪一步出现分歧。它们通常不会因为“请求返回概率”而改变模型权重或核心分布，但会增加响应数据量；流式客户端还要处理每个增量 Token 的附加信息。

> [!warning] Logprob 不是事实置信度
> 高 Logprob 只表示“在当前模型、Context 和解码处理下，这个 Token 相对自然”。一句错误陈述也可能由一串高概率 Token 组成。它不能直接解释为答案有 80% 概率真实，更不能替代校准评测和外部验证。

在 Chat Completions 一类接口中，logprobs 可能是是否启用返回的开关，top_logprobs 再指定返回多少个候选；在其他接口中，字段组织可能不同。必须按当前 Endpoint 的 Reference 组合，不能只凭同名字段推断请求格式。

## 5. 第四层：输出预算和停止条件决定最多生成到哪里

### Max Tokens、Max Completion Tokens 与 Max Output Tokens

max_output_tokens 一类字段限制这次 Response 最多使用多少输出预算。模型可以提前生成结束 Token，但不能无限超过上限。

在彩虹例子中，预算 100 足以容纳一句话；若要求分析一份长报告却只给很小预算，可能出现：

~~~text
模型仍在生成正文
→ 达到预算上限
→ 服务停止 Decode
→ 返回不完整结果
~~~

这不是模型判断任务已经完成。应用应检查响应状态或停止原因，而不是看到一段语法通顺的末尾就假设完整。

最大输出预算还会影响最坏情况下的延迟和成本，但它不是精确字数控制器。不同文字的 Token 数不同，模型也可能比上限更早结束。

不同代际和 Endpoint 使用过多个相似名称，不能把它们当成可以同时填写的三个独立旋钮：

| 常见名称 | 常见接口语境 | 核心含义 |
|---|---|---|
| max_tokens | 较早的 Completions / Chat Completions 语境 | 旧名称或旧接口中的生成上限；在部分新模型中可能弃用或不兼容 |
| max_completion_tokens | 较新的 Chat Completions 语境 | Completion 输出上限；对推理模型通常还要考虑 Reasoning Token |
| max_output_tokens | Responses API 语境 | Response 输出预算上限，具体计入项按模型文档解释 |

这三个名称都属于“限制输出预算”这一层，但字段是否存在、是否包含不可见 Reasoning Token、与输入 Context 怎样共同受限，取决于当前 Endpoint 和模型。迁移接口时，应根据 Reference 替换字段，而不是把 max_tokens 和 max_completion_tokens 同时设置后期待取较小值。

> [!note] Token 上限不是文字长度
> 100 Token 不等于 100 个汉字或 100 个单词。Tokenizer 切分、工具调用和内部推理都会影响实际消耗。达到上限时必须检查停止原因或不完整状态。

### Stop 只匹配停止模式

对支持 Stop 的接口或模型，指定字符串出现后可以终止生成。它适合某些简单分隔协议，却不检查此前内容是否正确、完整或语义有效。

如果停止字符串恰好出现在正常正文中，响应还可能被提前截断。需要严格 JSON 结构时，应使用正式的输出格式约束，而不是只靠 Stop 拼出协议。

### N：一次请求生成多少个候选 Completion

某些接口提供 n，表示对同一个输入一次生成多个候选。例如 n=3 可能返回三段不同 Completion：

~~~text
同一 Prompt
├─ 候选 1
├─ 候选 2
└─ 候选 3
~~~

它不是让单条回答“思考三次”，而是建立多条独立或近似独立的 Decode 序列。采样开启时，不同序列可能在早期选中不同 Token，随后沿各自前缀继续生成。

多个候选可用于创意备选、外部评分器重排或可验证任务中的多次尝试。但代价通常近似随实际生成的总 Token 增长：n=3 可能产生接近三份输出成本和更大响应体，也增加尾部延迟和应用筛选工作。

如果没有可靠的选择规则，多生成候选并不会自动知道哪一个正确。对于支持 Tool Call 的请求，还必须防止多个候选被误当成多个都应执行的动作。

n 是某些 Completions / Chat Completions 接口的字段，Responses API 或特定模型不一定支持。需要多个候选时，也可以由应用发起多次独立请求，但这与单请求 n 在计费、缓存、并发和 seed 行为上未必完全相同。

## 6. 第五层：工具和格式参数改变允许生成什么形状

### tool choice 改变可走的工具路径

当请求提供 tools 后，tool choice 一类配置可以让模型自主选择、禁止工具，或要求使用特定工具。

它能解决“这次是否允许或要求产生 Tool Call”，不能解决：

- 参数值是否符合业务语义；
- 当前用户是否有权限；
- 工具是否执行成功；
- 返回结果是否被正确使用。

这些仍由应用校验和执行。

### Parallel Tool Calls 改变一轮能提出多少调用

如果模型需要查询多个互不依赖的城市天气，并行 Tool Call 可以减少往返次数。但调用之间若有依赖、会写同一资源或存在副作用，盲目并行可能产生顺序和冲突问题。

它改变工具交互的编排方式，不改变工具本身的权限与真实性。

### Structured Output / Text Format 改变输出合同

格式参数可以约束输出为文本或符合 JSON Schema 的对象。它显著减少解析失败，但完整接收路径仍是：

~~~text
模型按 Schema 生成
→ 程序解析
→ 校验字段间业务关系
→ 绑定可信数据来源
→ 决定是否使用或执行
~~~

Schema 是语法和结构合同，不是事实、权限或业务正确性的证明。

## 7. 第六层：stream、store 和 metadata 主要属于服务外围

### stream 改变传输时机

streaming 让 API 把生成中的事件陆续发给客户端，降低用户看到首段内容的等待感。客户端需要处理增量事件、断线、重复连接和未完成结构。

它通常不改变模型权重、Context 或核心 Token 分布。模型本来就在逐 Token Decode；stream 只是决定服务等完整响应后一次返回，还是边生成边传输。

### store、metadata 与用户标识改变管理方式

这类字段可用于响应保存、业务关联、观测或安全处理，通常不直接改变模型推理。具体保留和隐私行为应查官方文档，不应在 metadata 中放入密钥或不必要的个人信息。

它们与“把内容存进模型记忆”无关。服务保存一条 Response 不会更新模型权重。

### Service Tier：选择服务质量路径，而不是改变模型能力

某些 OpenAI 接口提供 service_tier 一类字段，用于选择或请求某种服务等级，例如默认处理、低优先级批量处理，或更稳定的低延迟路径。具体可选值、资格、额度和计费会随产品变化，应以当前账号和 Endpoint 文档为准。

它主要影响服务调度层：

~~~text
同一个模型请求
→ 选择符合资格的服务队列或容量策略
→ 影响排队、延迟承诺、吞吐和费用
→ 模型执行并返回实际使用的服务等级
~~~

Service Tier 通常不表示换成“更聪明的模型”，也不直接改变 Prompt、权重或采样概率。即使模型和输入相同，不同服务路径仍可能因后端版本、批处理和数值执行差异而不构成逐字一致保证。

应用应把它视为延迟、吞吐、可用性和成本之间的部署选择，并检查响应中实际采用的 tier。请求某个等级不一定意味着在所有账号、地区和流量状态下都能获得该等级。

### Seed：控制部分采样随机性

当接口支持 seed 时，相同 seed 会让伪随机采样从相同初始状态开始。若模型快照、完整 Context、采样参数和后端执行条件也相同，多次结果往往更容易复现。

但 seed 只控制随机来源的一部分。它不能固定：

- 模型别名后来指向的新快照；
- 隐藏系统模板、工具结果或检索材料变化；
- 分布式浮点计算和后端实现变化；
- 服务内部没有受该 seed 控制的动态流程。

因此 Seed 提供的是 **尽力而为的近似复现**，不是确定性合同。它适合调试、A/B 对比和回归测试；测试仍应记录模型版本、完整请求、外部结果和响应中的系统指纹或类似版本信息（若接口提供）。

Seed 与 Temperature 的分工也不同：Temperature 决定概率分布有多集中，Seed 决定在给定分布上伪随机选择从哪个随机状态开始。Temperature 为 0 时通常已接近贪心解码，Seed 的作用会减小，但服务层数值和版本变化仍可能造成差异。详细原因见 [[07-how-inference-produces-an-answer#10. 为什么相同输入不一定得到相同回答|相同输入为什么仍会得到不同回答]]。

## 8. 参数之间为什么会相互制约

参数并非彼此独立。例如：

- Context 很长会增加 Prefill 成本，也会挤占输入输出总预算；
- 推理投入和可见答案可能共同消耗某类输出预算；
- 较高 Temperature 可能提高格式波动，因此结构任务更依赖 Schema；
- 强制 Tool Call 会改变模型直接回答的路径；
- streaming 下客户端必须在停止前把增量结果视为不完整。

因此不能复制一套“最佳参数”到所有任务。参数值应服务于具体任务、模型支持范围和验收标准。

## 9. 结果不好时，按因果顺序排查

假设模型没有正确解释彩虹。比“试试把 Temperature 改成 0.3”更有效的顺序是：

1. **任务是否明确**：输入是否说明要解释原因、长度和受众？
2. **证据是否存在**：必要事实是否在权重可覆盖范围、输入或工具结果中？
3. **Context 是否可用**：历史、材料和工具描述是否冲突、过长或含糊？
4. **模型是否合适**：是否支持所需模态、工具和复杂度？
5. **推理预算是否足够**：复杂任务是否在计算或输出中途被截断？
6. **输出合同是否匹配**：程序需要 JSON 时是否提供正式 Schema？
7. **最后调采样**：只在确实需要控制稳定性或多样性时调整 Temperature / Top-p。

这个顺序对应请求真实生命周期：先确保模型看到了正确问题和证据，再检查计算与输出空间，最后才调整如何从候选中采样。

## 10. 用一张表回顾参数真正修改了什么

| 参数类别 | 主要改变 | 通常不改变 |
|---|---|---|
| input / instructions / 历史 / tools | 本次 Context 和可见协议 | 训练权重 |
| model | 权重、架构与支持能力 | 外部事实真实性 |
| reasoning effort | 运行时推理投入 | 正确性保证 |
| Temperature / Top-p / Top-k | Token 候选分布与集合 | 知识来源和证据 |
| Presence Penalty / Logit Bias | 指定 Token 的解码分数 | 语义级规则和安全保证 |
| Logprobs / Top Logprobs | 返回候选 Token 的概率信息 | 事实置信度和核心分布 |
| 输出预算 / Stop | Decode 上限和停止方式 | 任务是否实际完成 |
| N | 一次生成的候选序列数量 | 自动选出正确候选 |
| tool choice | 是否允许或要求 Tool Call | 权限与执行成功 |
| Structured Output | 输出结构 | 字段语义真实性 |
| stream | 响应传输时机 | 核心推理过程 |
| Seed | 部分采样随机状态 | 跨版本确定性 |
| Service Tier | 调度、延迟、吞吐和费用路径 | 模型本身的能力 |
| store / metadata | 服务保存、关联和观测 | 模型长期记忆 |
