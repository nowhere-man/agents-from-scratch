# 多模态视频理解模型原理

> [!abstract] 本章只回答一个问题
> 当用户对一段视频提问时，原始像素、声音和时间变化怎样被选择、编码并交给模型，模型又为什么必须把结论绑定回可检查的视频证据？

## 前置知识

前面已经知道：文本必须先变成 Token 和向量；模型只能使用实际进入 Context 的信息；Agent 系统应把生成结论与真实证据区分开。视频模型仍遵循这些原则，只是“哪些信息进入模型”变得更复杂。

本章跟踪一个具体问题：

> 在这段 10 分钟的厨房视频里，杯子是什么时候被碰倒的？是谁碰倒的？

回答这个问题不仅要识别“人”和“杯子”，还要找到短暂事件、理解先后变化、结合声音，并给出可以回看的时间范围。

## 1. 视频模型并不是无损地看完所有内容

10 分钟、每秒 30 帧的视频共有：

$$
10\times60\times30=18{,}000\text{ 帧}
$$

每一帧又包含大量像素。如果全部保留原分辨率并转换成视觉 Token，序列长度和 Attention 成本会非常高；音频、字幕和 OCR 还会继续增加输入。

所以视频理解的第一步不是推理，而是选择和压缩：

~~~mermaid
flowchart LR
    A[原始视频与问题] --> B[解码并建立时间轴]
    B --> C[粗采样帧和片段]
    B --> D[音频、ASR 与 OCR]
    C --> E[视觉编码与 Token 压缩]
    D --> F[带时间的音频和文本表示]
    E --> G[跨模态与时间融合]
    F --> G
    G --> H[模型定位候选事件]
    H --> I[回看相关片段]
    I --> J[生成带证据的答案]
~~~

==模型最终能回答什么，首先受它实际观察到什么限制。== 如果杯子倒下的瞬间没有被采样，后续语言模型再强，也不能从真实证据中恢复那个瞬间。

## 2. 先建立统一时间轴

视频文件中可能同时存在帧号、容器时间戳、音频时间、字幕时间和切片内相对时间。它们不一定天然一致，尤其是可变帧率、剪辑或重新编码后。

系统首先需要把不同来源映射到统一时间基准，例如毫秒：

~~~json
{
  "frame_id": "frame-7210",
  "timestamp_ms": 240333,
  "clip_id": "clip-24"
}
~~~

这一步看似只是工程预处理，却决定最终“04:00 到 04:03”能否准确指回原视频。若时间映射丢失，模型即使描述对了事件，也可能给出漂移的时间戳。

现在问题中的“什么时候”有了可计算的坐标，下一步才是决定哪些时刻要送入模型。

## 3. 采样决定模型是否有机会看到杯子倒下

最简单的方案是固定间隔抽帧。假设每 2 秒取一帧，而杯子从被碰到到倒下只持续 0.4 秒，这个事件可能刚好发生在两个采样点之间。

~~~text
04:00.0  采样：杯子直立
04:00.8  未采样：手臂碰到杯子
04:01.2  未采样：杯子倒下
04:02.0  采样：杯子已倒
~~~

模型能看出状态从“直立”变成“已倒”，却未必看到是谁接触了杯子。这时正确状态应是“观察到杯子状态变化，但缺少碰撞瞬间证据”，而不是根据最近的人物猜测。

采样策略都是覆盖和成本之间的取舍：

| 策略 | 怎样取信息 | 对当前问题的风险 |
|---|---|---|
| 固定间隔 | 每隔固定时间取帧 | 漏掉短暂碰撞动作 |
| 关键帧 | 保留视觉变化明显的帧 | 倒下前的接触帧未必显著 |
| 镜头感知 | 按镜头边界切片 | 同一镜头内短动作仍会丢失 |
| 运动感知 | 对运动剧烈区域加密 | 缓慢或遮挡动作可能不显著 |
| 问题引导 | 先找杯子相关片段再密集采样 | 初次检索错误会限制后续观察 |

长视频系统常先稀疏浏览全局，再对候选片段密集回看。这样既控制总 Token，又提高关键时刻的时间分辨率。

## 4. 一帧图像怎样变成视觉 Token

采样得到的帧仍是像素矩阵，不能直接使用文本 Tokenizer。常见做法是把图像切成小块，称为 **Patch**，再由视觉编码器把每个 Patch 转成向量。

对于高 $H$、宽 $W$、Patch 边长 $P$ 的图像，最简单情况下 Patch 数约为：

$$
N=\frac{H\times W}{P^2}
$$

公式表达一个直接取舍：

- Patch 越小，Token 越多，杯沿、手指和屏幕小字等细节更可能保留；
- Patch 越大，计算更省，但小物体和局部接触更容易在一个大区域中被压缩掉。

视觉编码器让每个 Patch 的向量结合周围区域，形成表示物体、形状、空间关系和局部语义的 **视觉表示**。它不是先把整张图翻译成一句文字，而是在数值空间中保留供后续读取的特征。

实际系统还可能动态调整分辨率、合并相似 Token 或使用层级编码器。无论具体实现怎样，目标都是在有限预算下保留与任务相关的视觉信息。

## 5. 为什么视觉表示还不能直接当文本 Embedding 使用

视觉编码器输出的向量维度和分布，不一定与语言模型的 Hidden State 匹配。系统需要一个连接模块，让语言侧能够读取视觉信息。常见路线包括：

- **Projector**：把视觉向量映射到语言模型需要的维度，再作为视觉 Token 放入序列；
- **Cross-Attention**：语言状态作为 Query，按需读取视觉 Key/Value；
- **Resampler / Query 模块**：用少量可学习 Query 从大量视觉 Token 中提取较紧凑的表示。

以当前问题为例，原始一帧可能产生上千个 Patch 表示；Resampler 可以把它们压成较少视觉 Token，再交给主模型判断“杯子”“手臂”和“桌面”的关系。

压缩减少成本，也必然做出信息取舍。若压缩模块认为背景大区域更重要，细小接触动作可能被弱化。所谓“视觉接入语言空间”不是无损格式转换，而是学习哪些视觉特征值得保留并怎样让文本问题读取它们。

## 6. 识别物体不等于理解动作

单独看三帧，模型可能都能识别出人和杯子：

~~~text
帧 A：杯子直立，手臂在远处
帧 B：手臂接近杯子
帧 C：杯子倒下，手臂离开
~~~

但问题问的是“谁碰倒”，需要知道顺序和状态变化：手臂接近发生在杯子倒下之前，并且两者在空间上接触。若把 A、B、C 打乱，物体仍都存在，动作含义却改变。

因此视频表示除了帧内空间关系，还必须包含：

- 帧或片段的先后位置；
- 动作持续了多久；
- 同一对象怎样跨帧移动；
- 一个状态如何变成另一个状态。

系统可以使用时间位置编码、时空 Attention、短片段编码器、3D Patch 或分层时间模块。实现不同，核心目的相同：让模型不只知道“出现了什么”，还知道“何时出现、怎样变化、前后顺序是什么”。

> [!note] 时间先后仍不自动等于因果
> 看到手臂靠近后杯子倒下，只能形成较强候选。若接触点被遮挡，也可能是桌子震动或其他人造成。因果判断需要足够细的视觉、音频和多角度证据。

## 7. 音频、ASR 和 OCR 为什么要与画面一起保留

假设碰撞时画面被遮挡，但音轨在 04:01 出现清晰撞击声，随后有人说“抱歉，我碰倒了杯子”。这些都是补充证据。

不同模态提供的信息不同：

| 来源 | 在当前问题中可能提供什么 | 容易丢失什么 |
|---|---|---|
| 画面 | 杯子状态、人物位置、接触动作 | 遮挡处的真实接触 |
| ASR | 人说了什么以及大致时间 | 非语音声音、说话人误识别 |
| 音频事件 | 撞击、碎裂、水声 | 具体是谁造成的 |
| OCR / 字幕 | 屏幕文字、字幕和标签 | 文字对应的真实对象与意图 |
| 元数据 | 时间、镜头和来源 | 内容本身的语义 |

ASR 是把语音转成文本，不等于理解所有声音；OCR 读取画面文字，也不等于证明文字内容真实。可靠系统应保留每条证据的模态和时间来源，而不是过早把它们压成一段没有出处的总结。

如果字幕说“甲碰倒杯子”，但画面显示乙在杯子旁，模型不应静默选择更醒目的文字。跨模态融合的职责是比较和组合证据，冲突无法解决时应明确保留冲突。

## 8. 跨模态融合怎样围绕同一问题工作

当视觉、音频和文字表示都带有时间信息后，模型可以根据问题进行条件读取：

~~~text
问题中的“杯子”
→ 定位出现杯子的片段
→ 找出“直立 → 倾斜 → 倒下”的状态变化
→ 在变化前后查找人物轨迹和接触区域
→ 对齐同一时间的撞击声、ASR 和字幕
→ 形成带来源的候选事件
~~~

这不是先让每种模态各写一篇摘要再随意拼接。细粒度系统会尽量保留“哪个向量或识别结果来自哪个时间片段”，使主模型能够围绕用户问题读取相互对应的证据。

模型可能最终形成：

~~~json
{
  "start_ms": 240700,
  "end_ms": 242100,
  "actor": "穿蓝色上衣的人",
  "event": "手臂接触杯子后杯子倒下",
  "evidence_refs": ["clip-24", "frame-7210", "audio-240900"],
  "confidence_state": "supported"
}
~~~

这里的结构只是候选结论；evidence_refs 让程序和人可以回到原片段检查，而不是只相信自然语言描述。

## 9. 长视频为什么需要分层浏览和回看

如果对 10 分钟视频始终使用最高帧率和最高分辨率，Token 成本很快失控。长视频系统通常采用分层流程：

1. 按时间切成较短 Clip；
2. 对全视频做稀疏采样，建立片段级表示或索引；
3. 根据“杯子被碰倒”检索可能相关的 Clip；
4. 对候选 Clip 使用更密集帧率和更高分辨率；
5. 联合读取对应音频、ASR 和 OCR；
6. 把结论绑定回原始时间范围。

这类似先浏览目录，再回到相关页面细读。但第一次粗览可能漏掉事件，因此系统应允许使用多种检索信号和回看原始片段，而不是把第一轮摘要当作不可更改的事实。

长视频越长，在固定预算下通常意味着采样更稀、单片段压缩更强或检索依赖更大。长度增加不等于模型实际看到的细节增加。

## 10. 训练怎样让这些模态协同

视频模型需要从不同训练信号中学习表示和协作关系，例如：

- 图像或视频与文本描述的对齐；
- 根据视觉与音频内容生成描述；
- 视频问答；
- 事件顺序与时间定位；
- 音视频同步；
- 指令遵循和偏好后训练。

这些目标会更新视觉编码器、连接模块和主模型的部分或全部参数，使“杯子倒下”之类的时空模式能够与语言问题和回答关联。

训练仍不会让模型无损保存视频。训练数据是否包含短动作、精确时间标注、遮挡场景和跨模态冲突，会直接影响模型擅长什么。

## 11. 证据在哪一步丢失，就产生哪一类边界

现在可以沿整条数据流诊断失败，而不是笼统说“视频模型没看懂”：

### 采样遗漏

碰撞瞬间未被抽到。模型最多根据倒下前后状态推测，不能确认谁接触。

### 空间压缩

分辨率或 Patch 太粗，杯子很小，手与杯子的接触像素被丢失。

### 时间建模错误

模型识别出手臂、杯子和撞击声，却把先后顺序或人物轨迹关联错。

### 跨模态冲突

字幕、旁白和画面指向不同人物，模型错误地把文字当作更可信来源。

### 语言补全

证据不足时，语言解码器根据常见厨房场景补出“最近的人碰倒了杯子”，形成流畅但没有观察依据的结论。

因此视频没有报告某事件，不等于事件没有发生。系统应区分：

- **not_observed**：采样没有覆盖到足够证据；
- **insufficient_evidence**：看到了候选，但画质、遮挡或冲突使其无法确认；
- **supported**：现有可回查证据支持结论；
- **confirmed_negative**：在满足任务要求的观察覆盖下，证据支持事件未发生。

confirmed_negative 的门槛远高于“模型没看到”。

## 12. 怎样生成一个可审计的最终回答

对最初问题，可靠输出不应只有：

> 穿蓝色上衣的人在 4 分钟左右碰倒了杯子。

还应保存可机器处理的证据关系：

~~~json
{
  "answer": "穿蓝色上衣的人碰倒了杯子。",
  "start_ms": 240700,
  "end_ms": 242100,
  "evidence_refs": ["clip-24", "frame-7210", "audio-240900"],
  "status": "supported"
}
~~~

完整流程是：

~~~text
保留原始视频
→ 记录解码与采样策略
→ 为帧、音频、ASR 和 OCR 保留统一时间戳
→ 检索并密集回看候选片段
→ 模型生成带 evidence_refs 的结论
→ 程序检查引用存在、时间范围合法且来源匹配
→ 高风险结论由人回看原片段
~~~

模型生成的是对证据的语义解释；原始媒体和时间片段才是可以回查的证据。若系统只保留一段摘要而丢弃中间引用，就无法判断错误发生在采样、识别、融合还是语言生成。

## 13. 不同视频任务在同一管线中关注不同环节

| 任务         | 最依赖的环节        | 典型失败        |
| ---------- | ------------- | ----------- |
| 视频摘要       | 全局采样和事件取舍     | 漏掉短事件或过度概括  |
| 视频问答       | 问题引导检索和证据组合   | 找错片段后合理猜测   |
| 时间定位       | 统一时间轴和细粒度回看   | 时间边界漂移      |
| 行为识别       | 对象跟踪、状态变化和顺序  | 把静态共现误当动作   |
| OCR / 字幕理解 | 分辨率、文字识别和时间关联 | 小字和闪现文字遗漏   |
| 高光识别       | 领域相关的重要性标准    | 把视觉显著误当业务重要 |

这些任务不是七套互不相关的知识点。它们都经过同一条“观察、编码、融合、推理、输出”管线，只是对不同环节的覆盖和精度要求不同。

## 常见误解

> [!warning] 视频模型看过每一帧
> 许多系统只处理采样帧或压缩后的片段表示。是否逐帧处理要看具体输入管线。

> [!warning] 视频越长，模型看到的信息越多
> 在固定 Token 和计算预算下，视频越长通常意味着采样更稀或压缩更强，细节更容易丢失。

> [!warning] 有时间戳就证明定位准确
> 时间戳可能来自粗片段边界或模型估计。必须保留统一时间映射并回查原视频。

> [!warning] ASR 已经包含全部音频信息
> ASR 主要记录说了什么，不完整表示撞击、音乐、语气、停顿和说话人关系。
