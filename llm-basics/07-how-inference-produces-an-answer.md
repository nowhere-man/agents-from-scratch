# 一次推理怎样生成回答

> [!abstract] 本章只回答一个问题
> 训练完成的 Assistant Model 收到一次请求后，怎样把完整输入处理成第一个输出 Token，再逐个生成后续 Token，直到返回答案？

## 前置知识

[[06-from-base-model-to-assistant|上一章]]得到了一套更倾向于理解指令和直接回答的权重。进入推理阶段后，这些权重保持不变：没有训练样本、Loss、反向传播和参数更新，只有一次次前向计算。

本章跟踪这个请求：

> 用户：请用一句话解释彩虹为什么出现。

最终回答可能是：

> 彩虹是阳光在水滴中发生折射、反射和色散后形成的。

不要把这句话看成一次性吐出的字符串。模型实际经历的是：先读完整输入，再选择“彩”，然后根据“输入 + 彩”选择“虹”，依次继续，直到停止。

## 1. 先看清一次请求的两段计算

~~~mermaid
flowchart LR
    A[消息和运行配置] --> B[构造本次 Context]
    B --> C[Tokenization]
    C --> D[Prefill<br/>处理全部输入]
    D --> E[选择第一个输出 Token]
    E --> F[Decode<br/>每轮处理一个新 Token]
    F --> G{达到停止条件？}
    G -->|否| F
    G -->|是| H[组装并返回结果]
~~~

这里最重要的分界是：

- **Prefill** 读取请求开始前已经存在的全部输入，并建立后续生成需要的内部状态；
- **Decode** 在此基础上每轮生成一个 Token，再把它追加到上下文中继续预测。

下面沿请求到回答的顺序展开。

## 2. 服务先构造模型本次真正看到的 Context

用户输入框里的句子不一定是模型的全部输入。服务还可能加入：

~~~text
System / Developer 指令
+ 对话历史
+ 当前 User 消息
+ 工具名称、用途和参数结构
+ 检索到的材料
+ 输出格式要求
~~~

这些内容经过消息模板和角色边界组织后，才形成模型本次能够读取的 **Context**。Context 是“一次推理当前可见的输入工作区”，不是模型权重，也不是自动跨请求存在的长期记忆。

在最小例子中，可以把实际输入近似理解为：

~~~text
[System] 你是一个回答简洁、准确的助手。
[User] 请用一句话解释彩虹为什么出现。
[Assistant]
~~~

最后的 Assistant 边界告诉模型：接下来应生成助手回复。角色标记的具体编码由模型和服务决定，但核心作用是把不同来源的文本组织成训练时熟悉的交互格式。

模型不会自动读取没有进入本次 Context 的网页、数据库、其他聊天或电脑文件。

## 3. Tokenization 把完整 Context 变成序列

Tokenizer 将刚才的输入转换成 Token ID 序列。为了说明流程，可以抽象成：

~~~text
[System] | 你是 | 一个 | 助手 | ... | [User] | 请 | 用 | 一句话 | ... | [Assistant]
~~~

实际切分可能与示意不同。重要的是，模型接收的不是原始字符串，而是一串有先后顺序的 Token ID。

输入 Token 数会同时影响：

- 是否超过 Context Window；
- Prefill 需要处理多少位置；
- KV Cache 需要保存多少历史表示；
- 首 Token 延迟和调用成本。

**Context Window** 是一次推理能够容纳的输入与输出 Token 工作区。它表示“最多能放进去多少”，不保证模型会同样可靠地使用每个位置，也不是长期记忆容量。

## 4. Prefill：一次处理全部输入

现在完整输入会经过 Embedding 和所有 Transformer 层。每个位置都根据自己左侧的内容更新 Hidden State；由于 Causal Mask，后面的 Token 能读取前面的 Token，前面的 Token 不能偷看后面。

虽然存在这种因果限制，输入中的许多位置仍可由硬件并行计算。这一整段“对已有输入做前向计算”的阶段叫作 **Prefill**。

Prefill 会得到两类后续结果：

1. 最后一个输入位置的最终 Hidden State，它总结了模型在当前 Context 下预测下一 Token 所需的信息；
2. 每一层、每个历史位置的 Key 和 Value，供后续新 Token 读取。

最后位置的 Hidden State 经 LM Head 投影成整个词表的 **Logits**，Softmax 再把它们转换成概率。此时模型得到的是“第一个输出 Token 应该是什么”的分布，例如：

| 候选 Token | 示意概率 |
|---|---:|
| 彩 | 0.42 |
| 当 | 0.11 |
| 阳 | 0.08 |
| 其他 | 0.39 |

这张表只是示意。它表达的关键是：Prefill 的直接产物不是整句答案，而是第一个输出位置的候选分布。

输入越长，Prefill 通常需要处理的计算越多，因此会显著影响 **TTFT**（Time To First Token），即从发出请求到收到首个 Token 的时间。

## 5. KV Cache：保存已经算过的 Attention 材料

假设模型从分布中选中了“彩”。下一轮要预测“虹”时，完整前缀已经变成：

~~~text
原始 Context + 彩
~~~

朴素做法是把所有历史 Token 再经过全部层计算一遍。但模型权重没有改变，历史位置在各层产生的 Key 和 Value 也不会因右侧新增“彩”而改变。

因此推理系统会在 Prefill 时保存各层历史位置的 K/V，这就是 **KV Cache**。生成“彩”后，只需：

1. 计算新 Token“彩”在每层的 Q、K、V；
2. 用它的 Query 读取 Cache 中所有历史 Key 和 Value；
3. 把“彩”的新 K/V 追加到 Cache；
4. 得到用于预测“虹”的新 Hidden State。

KV Cache 节省的是对历史 Token 的重复计算，代价是占用内存。它会随层数、序列长度、并发数量、KV Head 数和数值精度增长。

> [!warning] KV Cache 不是模型记忆
> 它是当前生成会话中的数值缓存，保存 Attention 已计算过的历史材料。请求结束或缓存被释放后，它不会自动成为模型的长期知识，也不会修改权重。

## 6. 从 Logits 中选出一个 Token

每一轮得到的 Logits 都要转换成概率，再由解码策略选出一个实际 Token。假设候选分布为：

| Token | 概率 |
|---|---:|
| 彩 | 0.42 |
| 阳 | 0.18 |
| 它 | 0.10 |
| 其他 | 0.30 |

选择并不总是机械取最高概率项。系统可以按配置改变分布或候选集合后再采样。

### Temperature 改变分布有多集中

$$
p_i=\operatorname{softmax}(z_i/T)
$$

- $z_i$ 是第 $i$ 个 Token 的 Logit；
- $T$ 是 Temperature；
- 较低的 $T$ 会放大高分候选的优势；
- 较高的 $T$ 会让更多候选有机会被选中。

Temperature 只改变如何从模型已有判断中选词，不会补充缺失知识，也不能把错误事实变正确。

### Top-p 改变参与采样的候选集合

Top-p 先按概率从高到低排列 Token，再取累计概率达到阈值的最小集合，只在其中采样。某一步分布很集中时，集合可能很小；分布较平时，集合会更大。

它过滤低概率长尾候选，但不会判断候选是否真实、完整或符合业务规则。

## 7. Decode：把刚选出的 Token 变成下一轮输入

选中“彩”后，它会被追加到序列并送入下一轮；模型读取历史 KV Cache，得到预测“虹”的分布。再选中“虹”后，继续预测“是”：

~~~text
完整输入
→ 彩
→ 彩虹
→ 彩虹是
→ 彩虹是阳光
→ ……
~~~

这段逐 Token 循环叫作 **Decode**。每一步的输入都包含上一步已经选出的结果，所以后面的生成依赖前面的选择，不能像 Prefill 那样把所有未来位置一次性完全并行算出。

这也解释了两个现象：

- 输出越长，Decode 循环越多，总延迟通常越高；
- 如果早期选错一个关键 Token，错误会进入后续上下文，模型可能沿错误方向继续生成。

生成阶段通常还要在每层反复读取不断增长的 KV Cache，因此常受内存带宽影响。Prefill 和 Decode 使用同一个模型，却有不同的计算形态和性能瓶颈。

## 8. 生成何时停止

模型不会因为人类觉得句子已经完整就自动拥有一个外部“任务完成”状态。生成会在某个明确条件触发时停止，例如：

- 生成了训练和协议中表示结束的特殊 Token；
- 命中了接口配置的停止序列；
- 达到最大输出 Token 预算；
- 生成了完整 Tool Call，等待外部执行；
- 服务触发安全策略、超时、取消或错误。

如果模型自然生成结束 Token，可以理解为它预测“回复应该在这里结束”。如果只是达到长度上限，回答可能被截断，不能把这种停止解释成任务已完成。

## 9. 返回给用户前还有一层服务处理

模型产生的是 Token 和不同类型的输出项。服务还会把 Token 解码回文本，并按照接口协议组装响应对象。响应中可能包括：

- 最终文本；
- Tool Call 名称和参数；
- 拒绝或不完整状态；
- Token 用量和停止原因；
- 其他模型或服务元数据。

**Streaming** 只是把已经生成的增量事件陆续传给客户端，让用户更早看到内容。它通常不改变模型如何计算下一个 Token，只改变传输时机。客户端仍要处理断线、半个结构化对象和未正常结束的响应。

## 10. 为什么相同输入不一定得到相同回答

先把“相同输入”说精确。用户两次输入了相同文字，不代表模型执行了相同计算。要讨论可复现性，至少要确认以下条件全部固定：

+ 相同模型权重和 Tokenizer
+ 完全相同的最终 Token 序列
+ 相同的推理与采样配置
+ 相同的工具、检索和外部结果
+ 相同的服务实现与数值执行路径


只要其中一项变化，输出不同就不神秘。下面按通常的影响优先级，从最直接、最常见的原因开始分析。

### 1. 启用了随机采样

如果 Temperature 大于 0，模型通常会从候选概率分布中随机抽样，而不是永远选择概率最大的 Token。假设某一步的概率为：

| 候选 | 概率 |
|---|---:|
| 彩 | 0.55 |
| 阳 | 0.30 |
| 当 | 0.15 |

第一次可能抽到“彩”，第二次可能抽到“阳”。两个 Token 都来自同一分布，因此模型参数和 Prompt 完全相同也可以产生不同结果。

Top-p 只决定哪些 Token 可以进入候选集合，不决定最后一定选哪个。top_p 固定为 0.9，只表示每次按同样规则建立候选集合；只要集合中仍有多个 Token 并继续随机采样，两次仍可能不同。

某些接口允许设置 seed。固定 seed 可以控制一部分伪随机选择，但只有模型快照、请求和服务执行条件也足够稳定时，才可能近似复现；它通常不是跨版本永久逐字一致的保证。

### 2.Temperature 为 0 不一定等于严格确定性

概念上，Temperature 趋近 0 时通常采用 **Greedy Decoding（贪心解码）**：每一步选择 Logit 最大的 Token。若每一步的 Logits 完全相同，且最大值唯一，整段输出就应该相同。

需要注意，公式 $z_i/T$ 在 $T=0$ 时不能直接做除法。API 中的 temperature=0 通常是服务定义的“近似贪心”或特殊解码路径，而不是把数学公式真的除以零。具体行为由服务实现决定。

因此，当模型权重、最终 Token 序列和解码逻辑都真正固定后，temperature=0 时仍出现差异，问题通常不再是“模型主动随机创作”，而是后面的输入、服务或数值条件并没有完全固定。

### 3：用户文字相同，但最终 Prompt Token 不同

API 服务送入模型的 Context 可能还包含：

- System / Developer 指令；
- 对话历史和 previous response；
- 当前日期、用户位置或应用状态；
- 工具定义及排列顺序；
- 检索材料、文件内容和工具结果；
- 服务添加的消息模板和特殊 Token。

用户看到的 Prompt 相同，只能证明 User 消息相同。若检索每次返回不同文档、天气工具结果变化、历史摘要变化，或服务模板升级，最终 Token 序列就不相同，Prefill 产生的 Hidden State 和首 Token Logits 自然也会不同。

所以排查时应比较真正发送给模型的完整请求和可观测 Context，而不是只比较输入框中的一句话。托管服务可能不会公开所有内部模板，这也意味着调用方无法证明隐藏输入完全相同。

### 4.调用的是同一个模型名称，但不是同一份执行快照

一个稳定的模型别名可能由服务方指向更新后的模型快照。服务还可能调整：

- 系统模板或安全策略；
- Tokenizer、推理配置和默认参数；
- 量化版本或推理内核；
- 推理模型使用的内部计算预算；
- 路由到的后端模型或模型变体。

这时 API 中的 model 字符串相同，不代表底层权重和整套服务配置逐位相同。若服务提供固定版本或快照标识，应在可复现实验中固定它，并记录请求时间和版本信息。

### 5. 浮点并行计算可能产生极小数值差异

即使权重和 Token 完全相同，GPU 上的矩阵计算也未必保证每次按完全相同顺序执行。浮点加法不满足严格的结合律：

$$
(a+b)+c\neq a+(b+c)
$$

并行归约、动态 Batching、不同 GPU、算子内核、低精度计算和量化，都可能让最后几位数出现微小差异。

多数时候，这些差异太小，不会改变最大 Logit 对应的 Token。但如果两个候选分数非常接近：

~~~text
第一次：Token A = 12.345681，Token B = 12.345679
第二次：Token A = 12.345678，Token B = 12.345680
~~~

贪心解码第一次选择 A，第二次选择 B。自回归模型会把刚选出的 Token 加入下一轮 Context，这一个早期差异会沿 Decode 不断放大，最终形成明显不同的整段回答。

这就是 temperature=0 后仍可能不同的核心数值原因：它消除了显式采样随机性，却没有自动保证每一步 Logit 的计算达到逐位确定。

### 6. 推理系统可能使用动态或非确定性内部流程

某些推理模型和服务不只是执行一次固定的贪心 Decode，还可能在最终回答前使用内部推理 Token、候选搜索、路由、提前停止或其他动态计算。MoE 模型的服务实现、推测解码和分布式推理也可能包含动态路径。

如果服务没有承诺这些流程严格确定，外部 temperature=0 只约束某一层的 Token 选择，未必关闭整个系统中的全部随机或动态决策。

需要区分两种情况：正确实现的推测解码可以保持目标分布不变，但“分布不变”不等于每次逐字相同；近似优化、动态路由或服务策略则还可能改变实际结果。

### 一个更准确的结论

如果满足以下理想条件：

1. 权重、Tokenizer 和模型代码逐位相同；
2. 最终输入 Token 序列逐位相同；
3. 不使用随机采样，而是固定的贪心解码；
4. 所有算子和并行归约都是确定性的；
5. 没有动态工具、检索、路由、隐藏推理和版本变化；

那么相同输入应该产生相同输出。

> [!important] 稳定不等于正确
> 即使所有条件固定并得到完全相同的答案，也只证明计算可复现，不能证明答案符合事实。确定性与正确性是两个独立维度。

## 11. “模型先想完再回答”应该怎样理解

普通自回归模型按刚才的循环逐 Token 计算，并不是先在某处保存一篇完整答案，再把它复制出来。

某些推理模型可能在最终可见回答前使用额外推理 Token、搜索或工具步骤。这里要区分：

- 神经网络每层产生的 Hidden State；
- 服务可能使用但不展示的推理过程；
- 模型生成给用户看的解释文本；
- 最终答案。

它们不是同一个对象。可读的“思考步骤”仍是生成内容，不是对所有内部神经计算的完整转录，也不能单独证明结论正确。

## 12. 推理优化分别省掉什么

理解基础链路后，常见优化才能找到位置：

- **Prefix Cache**：多个请求前缀完全相同时，复用部分 Prefill 结果；
- **Paged KV Cache**：更灵活地分配和回收不同长度请求的 KV 内存；
- **Continuous Batching**：动态让新请求进入批次，提高硬件利用率；
- **Quantization**：用较低精度表示权重或 Cache，减少内存和带宽；
- **Speculative Decoding**：先用较便宜的过程提出多个候选，再由目标模型批量验证。

这些技术主要改变计算、内存、吞吐或延迟。除近似计算可能带来质量差异外，它们不会给模型写入新知识，也不改变本章的基本生成闭环。

> [!important] 一次推理的本质
> 固定权重提供训练形成的计算规律，Context 提供这一次任务的条件；Prefill 读取已有输入，Decode 再把每个新 Token 变成下一轮条件，直到服务触发停止并组装响应。
