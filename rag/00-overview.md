# RAG 与 Agentic RAG：从搜索到可验证回答

> [!abstract] 学习终点
> 读完本教程，你应该能沿着一条完整数据流解释：一份政策文档怎样被解析、切成检索单元、建立关键词和向量索引；用户提问后，系统怎样做 metadata 过滤、BM25 与向量混合召回、重排、上下文组装和带引用生成；当第一次检索不够时，Self-RAG、CRAG 和 Agentic RAG 又分别改变了哪一层。

## 先看一个“资料明明存在，却答错”的问题

员工问：

> 最新的海外差旅政策中，东京每日住宿上限是多少？请给出政策版本和原文出处。

公司知识库里确实有答案，但可能同时存在：

- 2024 年已经失效的旧政策；
- 面向国内出差的相似段落；
- 一张包含“东京、住宿、150 美元”的表格；
- 一篇写着“海外酒店费用按当地标准”的概览；
- 一份只有 HR 才能看的草案；
- 同一政策的中文和英文版本。

如果把所有文本直接塞给模型，模型仍然可能选错版本、混淆适用范围，或给出没有出处的数字。**RAG（Retrieval-Augmented Generation，检索增强生成）**的核心不是“多拼一些文字”，而是把回答拆成两个可以检查的动作：

1. **Retrieval：**从外部知识集合中找出当前问题需要的候选证据；
2. **Generation：**只根据通过筛选的证据组织回答，并保留引用或明确缺口。

模型的参数知识可以提供语言能力，但不天然知道公司刚更新的政策。RAG 把会变化、需要权限或规模太大的知识放到模型之外，在推理时按需取回。

这里的生成模型通常是 **LLM（Large Language Model，大语言模型）**：它负责理解问题和组织语言；搜索、权限、版本和事实来源仍由 RAG 周边系统负责。

## RAG 不是什么

先把几个容易混淆的方案分开：

| 方案 | 改变了什么 | 什么时候适合 | 不能替代什么 |
|---|---|---|---|
| Prompt | 改变一次请求中的指令和示例 | 规则少、资料已在输入中 | 不会自动搜索外部知识 |
| 长上下文 | 一次给模型更多材料 | 文档数量小、上下文关系重要 | 不会自动判断版本和权限 |
| RAG | 在调用前选择外部证据 | 知识会更新、资料多、需要引用 | 不能保证召回到正确证据 |
| Fine-tuning | 改变模型参数中的行为或风格 | 固定格式、固定能力、风格迁移 | 不适合频繁写入事实 |
| Agentic RAG | 让带状态的工作流多次决定搜索路径 | 问题需要分解、验证或多来源交叉检查 | 不是所有问题都值得额外循环 |

> [!tip] 先记住一个判别问题
> 如果问题的答案会因为“今天的文档版本、用户权限或实时系统状态”而改变，优先考虑检索或工具；如果只是希望模型稳定地按某种格式表达，先改 prompt 或输出 schema。

## 一条主线：从文档到答案

把系统分成**离线索引**和**在线问答**两条路径。离线路径负责把原始资料准备好；在线路径负责针对当前问题取证和生成。

~~~mermaid
flowchart LR
    A["原始文档<br/>PDF / HTML / Markdown / 表格"] --> B["解析、清洗、去重"]
    B --> C["结构化分块<br/>chunk + metadata"]
    C --> D["关键词索引<br/>倒排表 / BM25"]
    C --> E["Embedding<br/>文本 → 向量"]
    D --> F["索引存储"]
    E --> F

    Q["用户问题"] --> Q1["意图、过滤条件、查询改写"]
    Q1 --> R1["词法召回"]
    Q1 --> R2["向量召回"]
    R1 --> H["混合、去重、重排"]
    R2 --> H
    H --> S["选择与上下文组装"]
    S --> G["生成带引用的回答"]
    G --> V["评测、日志、反馈"]
    V -. "需要继续查证" .-> Q1
~~~

每个箭头都可能丢失信息：

- **解析失败：**PDF 的表格顺序被打乱；
- **分块失败：**规则和例外被切到不同 chunk；
- **索引失败：**删除的文档仍留在向量库；
- **召回失败：**正确文档没有进入候选集，这叫 **zero recall**；
- **排序失败：**正确候选被旧版本压在后面；
- **组装失败：**模型看到了相关段落，却看不到适用范围；
- **生成失败：**模型把检索材料中的指令当成自己的指令，或把缺失值猜出来。

因此，RAG 不是一个单一模型，而是一条可以逐层观测的系统管线。

## 先建立最小术语阶梯

下面这些词会在后续章节反复出现。这里先用主线给出人话含义，细节在对应章节展开。

| 术语 | 在当前问题中指什么 | 它改变了什么 |
|---|---|---|
| Corpus | 公司所有可搜索政策和附件的集合 | 定义搜索范围 |
| Document | 一份有身份、版本和权限的政策文件 | 提供原始来源 |
| Chunk | 从文档切出的检索单元 | 决定召回粒度 |
| Metadata | 版本、地区、适用人群、权限等描述字段 | 让系统先做确定性过滤 |
| Tokenizer | 把文字切成模型或搜索器可处理片段的组件 | 影响长度、词项和成本 |
| Embedding | 把文本映射成数字向量的表示 | 让不同措辞的近似语义靠近 |
| Inverted index | “词项 → 出现在哪些文档”的倒排结构 | 支撑精确词法搜索 |
| Vector index | “向量 → 附近向量”的近邻结构 | 支撑语义搜索 |
| Retriever | 负责从索引取回候选的模块 | 决定候选覆盖率 |
| Reranker | 重新细看 query 与候选文本并排序的模块 | 提高前几名的精度 |
| Context | 本轮真正放入模型输入的材料 | 决定模型此刻能看到什么 |
| Generator | 根据上下文写出回答的模型 | 把证据变成自然语言 |

注意：**“相似”不是“正确”。** 一个向量距离很近的段落可能已经过期、没有权限，或只提到同一个词却不能支持数字。后续所有章节都在回答这个差距。

## 推荐阅读顺序

### 第一段：先把一条固定 RAG 跑通

1. [[rag/01-rag-architecture|RAG 的完整架构与数据契约]]：看离线/在线两条路径和最小记录结构。
2. [[rag/02-ingestion-chunking-metadata|文档摄取、分块与 metadata]]：理解“搜什么单元”在索引前就被决定了。
3. [[rag/03-embeddings-vector-search|Embedding、向量相似度与 ANN]]：理解语义检索的数学和向量库的职责。
4. [[rag/04-lexical-retrieval-and-bm25|倒排索引与 BM25]]：从词频、稀有度和文档长度推导精确搜索。

读完这四篇，你能实现一个可解释的 baseline：

> 解析文档 → 结构化 chunk → metadata 过滤 → BM25 或向量 top-k → 把候选放入 prompt → 引用来源。

### 第二段：让召回更稳、上下文更完整

5. [[rag/05-hybrid-search-reranking|Hybrid Search、Reranker 与查询改写]]：组合词法和语义信号，再用更强的二阶段排序。
6. [[rag/06-context-assembly-and-advanced-retrievers|上下文组装与高级检索器]]：处理 parent-child、small-to-big、sentence-window、表格和冲突证据。

### 第三段：让系统知道何时继续查

7. [[rag/07-adaptive-rag-self-rag-crag|自适应 RAG：Self-RAG 与 CRAG]]：判断“要不要检索”和“检索结果够不够好”。
8. [[rag/08-agentic-rag|Agentic RAG：让 Agent 规划检索路径]]：把检索变成有状态、可恢复、受预算约束的动作循环。

### 第四段：决定它能不能上线

9. [[rag/09-evaluation-production|评测、观测、安全与生产取舍]]：分别衡量召回、上下文、答案、延迟、成本和安全。
10. [[rag/10-minimal-implementation|最小可运行实现与升级路线]]：用简单 Python 伪代码把前面的接口串起来。
11. [[rag/99-sources|论文、官方文档与延伸阅读]]：按问题而不是按产品名查资料。

## 一张“先做什么”的决策表

| 现象 | 先检查 | 再考虑 |
|---|---|---|
| 错误码、版本号、员工 ID 找不到 | tokenizer、字段、BM25 分析器 | 字段 boost、短语查询、混合检索 |
| 用户换一种说法就找不到 | embedding 模型和 query 改写 | Multi-Query、RAG-Fusion、HyDE |
| 找到了相关段落但答案缺上下文 | chunk 边界和 metadata | Parent-Child、Sentence-Window |
| 正确文档根本没被取回 | 过滤条件、索引新鲜度、召回 top-k | 扩大候选、分解查询、换来源 |
| 前几名顺序不稳定 | 分数尺度和重复候选 | RRF、Reranker |
| 答案看似流畅却无依据 | 引用绑定和缺口策略 | 结构化输出、拒答/人工复核 |
| 每个问题都要多轮搜索 | 是否真的有不确定性 | Agentic RAG；先不要默认加 Agent |

> [!warning] 本教程的边界
> 向量数据库、Embedding 模型和重排服务更新很快。教程会解释稳定的算法和选型维度，并链接官方文档；具体 SDK（Software Development Kit，软件开发工具包）参数、模型版本和价格应在部署前重新核对。产品名不是架构本身。
