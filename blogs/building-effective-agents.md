# Building Effective Agents

来源：Anthropic Engineering《[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)》，发布于 2024-12-19。

## 一句话核心

构建有效 AI Agent 的关键不是堆叠复杂框架，而是从最简单、可评估的 LLM 调用开始，在确实能提升结果时，再逐步引入检索、工具、记忆、工作流和自主 Agent。

## 文章主张

Anthropic 的经验是：**生产中最成功的 Agent 系统往往采用简单、可组合的模式，而不是复杂框架或过度抽象**。复杂性本身不是价值。每多一层 Agent 化设计，通常都会增加延迟、成本、调试难度和错误累积风险，因此只有当它能带来可测量的任务表现提升时才值得引入。

文章把广义的 Agentic System 分成两类：

- **Workflow（工作流）**：LLM 和工具沿着预先写好的代码路径运行，控制流主要由工程系统决定。
- **Agent（自主 Agent）**：LLM 根据环境反馈动态决定步骤、工具使用和后续策略，控制流更多由模型在运行时决定。

这一区分很重要：很多产品真正需要的是可预测的工作流，而不是完全开放的自主 Agent。

## 决策原则

构建时应按复杂度阶梯推进：

1. 先尝试单次 LLM 调用，用好提示词、上下文示例和输出格式。
2. 如果单次调用不够，再加入检索、工具或记忆，形成增强型 LLM。
3. 如果任务可以拆成稳定步骤，用工作流。
4. 如果步骤无法预先确定，且需要模型长期根据反馈行动，再考虑自主 Agent。

判断是否该升级复杂度时，看三个问题：

- 更复杂的结构是否在评估中显著提升质量？
- 增加的延迟、成本和维护难度是否可以接受？
- 是否有足够明确的成功标准、反馈信号和人工监督点？

## 框架的使用态度

框架可以帮助快速启动，例如简化模型调用、工具定义、输出解析和链式调用。但框架也可能带来两个问题：

- 抽象层遮住真实的 prompt、模型响应和工具调用，使调试变困难。
- 框架让开发者更容易过早采用复杂结构。

文章的建议是：尽量先直接使用 LLM API 实现简单模式；如果使用框架，也要理解底层执行逻辑。生产系统里，透明性和可调试性通常比炫目的抽象更重要。

## 基础模块：增强型 LLM

增强型 LLM 是所有 Agentic System 的基本单元：一个 LLM 具备检索、工具调用和记忆能力。模型可以自行生成查询、选择工具、决定保留哪些信息。

![增强型 LLM](https://www-cdn.anthropic.com/images/4zrzovbb/website/d3083d3f40bb2b6f477901cc9a240738d3dd1371-2401x1000.png)

实现重点不是把所有能力都接上，而是：

- 能力要针对具体用例裁剪。
- 工具和检索接口要清晰、稳定、易于模型理解。
- 工具说明要像给新同事写文档一样明确，包含用途、参数、边界和示例。

## 五种常见工作流模式

### 1. Prompt Chaining：提示词链

把任务拆成固定顺序的多个 LLM 调用，前一步输出作为后一步输入，中间可以加入程序化检查点。

![提示词链工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/7418719e3dab222dccb379b8879e1dc08ad34c78-2401x1000.png)

适合：任务能清晰拆成固定子步骤，并且希望通过“让每次调用处理更小问题”来提升准确率。

典型例子：先生成营销文案，再翻译；先写大纲并检查，再生成完整文档。

### 2. Routing：路由

先分类输入，再分发到更适合的下游 prompt、模型或工具链。

![路由工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/5c0c0e9fe4def0b584c04d37849941da55e5e71c-2401x1000.png)

适合：输入类型差异明显，且每类输入需要不同处理方式。路由能让系统分离关注点，避免一个通用 prompt 同时兼顾太多场景。

典型例子：客服中把普通问题、退款、技术支持分到不同流程；把简单问题交给小模型，把复杂问题交给更强模型。

### 3. Parallelization：并行化

让多个 LLM 调用同时处理任务，再用程序聚合结果。它有两种主要形式：

- **Sectioning**：把任务拆成独立子任务并行处理。
- **Voting**：对同一任务运行多次或多视角判断，用投票或阈值提升置信度。

![并行化工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/406bb032ca007fd1624f261af717d70e6ca86286-2401x1000.png)

适合：子任务彼此独立，或者需要多个视角降低漏判风险。

典型例子：一个模型负责回答，另一个模型负责安全检查；多个模型或 prompt 分别审查代码安全、内容违规、评估指标等。

### 4. Orchestrator-Workers：编排者-工作者

由一个中心 LLM 根据输入动态拆分任务，分派给多个 worker LLM，再汇总结果。

![编排者-工作者工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/8985fc683fae4780fb34eab1365ab78c7e51bc8e-2401x1000.png)

它和并行化看起来相似，但关键区别是：并行化的子任务通常预先定义；编排者-工作者的子任务由模型在运行时决定。

适合：无法提前预测需要哪些子任务的复杂问题。

典型例子：一次代码修改可能涉及未知数量的文件；复杂搜索任务需要从多个来源收集和筛选信息。

### 5. Evaluator-Optimizer：评估者-优化者

一个 LLM 生成结果，另一个 LLM 按标准评估并给反馈，生成器再迭代改进，直到通过或达到停止条件。

![评估者-优化者工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/14f51e6406ccb29e695da48b17017e899a6119c7-2401x1000.png)

适合：评价标准清晰，且迭代反馈确实能提升结果质量。

两个适配信号：

- 人类给出明确反馈后，模型输出能明显变好。
- LLM 自身也能给出类似的有效反馈。

典型例子：文学翻译、复杂研究、多轮搜索与分析、对语气或细节要求较高的内容创作。

## 自主 Agent

自主 Agent 适合更开放的问题：步骤数量无法预先确定，路径无法硬编码，模型需要根据环境反馈连续决策。

![自主 Agent](https://www-cdn.anthropic.com/images/4zrzovbb/website/58d9f10c985c4eb5d53798dea315f7bb5ab6249e-2401x1000.png)

典型执行循环是：

1. 人类给出任务，必要时与 Agent 澄清需求。
2. Agent 制定计划并调用工具。
3. 环境返回真实反馈，例如搜索结果、执行结果、测试结果。
4. Agent 根据反馈继续行动、请求人工判断或停止。
5. 系统设置检查点、最大迭代次数、沙箱和护栏，控制风险。

![编码 Agent 高层流程](https://www-cdn.anthropic.com/images/4zrzovbb/website/4b9a1f4eb63d5962a6e1746ac26bbc857cf3474f-2400x1666.png)

自主 Agent 的价值来自灵活性，但风险也更高：成本更高，延迟更长，错误可能在多轮执行中累积。因此它更适合可信环境中的复杂任务，而不是所有用户请求都默认交给 Agent。

## 文章强调的三个工程原则

1. **保持简单**：先让简单方案跑通并可评估，再逐步增加复杂度。
2. **保持透明**：明确展示 Agent 的计划、步骤和中间状态，方便人类理解与干预。
3. **认真设计 ACI（Agent-Computer Interface）**：像设计人机界面一样设计模型使用工具的界面，包括工具名称、参数、说明、错误边界和测试用例。

## 工具提示工程

文章特别强调：工具定义本身也需要 prompt engineering。模型能不能可靠用工具，很大程度取决于工具接口是否符合模型习惯。

好的工具设计包括：

- 给模型足够空间先思考，再输出复杂结构。
- 使用接近自然文本或常见代码形式的格式，避免模型不擅长的额外负担。
- 避免要求模型精确计算行号、转义大量 JSON 字符串、维护复杂格式细节。
- 参数名和描述要直观，像写给初级工程师的 docstring。
- 为工具说明提供示例、边界条件和与相似工具的区别。
- 用大量真实任务测试模型如何误用工具，再修改工具接口来减少错误。
- 通过接口设计让错误更难发生，例如把易错的相对路径改成明确的绝对路径。

## 适合 Agent 的应用特征

文章提到两个特别有价值的领域：客服和编码。

它们共同具备这些条件：

- 既需要对话，也需要实际行动。
- 能接入有意义的外部工具和数据。
- 成功标准相对清晰。
- 环境能提供反馈信号。
- 可以放入人工监督和审查。

客服场景中，Agent 可以读取客户信息、订单历史、知识库，并执行退款、更新工单等动作。编码场景中，Agent 可以依赖测试、构建结果和代码审查反馈持续迭代。

## 选择模式的速查表

| 问题                         | 优先考虑                 |
| -------------------------- | -------------------- |
| 单次回答能否通过更好 prompt、示例和检索解决？ | 单次调用或增强型 LLM         |
| 任务是否能拆成固定顺序？               | Prompt Chaining      |
| 输入是否有明显类别，且类别处理方式不同？       | Routing              |
| 子任务是否独立，或需要多个视角投票？         | Parallelization      |
| 子任务数量和类型是否运行时才知道？          | Orchestrator-Workers |
| 是否有清晰评价标准，且反馈能改进结果？        | Evaluator-Optimizer  |
| 步骤无法预设，必须长期根据环境反馈行动？       | 自主 Agent             |

## 最重要的落地提醒

不要问“怎么做一个 Agent”，而要问“这个任务需要多少自主性”。

很多场景只需要一个增强型 LLM 或确定性工作流。真正的 Agent 应该留给那些开放、动态、可反馈、可监督，并且简单方案已经被评估证明不够的任务。
