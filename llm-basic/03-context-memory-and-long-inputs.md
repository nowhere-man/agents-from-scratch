# 上下文窗口、记忆与长输入

> [!important] 一句话核心
> 上下文窗口（context window）是一次调用的有限工作区，不是可靠长期记忆；更大的窗口提高可放入的信息量，却不保证模型能定位、关联、遵循或忠实使用每一段信息。

## 四种常被混淆的“记忆”

| 名称 | 存在位置 | 能做什么 | 不能保证什么 |
|---|---|---|---|
| **模型参数知识** | 训练后的权重 | 提供通用语言和世界模式 | 最新、私有、可引用或可删除的事实查询 |
| **当前 context** | 本次 API 输入/会话 | 让模型处理当前指令、材料、历史和工具结果 | 跨调用持久、均匀关注、自动优先可信来源 |
| **应用 state** | 数据库、文件、任务存储 | 保存任务 ID、已执行动作、授权、检查点和真实结果 | 自动被模型理解；必须显式选择并注入 |
| **retrieval memory** | 索引、知识库、日志 | 按当前问题取回相关证据 | 检索完整、来源正确或语义判断正确 |

Agent 需要把这四者分别设计。把聊天历史不断追加到 context，既不等于持久状态，也不是可控记忆策略。

## 上下文示例如何临时塑形行为

**In-context learning / few-shot** 指模型根据当前 context 中的示例、格式、反例和任务描述，临时推断这次调用应采用的映射或输出模式。它不修改模型参数，也不会在下一次调用中自动保留；它是运行时行为塑形，不是训练、长期记忆或业务规则。

对 Agent 而言，示例适合说明类别边界、字段语义、边界输入和输出格式。它们也会消耗预算、受位置和冲突影响，并可能把错误偏好或不可信指令带入任务。示例必须有来源，和稳定规则、用户数据明确分隔；关键权限、事实和确定性校验不能只靠 few-shot 维持。

## 长 context 的真实限制

窗口大小只是可接收 token 的硬上限。实际任务质量还受以下因素影响：

- **注意力与位置**：关键信息位于开头、中间、末尾或重复出现时，命中率可能不同；“Lost in the Middle”是长输入中常见的退化现象，而非所有模型、所有长度都相同的定律。
- **干扰与冲突**：无关材料、重复版本、相似实体和嵌入式指令会让选择相关证据更难。
- **输出预算**：输入占满窗口会挤压最终答案、工具调用与错误恢复所需空间。
- **计算与产品限制**：长序列通常增加首 token 延迟、成本和并发压力；不同模型/API 的缓存、计费与最大输出规则不同。

## KV cache：为什么生成和输入的成本不同

自回归生成时，每一层的历史 key/value 可以缓存。首次读取 prompt 的过程常称为 prefill；随后生成每个 token 时可复用历史 cache，而不必完整重算前文。

这解释两个工程现象：长 prompt 主要伤害首 token 延迟和内存；长输出仍是逐 token 串行过程。缓存命中、批处理、模型架构与服务实现会改变实际表现，不能仅凭 token 数估算。

### GQA / MQA 的意义

传统 MHA 为每个 query head 保存独立的 key/value head。**MQA** 共享更少的 KV head；**GQA** 让多个 query head 分组共享 KV head，在表达能力与 KV cache 内存/带宽之间折中。它们主要改善推理服务效率，不会自动解决长材料的语义遗漏。

## 上下文工程的正确顺序

任务与成功标准 → 选择允许证据 → 检索、过滤、去重、保留来源 → 组织最小必要 context → 模型做语义判断 → 验证、执行与持久化真实状态 → 记录失败并评估。

**先放进更多材料**不是默认策略。优先定义问题、筛选证据和未知值；在确实需要全局关系、检索不易覆盖或材料短小干净时，长 context 才是合理工具。

## 对 Agent 的设计模式

| 场景 | 建议 | 避免 |
|---|---|---|
| 需要跨轮完成任务 | 数据库保存结构化 state、决策和真实 tool 结果；按当前步骤取回 | 把自然语言总结当作唯一真相 |
| 需要基于资料回答 | retrieval 返回最少相关证据及来源 ID；要求引用或未知 | 只说“仔细读完整资料库” |
| 需要处理长文档 | 分段、索引、局部抽取，再在有出处的中间结果上聚合 | 一次全量塞入且无定位 eval |
| 需要压缩历史 | 保留不可丢失事实/授权/未完成事项，摘要可被原始记录回查 | 把摘要当作不可错误的记忆 |
| 需要抗 prompt injection | 明确区分规则与数据；检索内容不拥有指令权限 | 让网页、邮件或文件内容直接改变工具权限 |

## 最小长输入 eval

对每类真实输入创建可复现样本，并让关键事实分别处于开头、中间、结尾、相似干扰段和冲突段。至少量化：证据召回、引用/定位正确率、最终任务正确率、首 token 延迟、总成本、以及 context 满载时的失败行为。

> [!tip] 先测试“是否找到”，再测试“是否推理对”
> 如果模型根本没有选到正确段落，继续调推理 prompt 无法解决根因；如果证据已正确提供但结论仍错，才研究模型、任务分解或验证机制。

## 常见误解

- **“模型知道聊天历史。”** 只有被服务端保留并再次传入或由状态机制恢复的内容才可能被当前调用使用。
- **“参数记忆可以替代知识库。”** 参数中的统计知识难以精确检索、更新、审计或限定来源。
- **“把完整材料放进去比 RAG 更可靠。”** 这取决于任务；长 context 仍会受到位置、干扰、成本和输入质量影响。
- **“KV cache 是应用级长期缓存。”** KV cache 属于某次推理的内部计算优化，不是可靠业务 state。
