# 训练、对齐与模型行为

> [!important] 一句话核心
> 预训练赋予模型对语言和数据分布的统计能力；后训练让它更像可交互的助手。对齐改变模型的输出倾向，不会把它变成可证明诚实、完全安全或永久服从的规则引擎。

## 三层训练分别改变什么

| 阶段 | 优化目标的直觉 | 对开发者可见的结果 | 不应推断的结论 |
|---|---|---|---|
| **Pretraining** | 在大量序列上预测后续 token | 语言能力、知识模式、代码/图文关联和一些通用技能 | 模型拥有可追溯、实时、无冲突的事实数据库 |
| **SFT（监督微调）** | 模仿高质量输入—输出示例 | 更会遵循指令、对话、调用工具和输出目标格式 | 每条指令都会稳定压过训练先验和冲突上下文 |
| **偏好/强化对齐** | 偏向人类或自动评分更喜欢的回答 | 更有帮助、更安全、风格更一致，部分任务更愿意推理或自检 | 输出礼貌、拒绝或自信等于结论真实或风险已消除 |

这三个阶段不是严格只有一次的流水线。现代模型常混合数据、任务、偏好和可验证奖励反复训练；但这个三层框架足以解释大量 Agent 行为。

## 为什么“像助手”仍是概率行为

后训练会提高“遵守系统规则、先澄清、调用工具、承认未知”等行为的概率，却无法替代运行时机制：输入会有歧义和冲突，工具描述会变化，长 context 会稀释信号，攻击者也会把指令伪装在数据里。

因此应把 prompt 看作运行时任务契约的一部分，把 schema、权限、状态与验证放在模型外。见 [[prompt-engineering/01-task-contract|任务契约]]。

## 偏好优化方法的技术地图

这些方法解决的是“如何把偏好或可验证反馈转化为模型更新”，不是 Agent 在运行时必须选择的工具。对应用开发者，关键是理解模型行为可能受什么训练信号影响、何时应要求供应商或微调团队提供 eval 证据。

| 方法 | 反馈形态与核心直觉 | 常见优势 | 主要边界 |
|---|---|---|---|
| **RLHF / PPO** | 先以人类偏好训练 Reward Model，再用强化学习优化策略 | 可优化复杂、连续的偏好目标；是经典范式 | 需要 reward 设计与稳定 RL 训练；Reward Model 可被钻空子 |
| **DPO** | 直接用 chosen/rejected 偏好对调整相对概率，不显式训练独立 Reward Model | 管线较直接，适合高质量偏好对 | 质量和覆盖面仍受偏好数据限制；不是“无需评估” |
| **GRPO** | 用同组候选的相对奖励/优势更新，常用于有可验证回报的推理任务 | 可减少部分价值模型依赖，适配可检查结果 | 需要可靠奖励；奖励错会把错误模式放大 |
| **KTO** | 适配二元好/坏反馈，而非每样本严格偏好对 | 可利用较弱、较易收集的反馈 | 二元标签的信息量、偏差和覆盖决定上限 |
| **SimPO** | 直接以偏好差距构造简化目标 | 训练形式较简洁 | 并不自动意味着更适合所有数据、任务或安全要求 |

> [!note] “2026 默认选择”不是稳定事实
> 论文提出的方法、开源模型常用配方和某家实验室的生产栈不是一回事。应用侧应关注目标模型在自己的任务、风险约束和版本上的 eval，而不是把某个缩写当作质量保证。

## 对 Agent 开发的影响

### 指令遵循是能力，不是授权系统

模型可能理解“先确认后退款”，也可能输出貌似合法的退款参数；是否能退款必须由服务器端身份、金额、策略与用户确认决定。训练出的安全倾向不能替代权限检查。

### 拒绝不是完整的安全控制

拒绝可能遗漏危险请求、误伤正当请求，或随措辞、语言与模型升级改变。敏感领域要有独立的 policy、分类/审查、审计和人工升级路径。

### 训练分布会影响接口习惯

模型通常更擅长常见、清晰、可验证的工具接口和数据格式。工具设计应减少转义、隐含状态、模糊参数和需要精确心算的字段；失败样本比“更强的角色设定”更能指导改进。

### 后训练变化必须像依赖升级一样评估

同一模型家族的新快照可能改变指令、推理、拒绝、格式和 tool-use 行为。固定版本、保留 baseline、分离模型变更与 prompt 变更，并为回滚留路径。见 [[prompt-engineering/15-production-lifecycle|Prompt 的生产生命周期]]。

## 常见误解

- **“SFT 教会了模型事实。”** SFT 更多改变任务接口和输出风格；缺失或过期事实仍需 retrieval/tool。
- **“RLHF 让模型不会幻觉。”** 偏好优化可改善表达和承认不确定性的倾向，但不能让生成结果天然有证据。
- **“DPO 没有 Reward Model，所以不需要 reward 思考。”** 偏好对本身就是隐含奖励信号，质量、偏差与目标定义仍决定结果。
- **“推理训练让模型可以代替验证器。”** 可验证任务的最终约束仍应由代码、测试、数据库或独立证据承担。

## 最小检查表

- [ ] 模型行为要求被写成可测的任务和风险指标，而非“更聪明/更安全”。
- [ ] 对工具权限、业务规则、事实来源和数据访问没有依赖模型偏好来强制。
- [ ] 对模型或微调版本的迁移运行了相同 eval，并保存原始输出。
- [ ] 高风险失败同时覆盖“该拒绝却未拒绝”和“该完成却误拒绝”。
