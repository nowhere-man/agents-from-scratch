# 文本模型的能力边界与验证

> [!important] 一句话核心
> 文本 LLM 可以高质量地理解、归纳、规划和生成，却不能对事实、计算、格式语义、工具执行或自身置信度作天然保证；可靠 Agent 必须把每类失败交给能真正约束它的系统层。

## 模型擅长什么，在哪些前提下

| 能力 | 适合的任务 | 仍须保留的边界 |
|---|---|---|
| 语义理解与分类 | 意图识别、非结构化文本路由、软规则判断 | 类别定义、边界样例和未知类别必须清晰 |
| 归纳与生成 | 摘要、解释、草稿、候选方案、自然语言转换 | 不能把覆盖率、事实性或引用正确性默认为已满足 |
| 受约束抽取 | 从提供材料抽取字段、将描述映射到 schema 语义 | 模糊/缺失字段必须可返回 unknown，并用解析器验证 |
| 规划与工具选择 | 在明确工具、真实反馈和停止条件下决定下一步 | 计划不是执行；权限、参数与结果必须由系统核验 |
| 多步推理 | 有足够上下文、可中途检查或有可验证结果的任务 | 中间步骤流畅不等于结论对；复杂度会累积错误 |

## 提示敏感性、指令边界与不可信内容

同一模型的表现会随任务表述、语言、示例、context 顺序、工具描述、采样参数和模型快照变化。能力不是平滑、可由单个 demo 外推的常数；生产决策应比较代表性样本上的成功、边界和失败，而不是只优化一条 prompt。

消息角色可建立职责层次：稳定的系统/开发者规则定义安全和工具边界，当前用户请求定义目标，网页、文件、检索结果、tool 返回、OCR 文字和 ASR 转写提供证据数据。具体 API 的角色名称和优先级不同，但不可信内容不应拥有改变规则、扩展授权或触发写操作的能力。

> [!warning] 边界标记不是权限控制
> 用标签把文档包为“数据”能降低模型混淆，却不能让 prompt injection 消失。服务端仍须限制可用 tool、验证参数和授权，并把模型输出当作请求而非执行结果。详见 [[prompt-engineering/10-context-and-instruction-architecture|上下文与指令架构]]。

## 幻觉不是单一故障

“幻觉”通常指无依据、错误或虚构的输出，但根因不同，修法也不同：

| 症状 | 典型根因 | 正确机制 |
|---|---|---|
| 编造最新/私有事实 | 模型没有可用证据 | retrieval、数据库或实时 tool；缺失时返回未知 |
| 忽略已提供材料 | context 过长、噪声、位置或指令边界差 | 筛选、重排、抽取、引用与目标任务 eval |
| 算错、排序错、漏去重 | 概率生成承担了确定性工作 | code、SQL、计算器、校验器 |
| 合法 JSON 中有错误事实 | 结构约束与语义事实混淆 | schema + 证据绑定 + 字段级验证 |
| 声称 tool 已执行 | 模型预测了完成叙述 | 只以 tool 返回的真实状态为准 |

## 推理、解释与置信度

模型能够生成有用的分步解释、假设和计划，也常能在数学、代码和分析任务上受益于拆解；但输出的解释不是经过审计的内部证明。不要要求或依赖私有思维过程。

需要可检查性时，要求或保存**外部可验证产物**：引用段落、假设列表、计算结果、测试输出、tool ID、字段来源、阶段性 schema。对于可验证领域，让程序验证结论；对于开放判断，用独立证据、第二视角或人工量表评估。

模型给出的置信字段也是生成内容，不应当作经过概率校准的风险分数，除非你已针对目标模型、任务和分布做过校准验证。

## Tool calling 与 Structured Outputs 的边界

模型输出或 tool 请求 → 检查结构是否合法 → 检查参数、权限、证据与业务规则 → 执行受控 tool → 读取并持久化真实结果 → 由模型解释下一步。

- **Structured Outputs / JSON Schema** 约束返回形状，不能证明每个字段真实、完整或业务可接受。
- **Tool calling** 让模型提出操作和参数，不能授予权限，也不能替代 API 成功响应。
- **代码验证** 适合精确规则；**模型验证**只保留给无法程序化、但仍需语义判断的部分。

详见 [[prompt-engineering/11-structured-output-and-determinism|结构化输出与确定性保证]]。

## 一个实用的验证分层

1. **输入层**：验证身份、权限、文件格式、大小、来源与不可信数据边界。
2. **证据层**：检索结果带来源、版本、时间和冲突信息；材料不足时明确 unknown。
3. **模型层**：让模型做语义映射、摘要、比较或规划；约束输出语义与停止条件。
4. **确定性层**：解析、类型、枚举、计算、权限、数据库写入由代码验证。
5. **执行层**：受权 tool 执行；只使用真实响应更新 state。
6. **监督层**：高影响、低证据或低置信的结果进入人工审核；记录反馈进入 eval 集。

## 最小 eval 不应漏掉什么

- 典型成功样本和边界样本，而不只是一条漂亮 demo。
- 缺失、冲突、过期、无关和恶意/注入式上下文。
- schema 合法但语义错误的输出。
- tool 超时、权限拒绝、部分成功、重复调用与不可逆动作。
- 模型、prompt、schema、tool、context 或参数改动后的同条件比较。

## 常见误解

- **“引用存在就证明答案正确。”** 引用可能无关、被误读或无法支持结论；需要评估引用与断言的对应关系。
- **“第二次让模型自检就可靠。”** 同一模型可能重复同一偏差；确定性错误应直接用程序检查，事实错误需要独立证据。
- **“多 Agent 一定更可靠。”** 多轮调用也会传播相同 context 错误，并增加成本、延迟和调试难度；先建立单步 baseline。
- **“格式通过率高说明系统可靠。”** 格式、事实、业务正确性和安全性是不同指标。
