# Tech Notes

把技术笔记写成一堂可跟随的**课**，而不是术语目录。文章结构由技术本身和读者的认知顺序决定，不套固定模板。

实际创建或编辑文章时，必须同时读取并遵守 `obsidian-markdown` skill；本文只规定教学与内容组织，Obsidian frontmatter、wikilink、callout、公式和 Mermaid 等格式以该 skill 为准。

## 工作流程

### 1. 确定学习终点与章节边界

先从用户要求、相邻笔记和现有正文中确认：

- 读者是谁，已知什么；默认按第一次系统学习该技术的初学者处理。
- 读完后应能解释或完成什么，而不是应记住哪些名词。
- 本文负责讲到哪里，哪些内容由前文提供，哪些留给后文。
- 是新写、重写还是局部补充；编辑现有文章时先读完整文章与相邻章节，不局部盲改。

内容超出本文边界时只建立必要接口并指向后文，不偷讲，也不留下无法继续阅读的悬空术语。

完成条件：能用一句话说明“读者从什么起点，经由什么核心变化，最终理解什么”，且每个候选主题都属于本文职责。

### 2. 找到贯穿全文的主线

选择一个能自然暴露核心问题的具体场景、输入或对象，让它从开头走到结果。主线可以是一次请求、一段数据、一个报错、一条消息或一个状态变化；不要为了统一形式强行使用同类例子。

先画出因果链：

```text
起点
-> 遇到什么问题
-> 为什么已有办法不够
-> 引入什么机制
-> 数据或状态怎样变化
-> 得到什么结果
-> 下一问题为何自然出现
```

后续概念必须挂到这条链上。没有位置的概念应删除、后移或另立文章，不能作为“顺便补充”并列堆入正文。

完成条件：能够沿同一个对象口头复述全文；任一主要小节都能回答它承接了什么、又为下一节准备了什么。

### 3. 按认知依赖展开

先建立宏观地图，再放大局部：

1. 先说明技术要解决的问题、意义、输入、输出和总体数据流。
2. 再解释核心模块如何协作，以及每个模块在主线中的职责。
3. 最后进入公式、参数、变体、优化、边界和实现细节。

这只是依赖原则，不是文章模板。章节数量、标题和顺序由主题决定。不要因为某个术语重要就提前讲；读者尚不知道它为何出现时，定义再准确也只是孤立知识点。

每次引入概念时，按当前理解障碍选择需要回答的问题：

- 它为了解决什么具体问题？
- 它接收什么，产出什么，改变了什么信息或状态？
- 它怎样与前后模块配合？
- 为什么这样设计；没有它或换成朴素方案会怎样？
- 它是核心机制、常见替换、可选优化，还是实现细节？

并非每个小节都机械回答全部问题；以消除读者当前障碍为准。

完成条件：正文不存在先使用后解释的关键概念，也不存在只能靠读者自行猜测的章节跳跃。

### 4. 建立术语阶梯

术语第一次承担解释任务时就近说明。一个术语的最低合格解释包括：

- 人话含义；
- 在当前主线中指什么；
- 容易与什么混淆；
- 必要时给一个最小例子。

用新术语解释旧术语前，先确认新术语已经建立。若连续出现多个先修术语，先增加简短的“术语理解”作为台阶，再继续机制说明。术语解释应回到主线发挥作用，不单独形成词典式章节。

抽象词尤其要落地，例如“特征”“状态”“激活”“上下文”“容量”“路由”“投影”“归一化”。不要默认初学者理解业内习惯用法。

完成条件：从头阅读时，每个必要术语都能仅凭此前正文理解；全文检索不到未定义却承担关键推理的术语。

### 5. 讲透重点机制

对决定文章学习目标的重点概念，至少完成一次闭环：

```text
问题直觉
-> 宏观作用
-> 输入与输出
-> 一次具体数据流
-> 内部机制或公式
-> 与相邻模块的配合
-> 缺失后果、边界或常见误解
```

先用具体例子追踪一个位置、对象或状态，再推广到整体。例子只能帮助形成直觉，不能把模型学习到的行为说成设计者预设的固定规则。

公式必须紧接意义解释：

- 每个符号在当前场景中是什么；
- 计算分几步发生；
- 每一步改变了什么；
- 公式输出在后续哪里使用。

不得只写“公式如下”或把矩阵运算本身当成解释。技术上需要限定时，明确“直觉类比”与“精确定义”的边界。

完成条件：读者能够不用背原句，沿例子解释机制为何存在、如何运行，以及结果流向哪里。

### 6. 串联变体与优化

介绍多个现代技术、方案或优化时，先闭合基础主干，再从主干暴露出的真实问题引出它们，例如稳定性、位置、容量、缓存、延迟或长输入成本。

每项技术都要标明：

- 修改主干中的哪个部件；
- 解决哪个已经出现的问题；
- 保持什么不变；
- 引入什么代价；
- 是必要结构、常见选择还是实现优化。

禁止以“术语名 + 一段定义”的同级列表代替叙事。表格可以在主线讲完后用于回顾，不能承担首次教学。

完成条件：删除任何一个变体小节时，能明确指出它原本解决的上游问题；读者不会误以为所有技术都是固定配方。

### 7. 做初学者通读审计

从头到尾模拟第一次阅读，不依赖作者脑中的隐含知识。逐段检查：

- 本段为什么此时出现？
- 代词和“这个结果”“当前状态”等指向是否明确？
- 输入、输出、维度、阶段和主体是否说清？
- 训练与使用、模型输出与后处理、数学函数与所在层是否混淆？
- 同一术语是否保持同一含义？
- 是否有重复解释、旁支知识、突然出现的缩写或没收尾的例子？

发现跳跃时补的是缺失的因果桥，不是再增加一个独立知识点。发现篇幅长时优先删旁支和重复，不删主线所需解释。

完成条件：每段都能指出前因和后果；全文没有孤立知识点、未解释关键术语、范围越界或失去后续用途的内容。

### 8. 验证笔记

按照 `obsidian-markdown` skill 验证渲染与内部链接，并运行当前环境可用的 Markdown、frontmatter、公式、Mermaid、控制字符和 whitespace 检查。编辑系列文章时还要检查上一章、下一章和导读是否一致。

完成条件：格式检查通过；无法自动验证的项目明确说明；内容审计满足前述每一步的完成条件。

## 硬性约束

- 严禁独立知识点罗列；所有必要概念必须服务于可复述的主线。
- 不套固定笔记框架；固定的是认知顺序与完成标准，不是标题模板。
- 不用尚未解释的术语解释当前概念。
- 不把公式、图或表格当作解释本身。
- 不用“简单来说”“显然”“顾名思义”跳过关键推理。
- 不把可选优化写成技术成立的必要条件。
- 不以篇幅短为由省略重点概念的输入、输出、作用和数据流。
- 不以篇幅长为由保留偏离主线的背景百科。
