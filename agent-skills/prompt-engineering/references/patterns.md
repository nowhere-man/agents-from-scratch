# Prompt Patterns

只读取并应用与当前任务直接相关的模式。

## Structured Output

需要程序解析时，按以下顺序选择：

1. API 原生 `structured output` 或 JSON Schema。
2. 已安装 SDK 的类型模型。
3. 只有前两者不可用时，才在 `prompt` 中声明字段、类型、必填项、允许值、空值策略和禁止额外文本。

同时定义缺失值和解析失败后的处理方式，例如允许 `null`、增加明确状态、只修复格式或返回错误。`schema` 无法表达“未知”但任务又禁止猜测时，停止起草并请用户选择表示方式；得到选择前不要交付草稿或发明默认值。不要把“请输出 JSON”当作校验。格式失败时只修复格式，不重写事实内容。

## Deterministic Post-processing

把能由程序可靠完成的工作移出 `prompt`：

- 用 `schema` 约束字段、类型、必填项、枚举和空值。
- 用代码完成解析、排序、去重、精确计数和业务规则校验。
- 用 `post-processing` 移除允许安全删除的前后缀、空白或包装标记。
- 用明确错误处理格式失败，不让模型悄悄返回近似结果。

模型负责语义理解和判断；程序负责确定性保证。只有程序无法表达的语义边界才留在 `prompt` 中。

## Few-shot

只有直接指令无法稳定表达判断边界、格式或风格时才添加示例。

- 从能表达规则的最少示例开始。
- 让示例覆盖真实变化和关键边界，不要堆叠同义样例。
- 所有示例保持相同标签和输出结构。
- 示例与实际任务冲突时，以明确约束为准。
- 动态选择示例只在已有样例库且相关性确实影响结果时使用。

## Multimodal

明确每种输入的用途以及需要观察的内容：图片关注主体、文字和空间关系；视频关注动作和时序；音频关注语音、语气和声音事件；文本提供事实和术语。

不要假定不可见细节。要求区分观察结果、合理推断和无法确定的内容。

## Task Decomposition 与 Prompt Chaining

只在单个 `prompt` 无法可靠完成复合任务时拆分：

- **Prompt chaining**：前一步输出是后一步必需输入，例如提取、生成、校验。
- **并行后汇总**：不同材料可独立处理，最后比较共同点、冲突和不确定项。
- **Prompt Routing**：多个互斥任务需要先分类，再调用对应 `prompt`。
- **失败恢复**：复合任务失败时改为“提取 → 生成 → 校验”，保留各步中间结果以定位问题。

为每一步声明输入、输出和完成条件。不要为了“模块化”拆分一个本可直接完成的任务。
