# Prompt Evaluation

用户要求量化优化、`A/B test`、版本管理或生产发布时使用本参考。

## 1. 定义成功标准

根据任务选择指标，不使用通用阈值：

- 分类或抽取：正确率、召回率、字段完整率。
- `structured output`：`schema` 通过率、解析失败率。
- 事实回答：依据覆盖率、无依据断言率。
- 生成任务：人工评分量表、硬约束通过率。
- 生产系统：延迟、token 成本、工具成功率和安全违规率。

先明确指标、计算方式和可接受标准，再开始优化。

## 2. 固定 Eval 条件

沿用核心流程已建立的代表性测试集和 `baseline`，并固定模型、工具、`sampling parameters` 和评分方式。保存原始输出，确保后续版本在相同条件下比较。

保存每个样例的输入、期望属性和评分方式。开放式任务不要强行使用字符串完全匹配或词语重叠作为质量分数；无法实际运行时，明确写为待验证假设。

完成条件：测试集、`baseline`、运行条件和评分方式均可复现。

## 3. 比较结果

沿用核心流程的单变量迭代：每轮根据失败样例提出一个可证伪假设，只改变一个主要变量，再比较目标指标和副作用；改善则保留，否则回滚。不要同时改变 `prompt`、模型和 `sampling parameters` 后归因于其中一项。

## 4. 处理随机性

输出具有随机性且一致性重要时，对相同样例重复运行，并报告分布或通过率。重复次数由任务风险和成本决定，不固定为通用数字。

## 5. 生产发布

只有用户确实在维护生产 `prompt system` 时才增加：

- 为 `prompt` 设置版本标识并保留上一稳定版本。
- 小流量或离线验证后再扩大范围。
- 监控与成功标准相同的指标。
- 指标恶化或解析失败增加时回滚。

## Eval 报告

保持报告可追溯：

```text
目标失败：{{要修复的问题}}
改动假设：{{为什么该改动可能有效}}
唯一改动：{{本轮变化}}
测试集：{{样例范围}}
Baseline：{{原指标}}
结果：{{新指标}}
结论：保留 / 回滚 / 证据不足
```

没有真实运行结果时，不填写虚构数字。
