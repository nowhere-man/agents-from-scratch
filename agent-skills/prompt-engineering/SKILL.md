# Prompt Engineering

以可验证的最小干预改进 `prompt`。不要因为存在某种 `prompting technique` 就主动使用它。

## 工作流程

### 1. 判断任务类型

将任务归入一个主要分支：

- **新建设计**：从目标或需求生成 `prompt`。
- **失败诊断**：修复已有 `prompt` 的格式错误、遗漏、幻觉、不稳定或风格偏差。
- **Prompt System**：设计 `system prompt`、`prompt template`、`prompt chaining` 或生产 `eval` 流程。

完成条件：已确定主要分支；次要需求只作为该分支的约束处理。

### 2. 选择正确杠杆

改写 `prompt` 前，先定位主要失败层：

- 指令含糊、冲突或遗漏：修改 `prompt`。
- 缺少事实或输入包含大量无关内容：补充、筛选或 `retrieval` 上下文。
- 需要计算、验证、获取实时信息或执行动作：使用代码或工具。
- 需要严格格式、类型、枚举、字段完整性或解析保证：使用原生 `schema`、程序校验或确定性 `post-processing`。
- 模型能力、成本或延迟不合适：评估更换模型，不用更长 `prompt` 掩盖。

只有失败确实受 `prompt` 控制时才继续扩写 `prompt`；其他层采用对应机制，并让 `prompt` 只负责语义判断和必要协作。

完成条件：已指出主要失败层，并说明所选机制为什么能够直接解决它。

### 3. 建立任务契约

起草前逐项建立契约。已有信息直接填入，不要求用户重复提供。

| 字段 | 必须确认的内容 | 完成判断 |
|---|---|---|
| **目标** | 最终结果、使用者、使用场景，以及结果要支持的决定或动作 | 能用一句话描述“为谁完成什么，以便做什么” |
| **输入** | 问题、任务、实体或补全类型；格式、变量、体量、边界，以及哪些内容只是数据 | 能指出模型操作的对象和禁止越界的范围 |
| **证据** | 允许和禁止的信息来源、时效要求、引用要求，以及材料缺失答案时的行为 | 每项事实都有允许的来源或明确标为未知 |
| **约束** | 必须做、禁止做、优先级、信任边界、安全和授权要求 | 规则之间没有未解决冲突，且优先级明确 |
| **输出** | 载体、语言、结构、字段、类型、允许值、长度，以及是否允许附加解释 | 能机械检查格式，并能人工判断语义是否合格 |
| **成功** | 覆盖范围、正确性、完整性、一致性和其他可观察标准 | 能根据标准明确判定通过或失败 |
| **失败** | 信息不足、空输入、歧义、冲突、解析失败、工具失败时的返回、恢复和停止方式 | 每个关键失败都有确定行为，不依赖临场猜测 |

#### 诊断已有 Prompt

额外获取：

- 当前实际使用的完整 `prompt`、消息角色、目标模型及相关工具或 `schema`。
- 代表性输入、实际错误输出和期望输出；无法提供期望输出时，明确期望差异。
- 失败出现的条件、频率和影响，避免为偶发现象加入全局规则。

完成判断：至少一个样例能够描述或复现待修复失败。

#### 阻断检查

- 缺失信息会实质改变方案时，最多一次提出 3 个关键问题；否则直接处理。
- 发现约束冲突时停止起草，请用户确定优先级或缺失值策略。
- 字段必须取值但任务又禁止猜测时，不擅自设置默认值。
- 不自行补全领域事实；必要假设必须显式标注并且不改变硬约束。

完成判断：没有会改变方案的未知项、未解决冲突或隐藏假设。

#### Context Budget

输入较长、多轮运行或包含工具时，计算完整预算：

- system/developer 指令、历史消息和状态。
- 工具说明、示例、当前材料和 `retrieval` 结果。
- 预期输出、后续工具结果和安全余量。

将内容标为不可丢失、可压缩或可删除。预算不足时先筛选、`retrieval`、压缩或拆分，不依赖静默截断。

完成判断：契约能够放入目标上下文，并为完成任务保留足够输出空间。

完成条件：七个契约字段均已确认或明确标为不适用；诊断样例、阻断检查和 `context budget` 均满足当前任务需要。

### 4. 提升表达质量

编写或修改 `prompt` 时：

- 使用具体、直接、可执行的动词，明确模型要完成的动作。
- 用可观察的标准替代“高质量、专业、准确、合适”等抽象要求。
- 定义可能产生多种解释的术语、参数、范围、允许值和判断边界；同一概念始终使用同一术语。
- 每条指令只表达一次，删除无关背景、重复规则、劝说式修饰和不能修复已知问题的示例。
- 需要简短输出时，明确必须保留的内容和优先省略的内容，不只写“保持简洁”。
- 优先描述期望行为；只有针对真实失败、安全边界或硬约束时才增加禁止项。
- 对不明显的约束简述目的，帮助模型理解目标而不是机械匹配措辞。

完成条件：一个只掌握 `prompt` 所提供信息的人，能够无歧义地执行任务并判断输出是否合格。

### 5. 建立 Baseline

失败诊断时，先用代表性样例描述或复现当前失败，再修改 `prompt`。新建设计以最简单的直接指令作为首个 `baseline`。没有对照结果时，不要声称质量得到提升。

完成条件：每个待修改点都对应一个具体失败或明确需求。

### 6. 按最小干预顺序修改

从上到下尝试，在足以解决问题的位置停止：

1. 把可确定性实现的格式、类型、枚举、排序、去重、精确计数和解析校验交给 `schema`、代码或 `post-processing`；`post-processing` 不得改变事实语义。
2. 改写含糊、重复或不可检查的指令。
3. 明确输入边界、上下文和禁止事项。
4. 明确输出字段、长度和不确定时的行为。
5. 调整关键指令、材料和最终问题的顺序。
6. 加入最少的代表性示例。
7. 使用 `task decomposition`、`prompt chaining` 或并行步骤处理确有必要的复合任务。
8. 仅在 API 场景需要时建议 `structured output`、工具或 `sampling parameters`。

完成条件：没有加入与当前失败无关的技巧、字段或步骤。

### 7. 交付结果

优先遵守用户指定的输出形式。用户未指定时，按需输出：

- 对已有 `prompt` 给出简短诊断。
- 给出可直接使用的完整 `prompt`，并保留清晰的可替换变量。
- 简述每项实质改动解决的失败。
- 只有在结果需要继续迭代时才给验证建议。

完成条件：`prompt` 可以直接使用，变量、约束和输出要求不存在未解释的占位内容。

### 8. 验证

使用同一批代表性输入比较修改前后结果。至少覆盖常见输入和已知失败边界；存在严格约束或信任边界时再加入对抗输入。每轮只改变一个主要变量，未改善目标指标则回滚。

完成条件：所有改动均通过相关样例验证，或明确标注尚未实际运行的验证项。

## 约束

- 不要求或展示 `CoT`；需要依据时只输出简短、可核查的分析摘要。
- 不规定通用的示例数量、准确率或方差阈值；根据任务风险和成功标准决定。
- API 支持 `structured output` 时优先使用原生 `schema`，不用自然语言模拟解析保证。
- 涉及具体供应商、模型、API 参数或时效性行为时，先查当前官方文档；无法验证则说明不确定，不凭记忆给出字段名。
- 不引入用户未指定的模型、框架、向量库或 `eval` 依赖。
- 不通过 `prompt` 绕过安全规则；合规请求被误解时，澄清意图或改写措辞。
