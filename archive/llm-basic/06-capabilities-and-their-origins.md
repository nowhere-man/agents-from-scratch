# 模型能力及其来源

> [!abstract] 本文回答什么
> 为什么“预测下一个 token”的训练会产生语言理解、知识问答、in-context learning、推理、代码和工具使用等能力？这些能力分别主要来自预训练、后训练、context 还是外部系统？

## 先建立一个因果模型

模型表现不是单一来源。可以简化为：

$$
\text{Behavior}=f(\text{architecture},\text{parameters},\text{context},\text{decoding},\text{tools})
$$

- **Architecture** 决定信息可以怎样表示、混合和生成。
- **Parameters** 压缩了预训练与后训练中的统计规律。
- **Context** 指定当前任务、证据、示例和约束。
- **Decoding / inference-time compute** 决定如何从分布产生一条或多条轨迹。
- **Tools** 提供参数之外的事实、计算、动作和反馈。

因此不能把某次回答的全部能力都归因于“模型参数很聪明”，也不能把 prompt 看作创造了参数中不存在的能力。

## 能力来源总表

| 表现出来的能力 | 主要来源 | 运行时还需要什么 |
|---|---|---|
| 语言生成与理解 | 大规模序列预训练、共享表示 | 清楚的 context |
| 参数知识 | 训练数据中的重复事实与关系 | 时效与来源验证 |
| In-Context Learning | 预训练中学到的条件化模式、attention | 指令与代表性示例 |
| 指令遵循 | SFT、偏好与安全后训练 | 消息边界、无冲突任务契约 |
| 推理与分解 | 模式学习、容量、推理训练、可验证奖励 | 适当计算预算与 verifier |
| 代码能力 | 代码数据、形式结构、执行反馈 | 测试、编译器和 sandbox |
| Tool Calling | 工具调用示范、schema 和反馈 | 真实 tool runtime 与权限 |
| 结构化输出 | 格式示范、约束解码 | parser 与业务校验 |
| 自我检查 | 后训练、自评示范、多次采样 | 独立证据或验证器 |

## 1. 为什么 Next-Token Prediction 能学到语言结构

要持续降低：

$$
-\log p_\theta(t_i\mid t_{<i})
$$

模型必须利用能预测后续的规律：词法、语法、指代、篇章结构、说话者意图、代码依赖、事实共现和任务格式。如果它只记住局部词频，就无法在多样长序列上继续降低 loss。

Transformer 让网络可以按当前 token 的需要组合远近信息；多层非线性表示使低层形式特征逐渐形成更抽象的 context-dependent 特征。所谓“理解”在工程上表现为：内部表示支持语言条件下的预测、迁移和组合，而不是模型内存在一套人类可直接读取的符号解释。

## 2. 世界知识：训练分布的统计压缩

事实、实体与关系反复出现在数据中，会对共享参数产生一致梯度，使模型在相关 context 下给相应 token 更高概率。可以把参数知识理解为：

```text
大量有重复也有冲突的观察
→ 分布式参数更新
→ 在相似 context 中重建高概率关系
```

这种知识具有几个特征：

- **模糊**：不是按键查询，相关模式分散在参数中。
- **有截止与覆盖差异**：取决于训练数据。
- **可能冲突**：不同来源和时间版本共同影响参数。
- **难追溯**：单次生成通常不能给出参数知识的原始来源。
- **可组合但会重构**：模型能把多个模式结合，也可能生成训练中未出现过的错误组合。

## 3. 表示学习与迁移

模型不能为每个表面字符串建立独立规则；共享参数迫使它学习可复用特征。相似任务可以在隐藏表示中复用语义、结构和关系，因此出现 zero-shot 与 few-shot 迁移。

这不意味着模型形成了唯一、稳定、可解释的“概念向量”。表示是高维、分布式、随层与 context 变化的。一个方向可能参与多个特征，一个概念也可能分散在多处。

## 4. In-Context Learning：参数不更新，行为被条件化

给定示例 $D=\{(x_1,y_1),\ldots,(x_k,y_k)\}$，模型输出：

$$
p(y_*\mid x_*,D)
$$

模型在一次前向推理中利用 $D$ 推断任务映射、格式或策略。参数没有更新；context 一旦消失，这次“学习”也消失。

能力来源可能包括：训练数据中大量“模式从上下文延续”的任务、attention 的信息读取、参数中形成的元学习倾向。对开发者最重要的结论是：

- 示例能临时塑形行为；
- 示例质量、顺序和标签偏差会影响结果；
- few-shot 不等于把知识写进模型；
- 示例不能授予工具权限或覆盖系统规则。

## 5. 指令遵循：后训练重塑交互接口

Base Model 学习“什么文本通常接在后面”；Assistant Model 的后训练进一步提高：

$$
p(\text{helpful compliant response}\mid\text{instruction})
$$

SFT 提供理想示范，偏好训练区分更好和更差行为，安全训练提供拒绝与边界样本。这形成一个易用的自然语言接口。

指令遵循不是逻辑解释器：规则会有冲突、歧义、长距离稀释和分布外表达。模型对规则的理解与遵守都是概率行为。

## 6. 推理能力来自哪里

“推理”不是一个单独模块。它通常由以下因素共同形成：

1. 预训练数据包含论证、证明、代码、教程、计划和问题解法。
2. 大容量网络能学习可复用的中间关系和算法近似。
3. 后训练鼓励分解问题、使用中间步骤或延长计算轨迹。
4. 可验证奖励提高能得到正确结果的轨迹概率。
5. 推理时可以采样、搜索、调用工具和验证。

自回归输出本身提供一个外部 scratch space：较长序列可以把复杂映射拆成多个条件预测。但每一步仍可能出错，而且错误 token 会进入后续 context。

### 隐式计算与显式解释不同

模型给出的解释文字是另一段输出，不是内部计算的完整读取。可能出现：

- 结论对，解释错；
- 解释看似合理，结论错；
- 先凭模式得到答案，再生成事后解释；
- 中间步骤正确，但最后抄写或计算错。

因此可读 reasoning 有助于调试和协作，却不是正确性证明。

## 7. “涌现”怎样准确理解

某些 benchmark 在规模增长时表现出突然跃升，可能来自：

- 底层能力连续改善，但离散指标只在超过阈值后记为正确；
- 多项子能力必须同时达到阈值；
- 更大模型更能利用 prompt 和 few-shot 格式；
- 数据、训练方式和评测一起变化。

因此“涌现”可以描述观察到的非线性表现，但不应被解释为模型突然获得无法研究的神秘模块。应查看连续指标、任务分解和评测敏感性。

## 8. 代码能力为何通常较强

代码具有：

- 明确语法和局部结构；
- 大量重复的 API 与模式；
- 跨文件依赖与长程约束；
- 编译器、类型检查和测试等可验证反馈。

这些特征适合序列学习和可验证后训练。但代码模型仍会生成不存在的 API、忽略环境状态或写出只在示例上通过的实现。真正可靠性来自 repository context、执行环境、测试和 review。

## 9. Tool Calling 是学习一种协议

工具调用可以建模为条件生成：

$$
p(\text{tool name},\text{arguments}\mid\text{task},\text{tool schemas},\text{history})
$$

训练数据让模型学会何时选择工具、字段对应什么含义、结果返回后怎样继续。Structured decoding 可以把输出限制在合法语法空间。

模型获得的是协议生成能力，不是工具实现、网络连接或权限。见 [[08-using-assistant-models-in-agents#Tool Call 不是执行|Tool Call 与执行边界]]。

## 10. 多模态能力是统一预测目标下的表示对齐

图像、音频或视频先被编码成连续表示或离散 token，再与语言表示融合。训练让模型把跨模态观察与文本描述、回答和动作联系起来。详细机制见 [[09-multimodal-language-models|多模态大模型专项]]。

多模态能力不是“文本模型突然长出眼睛”：输入编码、采样、融合、训练数据和时序建模共同决定它实际看见什么。

## 11. 能力表现为什么依赖 Prompt

模型计算的是条件分布。相同参数模型面对不同任务描述、示例和输出约束时，条件分布随 context 改变：

$$
p(y\mid x,c_1) \quad \text{与} \quad p(y\mid x,c_2)
$$

Prompt sensitivity 一部分来自任务歧义，一部分来自模型在训练分布中学到的不同模式竞争。好的 prompt 让目标模式清楚，不会为模型新增缺失知识，也不能把统计能力变成系统保证。

## 12. 能力边界的统一判断方式

面对一个任务，按顺序问：

1. **参数中可能有这种模式吗？** 没有则需要数据或工具。
2. **当前 context 提供了必要事实吗？** 没有则需要 retrieval。
3. **模型能在当前长度和噪声下找到并组合它们吗？** 需要任务 eval。
4. **结果能否机械验证？** 能则使用 code、test、schema 或 verifier。
5. **错误影响是什么？** 高风险则加入权限、人工和停止路径。

## 对 Agent 开发的含义

- 用模型处理语义不确定性，而不是把所有规则都改写成自然语言交给模型。
- 用 retrieval 提供最新、私有和可引用事实。
- 用工具与代码提供精确计算、真实执行和环境反馈。
- 用 verifier 把“更长推理”变成可选择的正确轨迹。
- 将模型升级视为能力分布变化，而不是线性全面变强。
