# 文本怎样变成训练数据

> [!abstract] 本章只回答一个问题
> 人写出的文字，怎样一步步变成模型能够读取、预测并用来更新参数的训练样本？

在 [[01-what-an-llm-really-does|上一章]]，我们知道语言模型根据已经看到的 Token 预测下一个 Token。这个说法还留下了两个问题：训练时“已经看到的 Token”和“正确答案”从哪里来？一个整数编号又怎样进入神经网络？

本章始终跟着同一句话走：

> 北京今天下雨，出门要带伞。

读完后，你应该能把它区分成四种不同的东西：原始文档、训练样本中的 Token ID、模型参数里的 Embedding Table。

## 先看最终产物：模型真正拿到的是什么

一篇文章、一个网页或一段代码不是天然的训练题。对自回归语言模型，最终需要的是一对错开一位的 ID 序列：

```text
输入 x:  [北京, 今天, 下雨, ，, 出门, 要, 带, 伞]
目标 y:  [今天, 下雨, ，, 出门, 要, 带, 伞, 。]
```

模型在输入 `x` 的每个位置预测对应的 `y`。例如，看到“北京 今天”后，目标是“下雨”；看到“北京 今天 下雨 ，出门 要 带”后，目标是“伞”。

这些目标原本就存在于同一段文字中，可以从原始数据自动构造，不需要人工为每句话逐项写出标签。这就是**自监督学习**：它仍然有明确的监督目标，只是目标不是人工额外标注的，而是由数据本身产生的。对自回归语言模型来说，这个目标就是前文后面的下一个 Token。

| 学习方式 | 训练目标从哪里来 | 例子 |
|---|---|---|
| 监督学习 | 人工标注 | 人工标记“这张图片是猫” |
| 自监督学习 | 从原始数据自动构造 | 根据前文预测下一个 Token |
| 无监督学习 | 不预先提供明确的预测标签，直接发现数据结构 | 对文本或向量进行聚类 |

从文档到这道“预测题”，再到模型内部计算，完整顺序是：

```mermaid
flowchart LR
    A[原始文档] --> B[解析 清洗 去重 配比]
    B --> C[Tokenizer]
    C --> D[Token ID 流]
    D --> E[错开一位构造 x 和 y]
    E --> F[组成 Batch]
    F --> G[Embedding Lookup]
    G --> H[带位置信息的输入状态]
    H --> I[Transformer]
    I --> J[预测 y 并计算 Loss]
    J --> K[更新模型参数]
```

下面依次解释每个箭头。前半段回答“训练数据怎样做出来”，后半段回答“这批 ID 怎样成为模型能计算的输入”。

## 1. 原始文档先要变成可用文本

训练语料可以来自网页、书籍、代码、对话或其他授权来源，但收集到的内容通常不能直接使用。网页里有导航栏、模板和重复页；文档可能有乱码或错误编码；同一内容也可能被转载许多次。

因此，数据准备会先解析正文，再清洗、去重、筛选语言和质量，并决定各类数据在训练中出现的比例。它的目的不是把文字变得“漂亮”，而是决定模型最终反复练习什么。数据中缺少什么、重复什么、哪些内容比例更高，都会改变模型更容易学到的规律。

处理后的文档仍然只是字符串。我们的例子现在仍是：

```text
北京今天下雨，出门要带伞。
```

下一步才是把字符串切成模型词表能识别的片段。

## 2. 字符串被切成 Token，再映射成 ID

神经网络不能对“北京”或“下雨”这样的字符串直接做矩阵乘法。第一件事是让 Tokenizer 把字符串切成 Token。为了说明主线，先假设它得到：

```text
[北京] [今天] [下雨] [，] [出门] [要] [带] [伞] [。]
```

真实 Tokenizer 不一定按人类词语切分。一个 Token 可能是汉字、词的一部分、标点、空格模式、代码片段或字节。

现代模型常用子词或字节级切分：常见片段可以用较少的 Token 表示；少见名字、拼写和代码仍能拆成已知片段表示。

> [!important] Token 不是“词”的技术叫法
> Token 的主要任务是让任意文本都能在有限词表中表示，同时让序列不要长得难以计算。它不保证每个 Token 都是一个完整概念。

### 以 BPE 为例：从小片段逐步合并

BPE（Byte Pair Encoding，字节对编码）可以把 Tokenizer 理解成一套“常见相邻片段优先合并”的规则。现代模型常见的是 **Byte-level BPE**：先把文本表示成字节或基础字符片段，再学习哪些相邻片段经常一起出现。

以英文片段为例，初始切分可以是：

```text
lower  ->  l o w e r
```

在大量训练文本中，如果 `l` 和 `o` 经常相邻，算法就可能把它们合并成 `lo`；随后继续统计和合并高频相邻片段：

```text
l o w e r  ->  lo w e r  ->  low e r  ->  lower
```

BPE 训练阶段大致重复三步：

1. 从基础字节或字符片段开始；
2. 统计语料中相邻片段对的频率，合并最常见的一对，并把新片段加入词表；
3. 重复合并，直到词表达到设定大小。

使用已经训练好的 Tokenizer 时，不会重新统计语料，而是按学习到的合并优先级处理新文本。

常见的词或词片段可能一次变成一个 Token，少见内容则会退回到更小的片段。Byte-level BPE 的基础单位覆盖字节，因此通常可以把新名字、拼写、表情或代码拆成已知字节片段，而不必为每个新词准备一个独立词表项。

BPE 的结果仍然只是 Token 序列；随后 Tokenizer 再根据固定 Vocabulary 把每个 Token 映射成 Token ID。实际 Tokenizer 还可能包含文本规范化、空格处理、特殊 Token（如文档结束标记）和预切分规则，所以不同模型的 Tokenizer 不能随意混用。

Tokenizer 带着一个固定词表（Vocabulary）。词表做的是 **Token -> Token ID** 映射，而不是“单词 -> ID”映射：

| Token | Token ID |
|---|---:|
| 北京 | 15432 |
| 今天 | 8921 |
| 下雨 | 23781 |
| 伞 | 6843 |

于是同一句文本会变成类似：

```text
[15432, 8921, 23781, ..., 6843, ...]
```

ID 只是索引。`23781` 比 `8921` 大，不代表“下雨”比“今天”更重要，也不代表两者的意思相差 `14860`。

在训练大模型前，通常先用代表性语料训练或选定 Tokenizer；此后 Token 与 ID 的对应关系一般保持不变。原因很快会看到：ID 将直接对应 Embedding Table 中的一行。若把一个 ID 改指另一个 Token，模型会取到错误的那一行参数。

## 3. ID 流被组织成训练样本

现在我们有了连续的 Token ID 流，但它还不一定正好是一条训练样本。Transformer 一次接收的 Token 数量通常有上限，称为最大序列长度（Context Length）；过长的文档需要切分成多个不超过上限的片段。对于较短的文档，可以在文档边界加入结束标记（EOS）后拼接到同一条序列中，再按长度组成训练样本，并通过边界处理避免把不同文档误当成连续文本。

对我们这句短文本，可以直接把同一串 Token 错开一位：

```text
输入 x:  [北京, 今天, 下雨, ，, 出门, 要, 带, 伞]
目标 y:  [今天, 下雨, ，, 出门, 要, 带, 伞, 。]
```

这不是两份独立标注数据，而是同一序列错开一位后的两个视图。对应关系是：看到“北京”预测“今天”，看到“北京、今天”预测“下雨”，看到前面的内容直到“伞”预测“。”。也就是说，`y` 中每个位置的目标，都是 `x` 中对应位置的下一个 Token。

### 自回归

“自回归”指的是：模型用已经出现的 Token 预测下一个 Token；新生成的 Token 又会被接回序列，作为下一轮预测的输入：

```text
北京
→ 北京 今天
→ 北京 今天 下雨
→ 北京 今天 下雨 ，
→ 北京 今天 下雨 ， 出门
```

训练时，真实文本已经存在，所以可以把整条序列错开一位，在所有位置并行计算“下一个 Token”的预测。因果 Mask 会限制每个位置只能读取当前位置及其左侧的输入 Token，不能偷看未来。

实际生成时没有真实的下一个 Token 可直接提供，模型只能把自己刚生成的 Token 接回输入，再预测下一个 Token。因此，生成过程是“预测一个、接回一个、继续预测”的循环，直到生成结束 Token 或满足其他停止条件。

许多这样的 `(x, y)` 样本一起组成 Batch，送入设备计算一次 Loss。为了提高利用率，短序列可以 Packing 到同一长度内；需要补齐时则使用 Padding，并让 Loss Mask 忽略填充位置。

| 名称 | 在本章中的含义 |
|---|---|
| 原始文档 | 收集并清洗后的一个内容单位，例如一篇网页或一段代码 |
| Token ID 流 | 文档 Tokenize 后得到的一串整数 |
| 训练样本 | 一段长度受限的输入 `x` 和对应的下一 Token 目标 `y` |
| Batch | 同时计算的多条训练样本 |

> [!note] 到这里，训练数据仍是离散 ID
> 预训练数据通常保存为文本或 Token ID，而不是预先计算好的文档向量。每个 Batch 真正进入模型时，才会由模型自己的 Embedding Table 把每个 ID 变成向量。

这就带来下一个问题：为什么不能把 ID 直接交给 Transformer？

## 4. ID 通过 Embedding Table 进入模型

Transformer 的核心计算是向量和矩阵运算。整数 ID 只表示“去哪里找”，本身没有可供模型连续调整的数值结构。因此，模型保存一张可学习的 Embedding Table；每个 Token ID 对应其中一行。

把词表大小记为 `V`，模型内部向量维度记为 `d_model`。Embedding Table 的形状是 `(V, d_model)`：有 `V` 行，每行有 `d_model` 个浮点数。

用一个很小的表来观察：

| Token ID | 对应的一行向量 |
|---:|---|
| 0 | `[0.10, 0.20, 0.30]` |
| 1 | `[0.50, 0.60, 0.70]` |
| 2 | `[0.90, 1.00, 1.10]` |
| 3 | `[2.00, 2.10, 2.20]` |

这张表的形状是 `(4, 3)`。当 Token ID 为 `2` 时，Lookup 只是取出第三行 `[0.90, 1.00, 1.10]`，得到一个长度为 3 的向量；不会把整张表送入 Transformer。

写成公式就是：

$$
x_i = E[t_i]
$$

其中 $t_i$是第 `i` 个 Token 的 ID，$E$ 是整张表，$x_i$ 是取出的那一行。==这是查表，不是把 ID 当作数值做算术。==

因此，`(100000, 4096)` 表示“10 万行、每行 4096 个数”的表形状。只有讨论参数量时才相乘：这张表有 `100000 * 4096` 个可训练数值。它只是模型参数的一部分；日常说的 7B、32B 指 Embedding Table、各层 Attention、FFN 和其他参数加起来的总数。

回到我们的 Batch：其中的每个 ID 都各查一行，整条输入序列就从一串整数变成“一列同样维度的初始向量”。此时它终于可以进入后续网络。

## 5. 这些向量为什么会变得有用

Embedding Table 不是人工把“下雨”写成一组有意义的数字。训练开始时，表中的数值和 Attention、FFN 等权重一样接近随机。模型用刚才的输入 `x` 预测目标 `y`，预测得不好就产生 Loss；==反向传播就是从 Loss 出发，反向计算每个参数对这次误差产生了多大影响，从而为优化器指出参数调整的方向和依据。==其中也包括本次 Lookup 到的 Embedding 行。

这个循环会在海量样本上重复：

```text
一批 Token ID
-> Lookup 初始向量
-> Transformer 给出下一个 Token 的预测
-> 与目标 y 比较得到 Loss
-> 反向传播计算各参数的梯度
-> 优化器更新 Embedding Table 和其他参数
```

经过大量更新，某些经常出现在相似预测环境中的 Token，初始向量可能在某些方向上更接近。但不要把它理解成一张人工设计的“语义坐标表”：单个维度通常没有可直接命名的人类含义，预测能力来自 Embedding 和所有后续层共同形成的计算。

这里也能回答“Embedding Table 固定吗”：Token 与 ID 的映射通常固定；Embedding Table 的数值在训练中会学习。训练完成并加载模型后，推理时权重不再自动改变，所以同一个 ID 总会查到同一个初始向量。

不过，“初始向量相同”不等于它在不同句子里始终表示同一件事。

## 6. 初始 Embedding 还没有理解上下文

目前，$E[t_i]$ 只取决于 Token ID。以“苹果”为例，无论它出现在“吃了一个苹果”还是“发布了新款苹果设备”中，查表取出的初始 Token Embedding 都相同。模型还必须知道位置，并让每个位置结合前文。

位置很重要：

```text
狗追猫
猫追狗
```

两句包含相同 Token，但顺序不同。模型会先把位置相关信息加入或作用到初始向量上，得到第一层的输入状态。随后 Transformer 才逐层改写每个位置的表示。

这个被逐层改写的内部向量叫 **Hidden State（隐藏状态）**。它不是额外存储的训练数据，也不是某个固定参数；它是一次前向计算中、每个位置在每一层的临时状态。“隐藏”只表示它是网络内部中间值，不是最终输出的文字。

```text
Token ID
-> Token Embedding
-> 加入位置相关信息，得到第 0 层输入状态
-> Transformer Block 反复更新，得到各层 Hidden State
-> 最后一层 Hidden State
-> 输出层给出整个词表的 Logits
```

因此，“吃了一个苹果”和“发布了新款苹果设备”中的“苹果”从相同的初始向量出发，却会得到不同的 Hidden State。最后一个位置的 Hidden State 经过输出层，才成为每个候选 Token 的分数（Logits），用于预测下一个 Token。

> [!important] 本章和下一章的边界
> 本章把训练样本构造到“初始向量进入模型”为止，并定义 Hidden State 是什么、为什么会出现。下一章 [[03-transformer-and-modern-architecture|Transformer 与现代架构]] 再解释模型具体怎样读取前文、更新状态并产生 Logits。

## 本章闭环

```text
原始文档
-> 清洗、筛选、去重和配比
-> Tokenizer 切成 Token
-> 词表映射成 Token ID
-> 错开一位构造输入 x 与目标 y
-> 多个样本组成 Batch
-> Embedding Table 把每个输入 ID 查成初始向量
-> 加入位置信息后交给 Transformer
-> 预测目标 y，Loss 反过来更新参数
```

从这里开始，问题不再是“训练题目从哪里来”，而是“Transformer 怎样让每个位置利用前文”。下一章继续这条链路。
