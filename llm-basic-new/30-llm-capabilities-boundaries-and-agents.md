# 模型能力、边界与 Agent

> [!abstract] 本章回答什么
> 大模型适合完成哪些任务，为什么会失败，以及把它放进 Agent 系统后，模型、工具、代码和状态应该怎样分工？

## 前置知识

前面已经建立三个事实：模型根据 Context 和权重逐 Token 生成；后训练改变行为倾向而不是提供硬保证；API 可以把工具描述交给模型，但真正执行发生在外部。

## 能力来自哪里

模型能力不是来自单一阶段：

- 预训练数据提供语言、知识、代码和任务模式；
- Transformer 提供在上下文中组合信息的计算结构；
- 模型规模和计算增加可表示和学习的规律；
- 后训练塑造指令遵循、工具协议和安全行为；
- 当前 Context 提供任务、证据和示例；
- 推理时计算、搜索和工具结果可以扩展当次能力。

因此，“模型能不能完成任务”不能只看一个固定能力清单，还取决于输入、工具、风险和验收标准。

## 模型擅长的任务

模型通常适合处理语义开放、规则难以穷举、结果容易复核的工作：

- 总结、改写、翻译和信息抽取；
- 对非结构化文本分类；
- 生成草稿、候选方案和解释；
- 根据描述选择可能适用的工具；
- 结合给定材料回答问题；
- 生成和解释代码候选；
- 把自然语言转换成结构化意图。

这些任务的共同点是：语言模式和上下文理解很重要，允许系统在模型输出后继续检查。

## 有条件才能完成的任务

以下任务模型可以参与，但必须提供外部条件：

| 任务 | 需要补充什么 |
|---|---|
| 回答最新事实 | 搜索、数据库或实时 API |
| 回答私有知识 | 检索和访问控制 |
| 精确计算 | 计算器或代码执行 |
| 修改真实系统 | 有权限的工具和执行确认 |
| 长任务 | 持久状态、计划和恢复机制 |
| 高风险决策 | 明确规则、独立验证和人工门控 |

模型负责理解和提出候选，外部系统提供事实、执行和保证。

## 不应只交给模型的任务

- 用户身份和权限判断；
- 金额、计数、日期等必须精确的计算；
- 事务、锁、幂等和一致性；
- 真实任务进度的长期保存；
- 不可逆操作的最终授权；
- 法规和安全规则的强制执行；
- 对自身回答的最终真实性证明。

这些任务需要确定性规则、可信数据源或独立责任主体。

## 为什么会幻觉

模型的直接目标是生成在当前条件下高概率的后续 Token，没有一个内置变量自动表示“这句话已被现实世界验证”。当证据不足时，它仍可能组合出形式合理的名字、引用和细节。

后训练可以让模型更常承认未知，但不能从概率生成目标中推出事实保证。

## 参数知识不是数据库

模型权重没有稳定记录 ID、原始来源、更新时间和精确删除接口。需要最新、私有、可引用或会变化的事实时，应查询外部数据源，并把结果作为当前证据提供给模型。

## Context 足够长不等于一定会使用

模型可能因为信息位置、干扰、冲突、距离和需要组合的事实数量而漏用内容。把所有文档塞进 Context 只是让信息“可见”，不代表它会被准确定位和使用。

## 推理错误为什么会积累

复杂任务常由多个依赖步骤组成。前一步一旦错误，后续可能在错误前提上继续生成得很流畅。生成更多解释不保证纠正，因为自我检查仍使用相同权重和相似 Context，可能共享原来的盲点。

高可靠任务需要独立验证，例如单元测试、数据库约束、计算器、第二数据源或人工审核。

## 什么是 Agent

Agent 不是一种神奇的新模型。它是把助手模型放进一个可循环观察和行动的运行环境：

~~~mermaid
flowchart LR
    A[目标与当前状态] --> B[模型提出下一步]
    B --> C[验证与权限检查]
    C --> D[工具实际执行]
    D --> E[返回真实结果]
    E --> F[更新持久状态]
    F --> G{任务完成或达到限制}
    G -->|否| A
    G -->|是| H[结果]
~~~

模型提供语义决策能力；Agent Runtime 提供工具、循环、状态、权限、验证和停止条件。

## 必须区分的六个对象

| 对象 | 负责什么 | 不负责什么 |
|---|---|---|
| 模型权重 | 训练形成的通用规律 | 当前任务真实状态 |
| Context | 本次调用可见的信息 | 自动长期保存 |
| Memory | 检索和重新提供历史信息 | 业务事实唯一真相 |
| State | 记录真实任务进度和结果 | 自然语言推理 |
| Tool | 查询或改变外部世界 | 自主决定是否有权限 |
| Agent Runtime | 组织循环、权限和验证 | 代替模型做所有语义理解 |

## Tool Call 不是执行

模型生成“调用转账工具，金额 100 元”只是一份候选请求。系统仍应：

1. 验证 JSON 和字段类型；
2. 校验金额、账户和业务规则；
3. 检查用户权限；
4. 必要时要求明确确认；
5. 使用幂等键执行；
6. 读取真实结果；
7. 更新状态和审计日志。

模型说“已经完成”也不能证明外部动作成功，只有工具结果和真实系统状态可以证明。

## 怎样设计工具

### 职责单一

一个工具完成清楚、可验证的动作。不要把“分析并修改所有相关系统”藏在一个模糊工具中。

### 名称和参数语义明确

写清单位、格式、必填条件和副作用。Schema 负责结构，描述帮助模型选择。

### 最小权限

模型只能看到和调用当前任务必要的工具。只读和写入工具分开，高风险工具增加确认。

### 返回机器可判定结果

工具应返回成功状态、错误码、资源 ID 和关键字段，而不是只返回“操作完成”这样的自然语言。

## Agent Loop 的控制权必须在外部

外部 Runtime 应控制：

- 最大步数和总 Token；
- 时间和费用预算；
- 工具超时与重试；
- 重复调用检测；
- 失败和取消状态；
- 人工接管；
- 最终停止条件。

不能只让模型自己决定“何时算完成”，因为它可能过早结束、无限循环或把计划当成结果。

## 什么任务不需要 Agent

如果步骤稳定、分支有限、规则明确，普通工作流通常更可靠：

~~~text
固定校验 → 查询数据库 → 调用服务 → 写入结果
~~~

只有当中间步骤需要根据非结构化观察动态选择，且这种灵活性带来的收益大于不确定性时，Agent Loop 才更有价值。

## 风险决定自主程度

| 风险 | 合适策略 |
|---|---|
| 低风险、可撤销 | 可自动执行并记录 |
| 中风险、有副作用 | 执行前规则校验，必要时确认 |
| 高风险、不可逆 | 强权限、独立验证、人工批准 |

模型能力强弱不能改变动作本身的风险等级。

## 怎样评测 Agent

只看最终回答不够，还要检查轨迹：

- 是否选对工具；
- 参数是否正确；
- 是否使用了真实结果；
- 是否出现重复或无效步骤；
- 是否违反权限和预算；
- 失败后是否进入正确状态；
- 最终结果是否可验证。

评测应使用真实任务分布和失败案例，而不是只展示成功 Demo。

## 最终分工原则

> [!important] 一条最实用的边界
> 模型负责理解语义、生成候选和选择下一步；确定性系统负责真实事实、权限、执行、状态、一致性和最终验证。
